## 1. B4 — 三阶段主路径 Stage 2 RAG 检索失败

### 1.1 根因分析

评估发现三阶段编辑视角提案的主路径运行时 100% 回退到旧版三维度。Stage 2 的 RAG 检索调用 Go 后端 `/v1/embeddings` 代理接口，该接口恒定返回 500。

定位到两个层面的问题：

**问题 A — Go 配置模板缺少 `Embedding` 段**

Go Config 结构体（`backend/internal/defaultService/conf/conf.go`）定义了 `Embedding` 字段：

```go
Embedding struct {
    APIKey  string
    Model   string `default:"doubao-embedding-vision-251215"`
    BaseURL string `default:"https://ark.cn-beijing.volces.com/api/v3"`
}
```

但配置模板（`configs/config.yaml`）的 Go 段（`Log`/`Http`/`Sqlite`/`Storage`/`VLM`）中没有 `Embedding` key。虽然 Python agent 侧的 `embedding` 段存在（小写），但 Go 侧 `getEmbeddingConfig()` 的回退逻辑是先检查 `Embedding.APIKey`（空），再回退到 `VLM.APIKey`（在配置模板中也为空占位符），最终构造出的 `BaseURL` 为空字符串。

Model 和 BaseURL 在 Go struct 中已有 `default` tag，无需在配置模板中重复提供默认值。配置模板只需补充 `Embedding` 段的**结构**（含 `APIKey` 占位），实际值由用户本地配置文件（如 `.local/pancake.yaml`）提供，该文件已在 `.gitignore` 中，不会提交入库。

**问题 B — 错误日志不可观测**

`callVolcengineEmbedding`（`svc_embedding.go:177-213`）使用 `putil.HttpDo` 发送 HTTP 请求，该函数在非 200 响应时返回的错误信息仅为 `"status code : XXX"`，丢弃了火山引擎返回的响应体。运维人员无法从日志中判断是认证失败、模型不存在、还是配额超限。

### 1.2 方案

**改动 1 — 配置模板补充 Embedding 段结构**

在 `configs/config.yaml` 的 Go 段（`VLM` 之后）新增 `Embedding` 段，只提供 `APIKey` 占位，Model 和 BaseURL 依赖 Go struct 的 `default` tag：

```yaml
Embedding:
  APIKey: ""
```

用户的本地配置文件（如 `.local/pancake.yaml`）中已有完整的 embedding 配置值，无需在模板中重复默认值。

**改动 2 — Go embedding 代理增强错误日志**

修改 `callVolcengineEmbedding`：在 `putil.HttpDo` 返回错误时，用 `putil.HttpDoWithBody` 或自行读取响应体，将火山引擎返回的错误详情包含在错误信息中。改动后日志格式类似：

```
request failed: status code 403, body: {"error":{"code":"InvalidApiKey","message":"..."}}
```

同时，在 `getEmbeddingConfig()` 返回空 `BaseURL` 时，handler 应直接返回明确的错误信息（如 `"embedding not configured: BaseURL is empty"`），而非发一个必然失败的 HTTP 请求。

**改动 3 — Go 启动时配置校验（可选，低优先级）**

在服务启动时检查 `Embedding` 配置的有效性，若 `BaseURL` 为空则输出 warning 日志。此为锦上添花，非阻塞性修复。

### 1.3 影响范围

- `configs/config.yaml`：新增 Embedding 段
- `backend/internal/defaultService/service/svc_embedding.go`：增强错误日志，增加空 BaseURL 前置校验

## 2. B5 — 三阶段主路径前置检查缺失

### 2.1 根因分析

当前 `run_suggest`（`suggest.py:1012-1191`）的执行流程：

```
数据采集 → Stage 1（LLM 主题直觉）→ Stage 2+3（RAG 扩展 → LLM 提案）
                                              ↓ 失败
                                         回退路径（三维度分析）
```

Stage 1 会在 embedding 不可用时仍然消耗 LLM token 生成主题直觉（评估中 3 个直觉的 LLM 调用白白浪费），然后因 Stage 2 RAG 全部失败而丢弃这些结果。当前 `_stage2_expand_selection` 只在 RAG 调用失败时 catch 异常并返回空列表，但没有在进入三阶段流程前做前置可用性检查。

### 2.2 方案

在 `run_suggest` 的 Stage 1 之前，插入一个轻量的 embedding 可用性检查：

**方案选择**：

- 方案 A：新增 Go 后端 `/v1/embeddings/health` 端点，Python 侧在调用 Stage 1 前做一次健康检查
  - 利：独立端点，语义清晰
  - 弊：需要 Go 和 Python 两侧改动
- 方案 B：Python 侧直接发一个最小 embedding 请求（如文本 `"health"`）测试可用性
  - 利：无需新增 API，改动集中在 Python 侧
  - 弊：浪费一次实际 embedding 调用（虽然成本极低）
- 方案 C：在 B4 改动 2 的基础上（Go 返回明确错误信息），Python 侧在数据采集阶段同时检查 embedding，通过一个简单的 HTTP 探测

推荐 **方案 A**，因为健康检查端点是标准做法，且可以与 B4 的 Go 侧改动一起完成。

### 2.3 实现步骤

**Go 侧**：
1. 新增 `GET /v1/embeddings/health` 端点，调用 `getEmbeddingConfig()` 检查配置有效性，返回 `{"status":"ok","model":"..."}` 或 `{"status":"unconfigured","reason":"BaseURL is empty"}`

**Python 侧**：
2. `run_suggest` 在 Stage 1 之前调用 `GET /v1/embeddings/health`
3. 若不可用，跳过三阶段主路径，直接走回退路径，日志记录跳过原因
4. 健康检查失败时 `meta["pipeline"]` 设为 `"legacy_three_dimension"`，与当前回退路径一致

### 2.4 影响范围

- `backend/internal/defaultService/service/svc_embedding.go`：新增 health handler
- `agent/chain/suggest.py`：`run_suggest` 新增前置检查逻辑

## 3. B6 — `_fetch_all_photos` 仅返回 300 张

### 3.1 根因分析

调用链路中存在 `page_size` 截断不一致的问题：

1. `suggest.py` 的 `_fetch_all_photos` 请求 `page_size=500`
2. Go DAO 层（`dao_photo.go:57-59`）将 `PageSize` 截断到最大 100：
   ```go
   if params.PageSize > 100 {
       params.PageSize = 100
   }
   ```
3. Go handler（`svc_photo.go:84-87`）用**未截断的** `params.PageSize` 计算 `totalPages`：
   ```go
   totalPages = int32((int(total) + params.PageSize - 1) / params.PageSize)
   // 1177 张照片，pageSize=500 → totalPages = ceil(1177/500) = 3
   ```
4. Python 循环 `page=1..3`，每页实际返回 100 条 → 最多 **300 张**

`embed_queue.py` 中的同名函数不受影响（它请求 `page_size=100`，与截断后一致）。

### 3.2 方案

**方案选择**：

- 方案 A：在 Go handler 中将 `page_size` 截断逻辑前置，确保计算 `totalPages` 时使用的是截断后的值
  - 利：修复在 Go 侧，所有调用方受益；不依赖客户端传对参数
  - 弊：Go handler 中需要重复 DAO 的截断逻辑（或提取公共函数）
- 方案 B：在 Python 调用方将 `page_size` 改为 100，请求与实际一致
  - 利：改动最小（一行）
  - 弊：只修了一个调用方，其他调用方仍可能踩坑；治标不治本

推荐 **方案 A**（Go 侧修复），同时 Python 侧 `suggest.py` 的 `_fetch_all_photos` 也把 `page_size` 改为 100 作为防御性编程。

### 3.3 实现步骤

**Go 侧**：
1. 在 `svc_photo.go` 的 `SearchPhotos` 中，构建 `params` 后立即做截断：
   ```go
   if params.PageSize < 1 {
       params.PageSize = 20
   }
   if params.PageSize > 100 {
       params.PageSize = 100
   }
   ```
2. DAO 层 `GetPhotoList` 中的截断逻辑保留（防御层），但 handler 层先截断后 `totalPages` 计算就正确了

**Python 侧**：
3. `suggest.py` 的 `_fetch_all_photos` 中 `page_size=500` 改为 `page_size=100`（减少歧义，与后端上限一致）

**备选优化**（本次不做）：
- 提高 DAO 的 `PageSize` 上限到 500 或更大，减少分页请求次数
- 新增 `GET /api/v1/photos?page_size=0` 的"不分页"模式

### 3.4 影响范围

- `backend/internal/defaultService/service/svc_photo.go`：`SearchPhotos` 新增 page_size 截断
- `agent/chain/suggest.py`：`_fetch_all_photos` 的 `page_size` 改为 100

## 4. R5 — 选题模块 JSON 解析逻辑重复

### 4.1 根因分析

`_parse_intuitions_response`（Stage 1 用，`suggest.py:204-251`）和 `_parse_legacy_response`（回退路径用，`suggest.py:906-951`）的解析策略完全一致：

1. 尝试直接 `json.loads`
2. 如果以 ` ``` ` 开头，去掉 markdown 标记后重试
3. 正则提取 JSON 数组 `[...]` 后重试
4. 正则逐对象提取 `{...}` 后重试
5. 失败时 log warning，返回空

两份函数各自约 40 行，差异仅在：
- 日志前缀（`"Stage 1 LLM 主题直觉响应"` vs `"备选路径 LLM 响应"`）
- Stage 1 版本接受 `list` 或单个 `dict`（带 `title` key），legacy 版本同样接受两种格式

实际上没有实质差异，可以合并。

### 4.2 方案

提取公共函数 `_parse_llm_json_response(raw, context_label)`：

```python
def _parse_llm_json_response(raw: str, context_label: str = "") -> list[dict]:
    """通用 LLM JSON 响应解析：直接解析 → 去 markdown → 正则提取数组 → 逐对象提取。"""
    # ... 合并后的解析逻辑，使用 context_label 构造日志
```

两个现有函数改为调用公共函数：

```python
def _parse_intuitions_response(raw: str) -> list[dict]:
    return _parse_llm_json_response(raw, "Stage 1 主题直觉")

def _parse_legacy_response(raw: str) -> list[dict]:
    return _parse_llm_json_response(raw, "备选路径选题建议")
```

### 4.3 影响范围

- `agent/chain/suggest.py`：新增 `_parse_llm_json_response`，简化两个现有函数
- 仅重构，不改变行为，现有测试应通过
