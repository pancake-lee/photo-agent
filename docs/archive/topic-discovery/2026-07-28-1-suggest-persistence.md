# 主题发现持久化存储 + 打分

> 状态：✅ 已实现（2026-07-28）
> 关联中枢：[2026-07-27-5-topic-discovery-hub.md](2026-07-27-5-topic-discovery-hub.md)

---

## 1. 问题背景

当前主题发现（`SuggestView.vue` + `POST /api/suggest/run`）的数据流是：

```
用户点击「生成选题建议」→ Agent 计算 → 返回 JSON → 前端 ref 临时持有
```

**缺陷**：
- 刷新页面后结果消失，无法回溯历史选题
- 无法对历史结果做比较/筛选/打分
- 每次想回顾之前的选题建议，必须重新跑一遍 LLM（费 token 且结果不同）

## 2. 需求概述

1. **持久化存储**：每次生成的选题结果自动保存，刷新页面后仍可查看历史
2. **删除**：每条历史结果可单独删除
3. **时间倒序**：历史列表按生成时间倒序排列（最新在上面）
4. **五星打分**：每条结果展示 5 颗星，用户点击任意一颗点亮该星及左侧所有星（1-5 分）

## 3. 存储方案

### 3.1 存储位置

Agent 层 JSON 文件存储，路径：`agent/data/suggest_history.json`

遵循项目既有模式（黄金用例用 `golden_queries.json`，聚类结果用 `data/clusters/*.json`）。

### 3.2 数据结构

每个主题（topic）作为独立记录存储。一次生成 N 个主题即写入 N 条记录。

```json
[
  {
    "id": "abc123def456",
    "generated_at": "2026-07-28T15:30:00",
    "pipeline": "editorial_three_stage",
    "total_photos": 1200,
    "cluster_count": 15,
    "rating": 0,
    "title": "晨昏之间的城市",
    "angle": "...",
    "rationale": "...",
    "category": "editorial_proposal",
    "photo_ids": ["uuid1", "uuid2"],
    "error": ""
  }
]
```

字段说明：
- `id`：12 位 hex，每个主题独立分配
- `rating`：0-5 整数，0 表示未打分，每个主题独立评分
- `total_photos`、`cluster_count`、`generated_at`、`pipeline`：来自同一次生成批次的元信息，在同一批次的各主题间值相同
- 不再嵌套 `suggestions` 数组，每个记录就是一个主题

### 3.3 为什么不选 SQLite

项目已有 `chat_sessions.db`（SQLite），但选题历史的数据特点是：
- 单条记录大（含完整 suggestions 数组），适合文档存储而非关系表
- 查询模式简单（全量列表 + 单条 CRUD），JSON 文件加内存缓存足够
- 与黄金用例（`golden_queries.json`）的存储模式一致，降低认知负担

## 4. API 设计

全部新增在 Agent（Python FastAPI）的 `/api/suggest/` 路径下。

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/api/suggest/run` | 现有接口，**改为每个主题独立保存，返回 `{items, count, error}`** |
| `GET` | `/api/suggest/history` | 获取历史列表（时间倒序） |
| `GET` | `/api/suggest/history/{id}` | 获取单条历史详情 |
| `DELETE` | `/api/suggest/history/{id}` | 删除单条历史 |
| `PATCH` | `/api/suggest/history/{id}/rating` | 更新打分 `{"rating": 3}` |

`POST /api/suggest/run` 的返回增加 `id` 字段，方便前端定位刚生成的记录。

## 5. 前端改动

### 5.1 页面结构变化

当前页面：空状态 → 点击生成 → 单次结果展示

改为：

```
┌─ 页面头部 ─────────────────────────────────────┐
│ 主题发现                    [生成选题建议]      │
└────────────────────────────────────────────────┘
┌─ 历史列表（时间倒序，每个卡片 = 一个主题）─────┐
│ ┌─ 卡片 1 ───────────────────────────────────┐ │
│ │ 晨昏之间的城市  📝编辑提案  ★★★☆☆  [删除] │ │
│ │ 2026-07-28 15:30 | 编辑视角 | 照片:1200    │ │
│ │ 发布角度：...                              │ │
│ │ 选题理由：...                              │ │
│ │ 推荐照片：[缩略图]                         │ │
│ └────────────────────────────────────────────┘ │
│ ┌─ 卡片 2 ───────────────────────────────────┐ │
│ │ 季节的色彩    📅时间线规律  ★★★★★  [删除] │ │
│ │ ...                                        │ │
│ └────────────────────────────────────────────┘ │
└────────────────────────────────────────────────┘
```

### 5.2 交互细节

- **每张卡片就是一个主题**：一次生成 3 个主题，列表增加 3 张卡片，不再按批次分组
- **打分**：5 颗星横向排列，未打分时全部灰色空心。点击第 N 颗星，第 1~N 颗变为金色实心，其余保持灰色空心。点击已点亮的星可取消（恢复为 0）。每个主题独立打分
- **删除**：卡片右上角删除按钮，点击后确认弹窗
- **新生成**：生成完成后新主题自动插入列表顶部

### 5.3 组件划分

- `SuggestView.vue`：页面容器，管理历史列表状态，每个卡片直接渲染一个主题（标题、分类、角度、理由、照片、打分、删除）

## 6. 生成数量说明

当前数量由 LLM 自主决定（见 `suggest.py`）：
- 主路径 Stage 1 prompt："输出 2-4 个选题直觉"，temperature=0.8
- 备选路径 prompt："选出 3-5 个最有价值的选题"，temperature=0.7
- 主路径 Stage 3 还会因 RAG 扩展照片不足（<5 张）进一步过滤

如果希望数量稳定，可以在 prompt 中改为固定数值（如"输出 3 个"），但当前设计有意保留 LLM 的灵活性——选题质量优先于数量。**本次不做改动，保持现状。**

## 7. 验收标准

1. ✅ 生成选题建议后刷新页面，历史结果仍在 *(代码已实现，需重启 agent 服务 + 重编 web 前端后验证)*
2. ✅ 历史列表按时间倒序排列
3. ✅ 可删除任意一条历史，删除后列表即时更新
4. ✅ 五星打分可点击，点亮/取消逻辑正确
5. ✅ 打分结果持久化（刷新后保持）
6. ✅ 空历史时展示与当前一致的空状态

## 8. 不做的事

- 不修改生成数量逻辑（保持 LLM 自主决定）
- 不添加编辑/修改建议内容的功能（本次只做存储+打分）
- 不添加搜索/筛选（数据量小，后续需要再加）
