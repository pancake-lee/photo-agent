> 归档日期：2026-08-18
> 涵盖范围：v1.0.8（2026-08-01）之后完成的全部任务
> 版本主题：**导入工作流（Windows 客户端）** — 把「相机拍摄后导入照片库」串成桌面端三步引导流程

## 版本概述

v1.0.9 的核心是新增 Wails 桌面客户端（Windows），将原本手动的导入流程（建目录、比对 full/like/nef、迁移 NEF、上传服务器）串成 `#/import` 三步引导：新建活动 → 分析报告 → 上传同步。客户端内嵌现有 Vue 3 前端，同时充当 Photo Agent 的桌面入口。

架构分工：文件处理（本地扫描/EXIF/复制）由客户端 Go 承担，上传走客户端 Go 直连服务端（浏览器读不了本地文件且服务端无 CORS），服务端仅新增 NEF 存储与 storage/info 查询。NEF 仅存储不处理（不压缩/VLM/Embedding）。

**关键数字**：

- 完成 **4 个阶段需求**（W1-W4）+ **7 个衍生修复**（W5-W11）
- 评估 **3 轮**：7.7 → 8.3 → 8.4，W1-W11 代码侧全部闭环
- 新增 **client/ 模块**（Go 约 2200 行含测试）+ **ImportWorkflow.vue**（1010 行）+ 服务端 svc_storage.go
- 新增 **2 个服务端端点**（GET /api/v1/storage/info、POST /api/v1/storage/conflicts）
- 实测数据一致性：storage/info 计数 = 存储目录实扫 = DB 记录（146 JPG + 113 NEF ↔ 259 条）

**实测结论（2026-08-18）**：用户已实测一次，三步流程功能基本可用。剩余细节问题转为日常使用中的缺陷修复流程处理，不再阻塞本版本。

## 一、桌面客户端与三步流程（W1-W4）

> 设计文档：[2026-08-11-import-workflow.md](../design/2026-08-11-import-workflow.md)

### W1 Wails 工程搭建

- Wails v2.9.1 项目落位 `client/`，因 `wails build` 与 Go 1.24 不兼容，改用 `CGO_ENABLED=1 go build` 直接构建，前端资源 `//go:embed` 嵌入二进制
- 前端环境检测 `web/src/utils/env.ts`（检测 `window.go.main.App`），Wails 环境才显示导入入口
- DevTools 调试：WebView2「右键 → 检查」通过持久幽灵选区方案稳定启用（App.vue）；F12/Ctrl+Shift+I 快捷键确认不可行后放弃

### W2 服务端 NEF 存储

- `POST /api/v1/photos/upload` 识别 `.NEF` 后缀：跳过压缩/VLM/Embedding，直接存入月份/活动目录并写 DB（标记文件类型）
- `GET /api/v1/storage/info` 返回存储根的总文件数（JPG/NEF）、月份/活动目录列表、上次同步时间；存储根不可访问时返回 200 + warning
- `POST /api/v1/storage/conflicts` 上传前冲突检测
- 文件夹命名：`202608/`（随手拍）、`202608-山西旅游/`（有活动，`-` 分隔符）

### W3 客户端文件操作

- 扫描中转三目录 `full/ like/ nef/`（各含归档子目录 `YYYYMM-活动名`），返回文件列表与计数
- 比对分类（术语：收藏/留存/废弃）：like 有同名 JPG 的 NEF 保留迁移；已在 like 的记已迁移；仅 full 有的跳过；full/like 都没有的跳过
- EXIF 读取拍摄时间，相邻最大间隙启发式（阈值 7 天）检测混入其他活动的照片
- 执行阶段确立「**仅复制不删除**」原则：只复制收藏 NEF 到 like 目录，删除交还用户

### W4 前端三步流程

- `#/import` 路由 + ImportWorkflow.vue：步骤 1 新建活动（日期/名称/中转路径，客户端建目录，展示文件数与刷新确认）；步骤 2 分析报告（统计摘要/时间警告/折叠明细，确认后执行迁移）；步骤 3 上传同步（服务器地址验证 → 并行上传 → 结果统计）
- 上传与 storage/info 均走客户端 Go：`client/sync.go` 的 `syncLikeDir`（3 并发 POST upload，携带 folder 字段）与 `fetchStorageInfo`，经 `app.go` 暴露绑定；前端 `wails.ts` 统一封装

## 二、衍生修复（W5-W9，首轮评估产出）

- **W5 StorageRoot 分叉**：删除独立 StorageRoot 配置，storage/info 直接扫描上传落盘的 PhotoSrc，「总文件数」与「本次新增」天然同源
- **W6 overwrite 回写 shot_at**：覆盖同名文件时同步回写拍摄时间与 GPS，与 createPhotoRecord 字段口径对齐
- **W7 NEF EXIF 策略一致**：实测 113 个 NEF 服务端均成功读取，保留现状；修正客户端「防 goexif 卡死」的误导注释
- **W8 warning 展示**：存储根不可访问时前端用 NAlert 展示 warning，不再静默全 0
- **W9 上传进度**：客户端每完成一个文件经 Wails 事件推送进度，前端展示「已完成 X/N」进度条，完成后替换为结果统计

## 三、衍生修复（W10-W11，二轮评估产出）

- **W10 上传重试**：单文件失败自动重试 1 次（固定等待 2 秒），重试成功不计失败；前端有失败时提示手动「开始同步」（skip 模式只传失败文件构成第二层重试）；同步完成后自动刷新 storage/info。单测以 Hijacker 断连还原真实网络抖动
- **W11 收尾建议**：上传完成后展示文本建议区块，程序不删除任何文件；提示限定本次归档子目录 `full/like/nef/<归档名>/`；like 全部同步成功才提示可删，nef 需收藏已迁移且 like 全部同步，full 提示确认设备保留后再删

## 四、设计决策记录

- NEF 仅存储不处理（不压缩/VLM/Embedding），服务端入库时读 EXIF
- 中转目录嵌套结构：full/like/nef 各建归档子目录 `YYYYMM-活动名`（`-` 分隔符）
- 执行阶段仅复制不删除，NEF 删除交还用户
- 全链路保留原始时间戳，不用拍摄时间覆盖修改时间（Windows「日期」列是 System.ItemDate 智能日期）
- storage/info 扫描 PhotoSrc（与上传落盘同源）
- 上传重试从简：自动仅 1 次固定等待，持续失败交由用户手动重试 + skip 模式
- 收尾不删文件：只给文本建议，限定归档子目录

被否决/调整的方案记录于 [note.md](../note.md) §13（NEF 自动删除 → 仅复制）、§14（术语统一为收藏/留存/废弃 + 报告精简）。
