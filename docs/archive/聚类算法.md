# 聚类算法

## K-Means

假设对二维坐标上的一系列的坐标点做K-Means算法

1. 随机设定2个坐标作为质心。其中2是算法的参数K，可以设置其他值
2. 计算所有点到2个质心之间的距离，距离小则分配给对应质心，得到2组坐标点
3. 2组坐标点，重新计算他们的质心，会得到新的质心坐标
4. 重复步骤2/3多次，直到分组不在改变，或者变化极小，或者到达设定的计算次数上限
5. 输出分组

可以想象到，有些情况合适，并且会非常自然/直觉/简单

- 行政区域划分，村/镇/县/市/省/国，都很适合
- 但是有例外，比如：河北/北京/天津
  - 因为河北环绕了北京天津一圈，K-Means无法通过距离来区分出来

根据以上例子，可以先观察数据的分布情况，又或者直接计算几次，看看效果。
参数K在这里很重要，比如我们分类的就是性别，那K理所当然就是2，如果设置其他值，结果会完全不准确。
但是很多例子中是没办法提前知道可以分成几个类别的，所以也是这个算法的缺点之一。
这个问题也是可以用过测试看效果来确定。

## DBSCAN

我们尝试用传销组织来比喻这个算法

1. 随机选取一个点P[i]开始
2. 在这个点P[i]按设定的半径R画一个圈，比喻成一个人去发展他的下线
3. 如果这个圈包含的其他点的数量小于设定的MinPts（密度阈值），则P[i]是“噪声”，表示他不能很好的被分类
   3.1. 比如说一个几乎不交际的人，他的亲朋戚友都不够MinPts个，那就不指望他还能发展下线了
   3.2. 而MinPts的理解，也可以进一步比喻，MinPts则下线数量，如果1个下线也算的话，那绝大部分情况还是可以继续发展下去的。
4. 如果这个圈包含的其他点的数量大于设定的MinPts（密度阈值），先开一个团队C
   4.1. 把这些点记录到团队C中，再记录为集合N（方便后面计算），这里C是成员，而N是待发展下线的成员名单
   4.2. 遍历N里每一个点P[n]，对P[n]画圈，比喻成每个下线也都要尝试去发展下线
   4.2.1. P[n]的圈里有足够的“密度”，P[n]的圈里的点要加入到C和N中，可以比喻成这些人还要继续发展下线
   4.2.2. P[n]的圈没有足够的“密度”，P[n]的圈里的点要加入到C中，就不用加入N了，因为他们不需要发展下线了
5. 从P[i]开始做完一次算法后，判断整个数据集中有没有还没被遍历到的点，如果有，则用这个点重新做一次，全部数据都被处理过了

这个算法的路径是比较类似深度优先算法的，密度阈值就是类似“是否有子节点”的下钻的判断，
密度不够的时候，我们认为这个分类已经到达了边缘，不用再搜索下去了。

参数在这里很关键，半径R和MinPts都直接关系到结果，
其中半径R可以通过，测算一下距离得到一个突变点，来辅助确定。

- 随机选一个点P[i]，然后计算其他所有点和P[i]的距离，得到D[0]...D[i-1]...D[i+1]...
- 集合D从小到大排序，然后找到突变点，那么半径就选取小于突变点之前的距离
  - 比如去平均或者去小于突变点的最大值，但具体也要根据实际的数据情况
  - 比如最大比值法（Max Ratio Gap）：检测相邻距离的比值，在第一个显著跳跃处截断
  - 最大比值法我们也用在了rag的结果过滤中

于是半径R就可以又程序辅助计算一个基础值，但未必是最佳，因为最佳需要具体分析数据的情况。
密度阈值也许也可以在确定半径R的情况下来计算一个基础值，原理和半径的计算差不多，也是观察突变点。
但是需要昨晚整个聚类运算观察结果，所以对cpu和内存都有不少压力

- 我们可以从小密度开始尝试，设定一些经验值，比如设定一个`step = 数据总量/100`开始
- `step[n] = step * n` 计算得到数据最终被分成了M[n]个簇
- 对比M[n]列表，也能发现突变点，或者说符合理解的数量
  - 比如我希望分类的是照片的明暗程度，符合人类理解的，可能是5个簇[很暗/较暗/常规/较亮/很亮]
  - 一方面，M[n]列表可能是[1,2,4,5,5,5,6,10,20,50...]，那么4/5/6尤其是5的值可能是比较合适的
  - 另一方面，如果聚类是用来给人直接使用的，一般认为3-7个是比较适合展示给用户的
    - 米勒定律（Miller's Law）：人脑短期记忆一般能容纳 7±2 个信息块
    - 但要给脑子再留一些余量，所以使用 5±2 比较舒服
    - 关于这个话题，K-Means显然是更有优势的，因为提前让你设定K值进行分类，但总体而言只能多尝试

这个算法除了聚类，也能去检测“离群点”，把半径设置小一点，容易找到“离群点”，这些点可能是“噪声”
比如在[很暗/较暗/常规/较亮/很亮]分类下，
出现了一个几乎全黑的图片（忘了打开镜头盖？），
或者一个几乎全白的图片（参数错误，完全过曝了）

## HDBSCAN

在聚类算法家族里，HDBSCAN 就是 DBSCAN 的“亲儿子”升级版。它俩的核心思想完全一致（基于密度聚类），但 HDBSCAN 解决了一个在图像向量上最致命的问题：你不需要猜半径（eps）。

DBSCAN（硬骨头）：你必须手动指定两个参数，eps（半径范围）和 min_samples（最小样本数）。它把所有点按一个固定的全球半径（eps）画圈，密度超过阈值就聚成一类。

HDBSCAN（自适应）：它根本不管半径是多少。它把数据构建成一棵“密度树”（层次结构），然后把树“横切一刀”，自动保留那些最稳定的分支作为簇，把不稳定的点直接丢进“噪声（-1）”。你只需要指定一个min_cluster_size（最小簇规模）。

## UMAP

把 UMAP 想象成一个“极简主义的地图绘制师”。你的 Chroma 向量是 1024 维空间里的一个点，人类看不见；UMAP 的任务是把这些点“压扁”到 2 维或 5 维，但**必须守住一条底线：原来离得近的点，压扁后也必须离得近；原来离得远的，压扁后也不能强行贴在一起。**

它的核心原理可以拆解成两步“魔术”：

### 1. 在高维空间里“织一张网”（找邻居）

UMAP 不会去管全局的长距离，它只看每个点周围最近的几个邻居（参数 `n_neighbors`）。

- 它给每个点画一个“势力圈”，圈内是“朋友”（密度高），圈外是“路人”。
- 这一步的逻辑是：**在高维空间中，只要“朋友”关系确定了，距离的绝对值并不重要**（这就完美避开了“维数灾难”）。

### 2. 在低维空间里“拉弹簧”（优化布局）

UMAP 在低维空间随机摆放一些点，然后开始玩“弹簧模型”：

- 如果高维里是“朋友”，低维里却分得很开 → 弹簧会把它们**拉近**。
- 如果高维里是“路人”，低维里却挤在一起 → 弹簧会把它们**推开**（推开的力量有上限，避免所有点混成一团）。

> 参数 `min_dist` 控制低维空间点之间**允许的最小间距**。设为 0，簇内极其紧凑；设大一点，簇间边界清晰。对于照片聚类，建议 `min_dist=0.1~0.3`，保留簇的形状。

UMAP 反复调整低维点的位置，直到整张图里的“朋友关系”和“陌生人关系”与高维空间尽量一致。

### 为什么聚类（HDBSCAN）之前必须先过 UMAP？

这恰恰是你之前困惑的核心——**HDBSCAN 在原始的 1024 维向量上几乎没法用**。

- **维度诅咒**：在 1024 维空间里，所有点之间的欧几里得距离都趋向于“差不多远”。HDBSCAN 这种依赖“谁离谁近”的算法会彻底失灵，根本找不到密度差异。
- **UMAP 的解法**：UMAP 不强求保留大尺度距离，只保留局部的“邻居关系”。经过压缩后，照片的语义结构（猫、狗、风景、夜景）会在低维空间里显出清晰的“团块”，HDBSCAN 这时候再去抓这些团块，就是一抓一个准。

**补充一句**：UMAP 是完全随机的（每次运行结果会有细微差异），但这对照片聚类不是坏事——只要主题类簇大致稳定，局部微调不影响相册分组的可用性。如果追求极端确定性，可以固定 `random_state`。

## 关于聚类的延申

先留档，以后再来展处理

当我们从 **无监督（聚类）** 转向 **有监督**，本质上是思维的转换：

- **无监督（HDBSCAN+UMAP）**：你问 AI **“照片里有哪几类？”**（自动发现未知主题）。
- **有监督（分类/微调）**：你告诉 AI **“把猫片找出来”**，并给了几张猫片作为例子，AI 学会了标准，然后去海量数据里把猫片**捞出来**。

在 Agent 落地中，**纯有监督训练（从头训练模型）几乎用不上**，因为你的照片量（几千张）和算力都不足以微调大模型。真正实用的是 **“有监督的检索/分类”**，核心是以下 3 种实现方式：

---

### 1. 最简单有效的有监督：Centroid（质心分类）——推荐你首试

当用户说“我喜欢这种风格”并勾选了几张照片，你不需要重新训练任何模型，只需在向量空间做“求平均”。

**操作**：
1. 用户标记了 5 张“我喜欢的猫片”，获取它们在 Chroma 中的向量（`v1, v2, v3, v4, v5`）。
2. 计算这些向量的**平均值**（质心）：`centroid = mean([v1...v5])`。
3. 以后用户问“找类似的”，直接用这个 `centroid` 去 Chroma 做 `query_vectors` 检索。

**本质上，你不需要任何“有监督算法包”，这就是最简单的 Few-shot 分类器。** 它不需要 UMAP 降维，直接在原始 Embedding 空间做就行，效果往往出奇地好。

---

### 2. 半自动纠偏：有监督地“拉开”混淆簇（主动学习）

假设 HDBSCAN 把“日落”和“日出”聚成了一团（因为语义太像）。这时你对这两类纠偏，手动告诉系统它们不同。

**技术方案**：计算两个簇的质心 `C1` 和 `C2`，在向量空间中给它们施加一个 **“排斥力”**（数学上称为 Linear Discriminant Analysis 或简单的向量正交化），让后续检索时这两个簇的边界变得更清晰。这种“用户反馈驱动向量修正”已经是准产品级的做法。

---

### 3. 微调 Embedding 模型（重器，慎用）

如果你有上万张照片，且用户反复发现“阴天”和“雾天”总是检索混淆，可以考虑微调 Embedding 模型。

**原理**：使用 `sentence-transformers` 提供的监督对比学习（如 `MultipleNegativesRankingLoss`），构造三元组数据（锚点：猫片，正例：另一张猫片，负例：随机狗片），让模型学习把猫片拉近、狗片推远。

**对你而言，严重不推荐**。Python 代码量大、需要 GPU、可能破坏原有的通用语义能力，且你已有的 Chroma + Centroid 已经能解决 90% 的问题。

---

### 无监督 vs 有监督，在实际 Agent 中的协作模式

两者并不是二选一，而是**流水线式协作**：

1. **离线（无监督）**：HDBSCAN 自动把你几千张图聚成几十个主题（猫、城市、美食等），生成智能相册。
2. **在线（有监督）**：用户点开“猫”相册，觉得漏了 2 张，随手标记一下，系统实时计算质心，把这 2 张补充进去。下一次用户搜“猫”，**质心检索（有监督）** 优先于全局的 HDBSCAN 相册。

**结论**：对你目前的 `photo-agent` 项目，**有监督不需要额外的复杂算法**。你只需要在 Chroma 里存好每个用户标记组的 `centroid` 向量。当用户给相册起名（如“我的猫主子们”）时，系统记住这组向量的均值，下次直接拿这个均值去查，这就是最符合你 Go + Python 架构的有监督实践。
