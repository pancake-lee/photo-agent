# Photo Agent - 产品需求文档

## 1. 产品概述

### 1.1 产品定位

Photo Agent 是一个面向**个人摄影爱好者**的 AI 媒体资产助手。它通过对摄影作品进行 AI 视觉描述、建立时间线与标签知识库、构建向量检索系统，让用户可以用**自然语言**与自己的照片库对话，实现智能检索、摄影档案问答和创作辅助。

> **一句话定义**：让你的摄影照片库"会说话"的 AI Agent。

### 1.2 目标用户

- **摄影爱好者**：积累了大量照片，靠文件夹和文件名难以快速定位特定作品
- **创作者**：想基于历史作品分析风格特点，获取拍摄建议

### 1.3 核心价值主张

| 痛点         | 传统方式                           | Photo Agent 方案                                                 |
| ------------ | ---------------------------------- | ---------------------------------------------------------------- |
| 找照片困难   | 翻文件夹、靠记忆命名               | 自然语言描述即可检索                                             |
| 作品信息分散 | 拍摄时间、地点、主题散落在各文件夹 | 统一照片库，Web UI 管理 + AI 对话问答                            |
| 多维筛选困难 | EXIF 工具逐个查看                  | Text-to-SQL 自然语言转 SQL 过滤（光线/色调/场景/构图/情绪/EXIF） |
| 复合查询困难 | 无法同时按"类型"+"风格"搜          | Combined 查询：SQL 结构化过滤 ∩ RAG 语义检索                    |
| 创作灵感枯竭 | 孤立思考                           | Agent 基于历史作品激发思路                                       |
| 风格认知模糊 | 凭感觉                             | Agent 基于数据分析风格特点                                       |

## 2. 功能需求

### 2.1 功能优先级

```
P0 (MVP 已实现): 智能检索 + 摄影档案问答 + Web 照片管理 + AI 对话
P1 摄影主题分析与创作建议
P2 相似照片聚类（✅）+ 主题标签自动生成（✅）+ 时间线关联分析（待开发）
```

**当前状态**：

- Web 照片管理（上传/浏览/筛选/排序/删除/VLM预处理/Embedding嵌入）— ✅ 完成
- LangGraph Agent 多路由查询（SQL/RAG/Tool/Combined）— ✅ 完成
- Text-to-SQL 结构化过滤（6 个属性维度 + EXIF 参数）— ✅ 完成
- FastAPI 对话 API + 会话管理 — ✅ 完成
- 相似照片聚类 + 主题标签自动生成 — ✅ 完成
- 黄金查询用例 Web 管理 + 评估基线建立 — 进行中（Phase 1.3）

### 2.2 P0 - 智能检索

**用户故事**：

> 作为摄影爱好者，我想输入"2024 年在云南拍的雪山人像"，系统能返回匹配的照片列表和文字说明。

**功能描述**：

- 用户通过 **Web UI（对话界面）** 或 CLI 输入自然语言查询
- Agent（LangGraph）自动分类查询类型并路由：
  - **SQL 分支**：结构化统计（数量/EXIF 参数/时间范围）→ Text-to-SQL → Go 后端执行
  - **RAG 分支**：纯语义检索（场景/主体/氛围/构图）→ ChromaDB 向量检索 → LLM 生成回答
  - **Tool 分支**：需要调用 API 的操作（列出时间线/标签查询）→ Function Calling → Go API
  - **Combined 分支**：同时涉及结构化维度 + 语义内容（如"逆光的雪山照片"）→ SQL ∩ RAG 取交集
- 返回匹配照片列表（缩略图 + AI 描述 + 结构化属性），支持 Markdown 图片渲染
- 支持多轮对话（会话持久化），可在历史会话基础上追问

**验收标准**：

- [X] 输入"海边的日落照片"，返回相关图片
- [X] 输入"2024 年云南旅游的照片"，返回匹配照片，附带时间线信息
- [X] 输入"我有多少张照片？""用 Canon 拍的照片有哪些？""ISO 大于 1600 的照片"等结构化查询
- [X] 输入"逆光的风景照""暖色调的人像""黑白高对比度的照片"等组合查询，结果精准于纯文本搜索
- [X] 支持中文自然语言查询
- [ ] 输入"找每年的生日（3 月 7 号前后）收到的礼物"，返回历年相关照片（需多轮对话支持）

### 2.3 P0 - 摄影档案问答

**用户故事**：

> 我想问”我拍过几次海边日出？都在哪些地方？”，Agent 能基于照片库回答。

**功能描述**：

- 用户通过 Web UI 或 CLI 提问，Agent 自动选择查询策略：
  - 统计类问题（数量/分布）→ Text-to-SQL 查询 Go 后端统计 API
  - 语义类问题（”哪些照片拍过海边”）→ ChromaDB 向量检索
- 照片导入时自动提取 EXIF 信息（相机/镜头/ISO/光圈/GPS 等）
- 照片经 VLM 预处理生成 AI 描述，`ParseStructuredAttributes()` 提取 6 个维度的结构化属性（主体/色调/场景/光线/情绪/构图）
- Agent 可就作品档案回答，展示照片缩略图 + 结构化属性信息

**验收标准**：

- [X] 提问”我拍过多少次雪山”，Agent 正确回答并列出相关照片
- [X] 提问”2024 年我去过哪些地方拍照”，Agent 基于时间线标签回答
- [X] 提问”用 Nikon 拍的照片有哪些””焦段在 24-70mm 之间的照片”等 EXIF 查询
- [X] 提问”蓝调时刻的照片””柔和光线的照片”等结构化属性查询（通过 Text-to-SQL 过滤）
- [ ] 提问”我的人像片和风光片各有什么特点”这类对比问题（需 P1 主题分析）

### 2.4 P1 - 摄影主题分析与创作建议

**用户故事**：

> 我想和 Agent 讨论"今年生日想送什么礼物"，Agent 能基于历年 3 月 7 日前后的照片提供建议。

**功能描述**：

- 用户提出主题或创作方向
- Agent 检索相关历史作品（时间线、主题、风格）
- 基于素材生成分析建议、拍摄方案
- 输出纯文本（不生成图片/视频）

**验收标准**：

- [ ] 输入"分析我 2024 年云南系列的风格特点"，Agent 给出基于实际照片的分析
- [ ] 输入"今年生日送什么礼物好？"，Agent 基于历年 3 月 7 日前后的照片给出建议
- [ ] 建议中引用具体历史作品（如"参考 2024-02-云南/IMG_0234.jpg 中的构图方式"）

### 2.5 P2 - 时间线关联分析

**用户故事**：

> 我想了解"我每年春天都拍了什么主题"，Agent 能做跨时间线的关联分析。

**功能描述**：

- 基于全部素材的描述和时间线标签
- Agent 能回答跨时间线的关联问题
- 如季节性主题、地点重复出现、风格演变等

**验收标准**：

- [ ] 提问"我每年春天都拍什么"，Agent 给出跨年份的主题汇总
- [ ] 提问"我拍海边的照片有什么变化"，Agent 分析不同时期的风格差异

### 2.6 P2 - 个人摄影风格知识库（已降级/可选）

**用户故事**：

> 作为展示用途，Agent 能总结我的摄影风格特点。

**功能描述**：

- 基于全部素材的描述，Agent 能回答宏观问题
- 如风格特点、常用构图、色调偏好、主题分布等

**验收标准**：

- [ ] 提问"我的摄影风格是什么"，Agent 给出基于素材的总结

## 3. 数据需求

### 3.1 数据来源

| 数据类型     | 来源                          | 用途                          | 公开性                  |
| ------------ | ----------------------------- | ----------------------------- | ----------------------- |
| 个人摄影作品 | 用户自己拍摄（约 300 张精选） | 核心素材：检索、问答、分析    | **不上传 GitHub** |
| 真人短片截图 | 无版权真人超短片（辅助展示）  | 展示 VLM 对真人场景的识别能力 | 可公开                  |

> **为什么不使用动漫/影视素材？**
>
> 前期考虑过使用 Blender 开源短片（如《Sintel》）作为展示数据集，但最终决策全部使用真实摄影素材。原因见 [docs/note.md](note.md) 中的"数据集变更记录"。

### 3.2 数据预处理需求

- 系统需支持对原始照片进行批量视觉描述生成（VLM），输出结构化描述数据
- 系统需支持用户以 Markdown 表格形式提供时间线描述，按 EXIF 拍摄时间自动匹配活动标签
- 系统需支持将照片元数据（路径、描述、时间线标签、EXIF 信息等）持久化到本地数据库
- 系统需支持将描述数据同步到向量知识库，用于语义检索
- 所有照片必须先经预处理生成描述，server 导入阶段不再实时调用 VLM，避免重复计费
- 时间线标签完全来自用户提供的时间线文件，不依赖文件夹命名

### 3.3 数据量级预估

- 个人摄影作品：约 200-300 张（精选好片）
- 真人短片截图：约 20-30 张（辅助展示，可选）
- 总素材量：< 500 张，Chroma 完全可承载

### 3.4 关于人物识别的决策

**本项目不做人物身份识别。**

原因：

1. 亲友相貌相似，提高识别准确率需要大量工程投入
2. 这不是展示 AI Agent 能力的核心场景
3. 用户明确表示"不需要识别是谁"

照片中出现的人物将统一以"有人""人物特写""人群"等通用描述处理，不做具体身份区分。

## 4. 非功能需求

### 4.1 性能需求

- 单次查询响应时间：< 5 秒（含 LLM 调用）
- 图片处理（单张视觉描述）：< 10 秒
- 并发：无需考虑，单机单用户使用

### 4.2 可用性需求

- Web UI 交互友好，响应式布局，支持深色主题
- 上传支持拖拽，冲突检测提供对比预览
- 对话界面支持 Markdown 渲染（含图片），AI 回复标注查询类型
- CLI 保留作为开发/演示入口
- 错误信息清晰，引导用户修复
- VLM 预处理和 Embedding 嵌入支持断点续传（队列中断后可恢复）

### 4.3 可扩展性需求

- 模型可切换：支持 GPT-4o / Qwen-VL / Kimi 等
- 向量库可替换：Chroma 接口抽象，后续可换 Milvus
- 存储可扩展：本地文件 → MinIO / OSS（预留接口）

### 4.4 安全需求

- API Key 不硬编码，通过环境变量配置
- 个人照片不上传 GitHub，通过 `.gitignore` 保护

## 5. 交互设计

### 5.1 Web 前端（主要交互方式）

- **照片管理页**（`#/photos`）：网格展示照片缩略图，支持按时间线/日期范围/文件名筛选，按拍摄时间/文件名/导入时间排序，点击查看 EXIF 详情和 AI 描述，单张/批量删除
- **AI 对话页**（`#/chat`）：会话式聊天界面，支持 Markdown 渲染（含图片），显示查询路由类型（SQL/RAG/Tool/Combined），照片引用可点击预览，每条 AI 回复可一键保存为黄金查询用例
- **黄金用例管理页**（`#/golden-queries`）：列表展示所有黄金查询用例（查询文本/关联照片/分类/时间），支持查看详情、删除操作
- **上传**：拖拽/点击上传，前端提取 EXIF 拍摄时间，Go 后端 ImageMagick 压缩，冲突检测（覆盖/跳过/保留两份）
- **队列管理**：VLM 预处理和 Embedding 嵌入均支持批量队列，前端轮询显示进度

### 5.2 CLI（开发/演示）

- `python chain/photo_agent.py -c config.yaml` 进入交互式对话
- `--serve PORT` 启动 FastAPI 对话 API 服务
- `--demo` 运行全链路场景演示
- `--eval` 运行 RAG 检索评估

### 5.3 Dify（可选验证路径，已归档）

- Dify 本地 Docker 部署曾用于早期快速验证 Agent 可行性，现已不作为核心方案
- 配置和操作见 [dify/USAGE.md](../dify/USAGE.md)

## 6. 风险与假设

### 6.1 风险

| 风险               | 影响                | 应对措施                                                                |
| ------------------ | ------------------- | ----------------------------------------------------------------------- |
| VLM 描述不准确     | 检索效果差          | 结构化属性提取作为补充维度，Combined 查询 SQL∩RAG 提高精度             |
| API 费用过高       | 开发成本超支        | 使用 GPT-4o-mini / 火山引擎 Doubao 等低价模型，控制调用频率             |
| 向量检索召回率低   | 用户体验差          | Combined 查询（结构化过滤 ∩ 语义检索）提升精度，断层过滤去除低相关结果 |
| 属性值中英文不匹配 | SQL 过滤返回 0 结果 | 动态获取 DB 实际值拼入 Prompt，LLM 仅使用数据库中存在的值               |

### 6.2 假设

- 用户能提供图片存储根目录路径
- 用户能编写 Markdown 格式的时间线描述文件
- 云端 API 在国内可稳定访问（或用户有代理）
- 单张图片大小 < 5MB（VLM API 限制）
