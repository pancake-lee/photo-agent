# 文档审阅规范

> 定期执行文档治理，确保各文档各司其职、不冗余、不越界、与代码实现一致。
> 用户按需触发，每次自行判断采用第一版或第二版。

---

## 触发条件

- 新增一轮开发后（如某个 Phase 完成后）
- 技术栈或架构发生重大变更后
- 项目收尾阶段作为文档质量检查
- 用户主动要求"审阅文档"

---

## 第一版：纯粹文档整理（不读源码）

**目标**：仅通过文档间交叉比对，找出 5 类问题：

1. **职责越界**：文档包含超出其职责范围的内容
2. **内容冗余**：非 README/CLAUDE 文档重复描述其他文档已详述的内容
3. **引用失效**：文档间引用指向不存在的文件或锚点
4. **信息冲突**：同一事实在不同文档中描述矛盾
5. **过时残留**：已变更的决策或架构仍在文档中作为当前状态描述

**审阅顺序**：CLAUDE.md → README.md → PRD → TECH → TASK → note → backlog → USAGE
（先审高层，低层服从高层约束）

**审阅后输出**：

- 按类型和严重程度排序的问题清单
- 每个问题给出 `[位置]` `[问题]` `[证据]` `[建议]`
- 标记哪些问题"仅第一版可解决"，哪些"需要第二版源码验证"

---

## 第二版：源码对齐（基于文档声明读源码）

**目标**：基于第一版的问题清单，从文档声明出发**针对性**阅读源码，找出"文档这么说，但代码实际那样"的差异。

**核心原则**：不从源码出发推导文档问题，而是从文档声明出发验证源码。避免全量读源码。

**审阅维度**：

- D1 架构描述 vs 实际代码（模块划分、目录结构）
- D2 API 契约 vs 实际路由（路径、参数、响应结构）
- D3 数据模型 vs 实际结构（字段、类型、可空性）
- D4 功能实现 vs 需求覆盖（P0/P1/P2 是否都有对应代码）
- D5 配置与部署（命令、路径、默认值是否一致）

**差异分级**：

- **L1 严重**：文档描述的架构/功能根本不存在，或代码与文档承诺矛盾
- **L2 中等**：文档有但未更新（API 新增参数、字段类型变更）
- **L3 轻微**：文档遗漏了已实现的小功能

**审阅后输出**：

- 按 L1/L2/L3 分级的差异清单
- 每项给出 `[文档声明]` `[源码实际]` `[差异描述]` `[建议方案]`
- **L1 必须提交用户裁决**（改文档还是改代码？）
- L2/L3 可给出推荐方案，用户选择性裁决或授权直接修改
