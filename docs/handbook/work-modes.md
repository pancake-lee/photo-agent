# 工作模式手册

> AI 根据用户输入的关键词自动切换工作模式。
> 本文件定义每种模式的完整流程，是 CLAUDE.md 触发词表的下游详情文档。

---

## 路由规则

用户输入反馈后，先判断问题类型，再决定路由：

```
用户输入反馈
      │
      ▼
┌─ 问题类型判断 ─────────────────────────────┐
│                                            │
│  缺陷（功能不符合预期）                       │
│    → 生成器直接修复                          │
│    → 不涉及方案变更                          │
│                                            │
│  效果问题（功能能跑但输出不够好）               │
│    → 规划器分析是否需要调整方案                │
│    → 如果是参数/阈值问题 → 生成器直接调        │
│    → 如果是方案层面问题 → 规划器改方案 → 生成器 │
│                                            │
│  体验问题（交互流程不顺畅）                     │
│    → 规划器调整 UI/交互方案 → 生成器          │
│                                            │
│  需求变更（用户改变了对功能的期望）              │
│    → 更新 backlog → 规划器 → 生成器           │
│                                            │
└────────────────────────────────────────────┘
```

---

## 评估模式

**触发词**：`评估` / `我发现问题` / `这里不够好` / `效果不对` / `有个 bug`

**流程**：

1. 读 `docs/backlog.md` 了解当前需求池和评估状态（反馈条目也是 backlog 条目）
2. 把问题结构化记录为 `docs/backlog.md` 中的新条目（使用统一字段格式：状态 / 背景 / 方案 / 分析 / 验收）
3. 读取相关设计文档（`docs/design/`）和代码，对比设计意图与实际行为，分析根因
4. 判断问题类型并给出路由建议：
   - **缺陷**（功能不符合预期）→ 进入生成模式直接修复
   - **效果问题**（功能能跑但输出不够好）→ 分析是否需调整方案，是则先进入规划模式，否则进入生成模式
   - **体验问题**（交互流程不顺畅）→ 先进入规划模式调整方案，再进入生成模式
   - **需求变更**（用户改变了对功能的期望）→ 先更新 `docs/backlog.md`，再进入规划模式
5. 给出分析结论和建议方案，等用户确认后执行
6. 修复完成后自检验证，更新 backlog 条目状态为「Done」

## 规划模式

**触发词**：`规划一下` / `帮我设计` / `出个方案` / `怎么做`

**流程**：

1. 确认规划对象：用户口述的新需求、或 `docs/backlog.md` 中指定条目
2. 读 `docs/backlog.md` + `docs/prd.md` + `docs/tech.md` + `docs/note.md` 获取上下文
3. 需求分析：检查依赖项是否满足、判断复杂度（简单/中等/复杂）
4. 产出方案到 `docs/design/`，包含：问题/需求描述、方案设计、关键决策及理由、大致方向。design 文档只记录决策和方向层面的内容，不写具体技术细节
5. 简单任务：方案中直接包含实现步骤；复杂任务：方案中明确子阶段拆分（每个子阶段含目标、涉及模块、验收标准），如拆分复杂则建独立 exec plan
6. 更新 `docs/backlog.md` 中对应条目的状态为「已规划」，填入「方案」字段

**方案改动确认规则**：

- 方案改动较大：先在对话中简短描述改动点，确认后修改文档，再确认后进行代码修改
- 方案改动不大：无需对话先确认，直接修改文档，然后让用户确认后再改代码
- 用户主动说"全自动修改"等意思：无需确认，直接完成所有修改

## 生成模式

**触发词**：`按方案执行` / `开始开发` / `实现这个`

**流程**：

1. 确认执行对象：指定方案文档、或 `docs/backlog.md` 中状态为「已规划」的条目
2. 读方案文档 + `docs/tech.md` + `docs/handbook/coding-conventions.md`
3. 按方案中的实现步骤逐步执行，每步完成后编译 + 测试自检
4. 全部实现完成后，检查 tech.md 中是否存在已落地为代码的技术细节（结构体定义、schema、API 路由表、代码示例等），如有则删除，避免文档与代码重复维护
5. **文档同步（必须逐项完成，不可跳过）**：
   - [ ] 更新 `docs/backlog.md` **任务总览表格**中对应行的状态
   - [ ] 更新 `docs/backlog.md` **任务详情区**中对应条目的状态字段
   - [ ] 在方案文档（`docs/design/`）的实现步骤中勾选已完成项（✅）
   - [ ] 如方案文档含验收清单，代码侧已覆盖的项可勾选，运行时验证项留待用户部署后确认

## 项目管理模式

**触发词**：`版本归档` / `归档` / `里程碑` / `版本规划` / `迭代计划`

**流程**：

1. 确认任务类型：版本归档、里程碑规划、还是 backlog 治理
2. 读 `docs/backlog.md` + `docs/archive/` 了解当前版本状态
3. 按任务类型执行：
   - **版本归档**：识别 Done 条目 → 创建 `docs/archive/vX.Y.Z-completed-backlog.md` → 精简 backlog 至仅剩未完成条目 → 更新决策历史
   - **里程碑规划**：梳理剩余 backlog → 评估优先级和依赖关系 → 排定下一版本范围建议 → 更新 backlog 状态
   - **backlog 治理**：交叉比对 backlog.md 和实际代码 → 识别过时/遗漏条目 → 给出清理建议
4. 给出执行结果和变更摘要，等用户确认

## 角色间 Handoff：Plan → Generate

规划完成后到执行之间，通过 backlog 条目完成交接：

1. **规划产出**：Planner 将方案写入 backlog 对应条目的「方案」字段，状态更新为「已规划」。条目使用统一结构（状态 / 背景 / 方案 / 分析 / 验收），确保 `/clear` 后新会话中的 AI 能完整理解任务上下文
2. **启动执行**：用户在**新对话**中让 AI 读取「已规划」条目，进入生成模式执行
3. **交接内容**：backlog 条目本身即为交接协议，结构化字段使 AI 无需依赖对话历史即可理解要做什么、怎么做

当前由用户手动串这个流程（结束规划对话 → 开新对话 → 指向 backlog 条目执行）。后续工作流自动化后，状态流转自然触发角色切换。

## design 与 tech.md 的职责分离

- `docs/design/`：方案设计、决策、方向。只写"做什么、为什么这样做"，不写"具体怎么落地"
- `docs/tech.md`：规划阶段可临时存放技术细节（数据结构定义、API 路由表、配置格式、代码示例等），作为生成器实现时的参照
- **代码落地后，tech.md 中的临时细节必须删除**：结构体定义、数据库 schema、API 路由、代码示例等一旦写入代码文件，就应从 tech.md 移除
- 简单方案跳过 tech.md：方案本身不复杂时，design 文档已足够驱动生成器直接写代码

## 文档设计原则

- **设计文档只描述当前方案，否决记录与迭代痕迹分离处理**
  - 设计迭代中的中间产物不留痕迹：方案尚未定型期间的临时文件、中间方案、讨论性内容，被更优方案替代后直接覆盖更新
  - 经审议明确否决的方向，记录到 `docs/note.md`：当某一方案或需求方向经过讨论后被明确判定为"不采纳"且该判定对后续工作具有约束力，应将否决结论及理由记录到 `docs/note.md`
  - 设计文档（`docs/design/`）始终描述当前生效的方案，不包含"曾考虑 X 但未采用"或"不需要 Y"等否定性叙述

- **已完成的功能从 TODO 删掉**，功能适当写到其他文档合适的地方。不要在 TODO 中描述已实现的功能
