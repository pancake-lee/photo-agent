# 设计记录写法

本文规定 `docs/design-docs/` 中概要设计与详细设计的写法。

开头标识按[规划类型](../top/mode-planning.md#规划类型)填写，设计范围注明本次涉及的产品功能、UI 交互或技术方案。

1. Epic 使用 `epic-<编号>-<主题>.md` 记录概要设计；Feature 使用 `feature-<编号>-<主题>.md` 记录详细设计。Task 与 Bug 的实施说明留在 backlog。
2. 草案标为“待审批”，确认后标为“已确认”。设计变化时更新当前方案，保留解释选择所需的备选理由；详细设计引用概要约束，不重复完整论证。
3. 需要审批且细节较多时，开头集中呈现目标、主流程、影响判断的约束和待审批事项，让审批者读完核心部分即可作出判断。实现细节、示例和验收证据放在后半部分，注明按需查阅。影响审批的失败后果或边界留在核心部分。
4. 多步或有分支的交互、数据流和状态变化，适合用 Mermaid 表达时用图呈现路径。用分级标题和缩进列表补充图中难以表达的规则与取舍，合并重复描述。

## 概要设计

面向 Epic，确定整体框架和各 Feature 应遵守的约束。

```markdown
# <Epic 编号> <主题>概要设计
状态：<待审批或已确认>
规划类型：<资料驱动规划或简述需求规划>
需求来源：<reference 链接，或“用户对话”，结论见正文或关联规格>
本次设计范围：<本次新增或调整的内容>

## 目标与范围
<整体需求、范围外事项及规格入口>

## 框架与核心约束
<模块关系、依赖方向及必须保持的契约>

## 方向性决策
<关键选型、备选方案、理由与接受的代价>

## Feature 划分与整体验证
<职责划分、设计入口及组合后如何证明目标达成>
```

## 详细设计

面向 Feature，确定可落地的方案；Feature 可直接建立，无需先有 Epic。

```markdown
# <Feature 编号> <主题>详细设计
状态：<待审批或已确认>
规划类型：<资料驱动规划或简述需求规划>
需求来源：<reference 链接，或“用户对话”，结论见正文或关联规格>
本次设计范围：<本次新增或调整的内容>

## 目标与依据
<本特性目标、规格及关联概要设计的入口>

## 具体方案
<关键流程、模块协作、必要接口与数据约定、失败处理>

## 取舍与影响
<备选方案、选择理由、资源或兼容性影响>

## 验证依据
<核心行为的验收条件、验证方式及实施条目入口>
```

## 文档设计原则

- **设计文档只描述当前方案，否决记录与迭代痕迹分离处理**
  - 设计迭代中的中间产物不留痕迹：方案尚未定型期间的临时文件、中间方案、讨论性内容，被更优方案替代后直接覆盖更新
  - 经审议明确否决的方向，记录到任务关联的决策记录：当某一方案或需求方向经过讨论后被明确判定为"不采纳"且该判定对后续工作具有约束力，应将否决结论及理由记录到任务关联的决策记录
  - 设计文档（`docs/design-docs/`）始终描述当前生效的方案，不包含"曾考虑 X 但未采用"或"不需要 Y"等否定性叙述

- **已完成的功能从 TODO 删掉**，功能适当写到其他文档合适的地方。不要在 TODO 中描述已实现的功能


- **设计文档只描述当前方案**：设计迭代中的中间产物不留痕迹
- **否决方向记录到任务关联的决策记录**：经审议明确否决的方向，记录拒绝理由，避免未来重复提出
- **设计文档不写否定性叙述**：不包含"曾考虑 X 但未采用"或"不需要 Y"
