# 设计记录写法

本文规定 `docs/design-docs/` 中概要设计与详细设计的写法。

开头标识按[规划类型](../top/mode-planning.md#规划类型)填写，设计范围注明本次涉及的产品功能、UI 交互或技术方案。

1. Epic 输出概要设计，Feature 输出详细设计。持续新增的专题设计按全局日期前缀命名，如 `YYYY-MM-DD-<主题>-design.md`。类型与编号写在标题，已有任务编号可沿用到文件名。Task 与 Bug 的实施说明留在 backlog。
2. 草案标为“待审批”，确认后标为“已确认”。设计变化时更新当前方案，保留解释选择所需的备选理由；详细设计引用概要约束，不重复完整论证。

## 审批稿结构

需要审批且细节较多时，先写核心方案，再写按需查阅的补充说明。核心方案集中呈现目标与范围、主流程、影响判断的边界与取舍，以及需要用户决定的事项。实现细节、示例、验证方式与证据随补充说明组织。短设计按内容自然分节。

多步或有分支的交互、数据流和状态变化，适合图示时用 Mermaid 呈现路径。正文用短条目写图中未表达的条件、失败后果和取舍，每条表达一个主要判断。以分级标题和缩进列表组织并列信息。

```markdown
## 核心方案 · 审批读到这里
<目标、范围与主流程。适合图示时放流程图，用短条目补充关键约束和取舍>

### 本次审批项
<需要确认或选择的事项，以及会改变决定的条件或后果>

## 补充说明 · 按需查阅
<按职责组织契约、失败处理、示例与验证依据>
```

## 交付前自查

1. 对分区审批稿，只读核心方案，核对能否判断设计目标、主流程、关键失败后果和待确认项。凡是会改变审批结论的信息，放在核心方案。
2. 对照图、正文和关联规格，删去重复描述。正文直接写方案、条件和理由，合并同义说明，删去口语化过渡和工作过程叙述。独立事项分条，重复的验收条件引用规格。

## 概要设计

面向 Epic，确定整体框架和各 Feature 应遵守的约束。以下是内容要点，审批稿按[审批稿结构](#审批稿结构)组织。

```markdown
# <Epic 编号> <主题>概要设计
状态：<待审批或已确认>
规划类型：<资料驱动规划或简述需求规划>
需求来源：<reference 链接，或“用户对话”，结论见正文或关联规格>
本次设计范围：<本次新增或调整的内容>

## 目标与范围
<整体需求、范围外事项及规格入口>

## 框架与核心约束
<模块关系、依赖方向及必须保持的契约>

## 方向性决策
<关键选型、备选方案、理由与接受的代价>

## Feature 划分与整体验证
<职责划分、设计入口及组合后如何证明目标达成>
```

## 详细设计

面向 Feature，确定可落地的方案。Feature 可独立建立。以下是内容要点，审批稿按[审批稿结构](#审批稿结构)组织。

```markdown
# <Feature 编号> <主题>详细设计
状态：<待审批或已确认>
规划类型：<资料驱动规划或简述需求规划>
需求来源：<reference 链接，或“用户对话”，结论见正文或关联规格>
本次设计范围：<本次新增或调整的内容>

## 目标与依据
<本特性目标、规格及关联概要设计的入口>

## 具体方案
<关键流程、模块协作、必要接口与数据约定、失败处理>

## 取舍与影响
<备选方案、选择理由、资源或兼容性影响>

## 验证依据
<核心行为的验收条件、验证方式及实施条目入口>
```

## 文档设计原则

- 设计文档维护当前方案及其成立依据。设计演进时直接更新正文，已完成事项从待办移出。
- 经审议否决且对后续工作有约束力的方向及理由，写入任务关联的决策记录。
