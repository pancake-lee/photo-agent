# 设计记录写法

本文规定 `docs/design-docs/` 中概要设计与详细设计的写法。

开头标识按[规划类型](../top/mode-planning.md#规划类型)填写，设计范围注明本次涉及的产品功能、UI 交互或技术方案。

1. Epic 输出概要设计，Feature 输出详细设计。持续新增的专题设计按全局日期前缀命名，如 `YYYY-MM-DD-<主题>-design.md`。类型与编号写在标题，已有任务编号可沿用到文件名。Task 与 Bug 的实施说明留在 backlog。
2. 草案标为“待审批”，确认后标为“已确认”。设计变化时更新当前方案，保留解释选择所需的备选理由；详细设计引用概要约束，不重复完整论证。

## 审批稿结构

按[文档治理规范](../DOCUMENTATION.md#信息分层与维护)组织信息。细节较多的审批稿先给核心方案，集中呈现目标与范围、主流程、影响决定的边界和取舍，以及需要用户确认的事项。把详细契约、示例和验证依据放在补充说明或链接到已有资料。短设计按内容自然分节。

多步或有分支的交互、数据流和状态变化适合图示时，用 Mermaid 展示路径。正文用短条目补充会影响判断的条件、失败后果和取舍。

```markdown
## 核心方案 · 审批读到这里
<目标、范围、主流程和影响审批的约束及取舍>

### 本次审批项
<需要用户确认或选择的事项，以及影响决定的条件或后果>

## 补充说明 · 按需查阅
<详细契约、失败处理、示例与验证依据>
```

## 交付前自查

1. 对分层审批稿，只读核心方案，确认读者能判断目标、主流程、关键失败后果和待确认项。会改变审批结论的信息放在核心方案。
2. 对照图、正文和关联规格，合并重复说明，引用已有验收条件。保留判断方案所需的条件和理由。

## 概要设计

面向 Epic，确定整体框架和各 Feature 应遵守的约束。以下列出内容要点，细节较多的审批稿按[审批稿结构](#审批稿结构)组织。

```markdown
# <Epic 编号> <主题>概要设计
状态：<待审批或已确认>
规划类型：<资料驱动规划或简述需求规划>
需求来源：<reference 链接，或“用户对话”，结论见正文或关联规格>
本次设计范围：<本次新增或调整的内容>

## 目标与范围
<整体需求、范围外事项及规格入口>

## 框架与核心约束
<模块关系、依赖方向及必须保持的契约>

## 方向性决策
<关键选型、备选方案、理由与接受的代价>

## Feature 划分与整体验证
<职责划分、设计入口及组合后如何证明目标达成>
```

## 详细设计

面向 Feature，确定可落地的方案。Feature 可独立建立。以下列出内容要点，细节较多的审批稿按[审批稿结构](#审批稿结构)组织。

```markdown
# <Feature 编号> <主题>详细设计
状态：<待审批或已确认>
规划类型：<资料驱动规划或简述需求规划>
需求来源：<reference 链接，或“用户对话”，结论见正文或关联规格>
本次设计范围：<本次新增或调整的内容>

## 目标与依据
<本特性目标、规格及关联概要设计的入口>

## 具体方案
<关键流程、模块协作、必要接口与数据约定、失败处理>

## 取舍与影响
<备选方案、选择理由、资源或兼容性影响>

## 验证依据
<核心行为的验收条件、验证方式及实施条目入口>
```

## 文档设计原则

- 设计文档维护当前方案及其成立依据。影响协作或验收的接口、数据与配置约定随设计保存，已有详细定义时链接对应来源。
- 对后续工作有约束力的否决结论及理由，写入任务关联的决策记录。实施步骤与完成状态按[任务组织规则](../PLANS.md)维护。
