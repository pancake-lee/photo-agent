# 通用代码规范

修改代码时读取本文，再按语言读取专项规范；项目现有格式化、检查配置和接口契约作为具体依据。

1. 保持局部可读：命名表达职责与含义，函数围绕明确目标组织。只整理本次涉及的内容，扩大改动范围前说明必要性。
2. 保持层次一致：同层接口与参数使用可比较的抽象粒度。复杂参数先组织为有意义的对象，简单标量不为形式统一额外封装。
3. 处理真实失败：错误在有能力决定处理方式的位置处理；保留排障所需上下文。不要用吞错、默认成功或宽泛捕获隐藏程序缺陷。
4. 解释关键理由：注释记录代码难以表达的约束、算法依据与取舍；公开接口说明必要的输入、输出和失败含义。
5. 维护有效测试：围绕可观察行为断言；检查实现错误时测试是否会失败。复用真实契约与已有测试工具，隔离外部依赖，清理本次测试资源。

测试选择与回归成本由[生成模式完成门](../top/mode-generation.md#完成门)决定，本文不额外增加每次修改的检查项。

## 通用细则

- **不要滥用 try catch** 处理代码问题，要真正解决代码错误的根源

- **代码提交信息**：产出代码后给简短中文 commit 信息，一行/一句话，符合 commitlint 规范

> 按语言/模块分节。AI 在对应目录下工作时读取相关节。
>
> 每种语言独立一节。当某一语言的篇幅超过 200 行时，将其迁出为同目录下的独立文档（如 `golang.md`），本节只保留指向该文档的引用。

---


### 同级同构（宽泛指引）

- 同一层级的并列事物（参数、目录项、方法、同级标题）在抽象层级、复杂度、命名粒度上保持可比，不混搭；跨层级的事物用命名或结构分层隔开
- 只对齐当前写/改的局部，不主动重构存量；发现新的混搭场景时沉淀为新的锚点小节

### 调用参数同级同构

- 传给同一个调用的参数，构造层级保持一致：多键 dict / struct 这类重参数先提取命名再传入，调用行只放骨架（如 `invoke(initial, runtime_config)`），不混搭"一个有名、一个匿名临时字面量"
- 标量与自明的单键小字面量不受此限，不必为它们立名
