# 文档写法与审阅

编写各类文档时读取本文，内容组织遵循全局的“金字塔原理与工作组织”原则。Harness 规则同时遵循[审批规则](../top/RULES.md)。

文档治理的完整检查流程见 [文档审阅](doc-review.md)，个人文档类型的已有写法见 [文档类型与写法](document-types.md)，分别按对应条件读取。

## 编写

1. 按读者需要理解、判断或执行的内容组织文档。开头说明用途、结论与需要读者处理的事项，再按使用顺序展开。由 Agent 自行完成的细节简述处理安排，需追溯时提供对应记录入口。需求写行为，设计写方案与理由，任务写执行与进度，事实在所属文档维护。
2. 使用短句、明确主体与稳定术语；同类标题和条目保持可比较的粒度。保留必要条件，避免长串修饰和空泛总结。
3. 加粗与表格从简；表格只承载短字段对照，长说明用标题和列表。简短标识放在文案开头，长标识独立成行。
4. 链接注明读取用途或触发条件；受众按审批规则标记。命令给出工作目录与必要前提，示例明确区分占位符和可执行值。
5. 当前文档保持当前结论，保留解释决策所需的理由。历史记录按[记录规范](record.md)维护，已归档快照保持不变。

## 审阅

先只读相关文档，检查职责、重复、冲突、引用和现行状态。再针对影响结论的声明读取代码或运行证据，不为审阅文档遍历全部源码。

每项问题记录位置、原文、具体影响与建议替换；区分事实错误、必要限定和合理省略。代码与文档不一致时，先确认预期行为，再决定修正对象。

## 输出约定

- **减少 Markdown 表格**：优先用列表（`-`）组织内容。仅当表格每行内容可控制在 80 字符以内时才用表格（如 `docs/backlog.md` 的任务总览表）。宽表格在编辑器中阅读体验差

- **Mermaid 流程图方向**：默认 `flowchart TD`（向下）。当图中某一级存在超过 6 个平级节点时改用 `flowchart LR`（向右），让同级节点纵向排列获得更宽展示空间

#### Markdown 输出

- **减少**使用表格，**优先**使用标题层级（`##` / `###`）+ 无序列表（`-`）+ 缩进组织内容
  - 长文本内容会把表格撑得很宽，阅读体验差
  - 仅在数据对比（如配置参数对照）等真正适合表格的场景使用表格

#### 文本类文件输出

- 尽量不使用破折号 `--` 或 `——` 来展开，大部分情况下都可以改成 `,` 或 `，`
- 写文章时，避免"下定义"口吻，保持平和的个人叙述：
  - 去掉绝对化措辞：本质上、其实很简单、极其、没有任何、就是
  - 加上个人限定：我觉得、我理解、我目前的看法是、试着
  - 比喻用于辅助理解，不要写成"这就是真理"的句式
  - 结论写成阶段性认识，而非终极答案
