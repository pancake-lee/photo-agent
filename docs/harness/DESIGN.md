# 软件设计原则

设计以已确认的需求、验收条件和项目约束为依据。

1. 融入现有结构：先确认模块职责、依赖方向和已有能力，再决定修改位置；必要接口契约保持明确。
2. 解决实际问题：优先定位根因，复用已有机制。抽象依据真实的重复需求和变化原因，不为假设中的扩展增加层次。
3. 说明关键取舍：比较方案对用户行为、正确性、维护成本和验证成本的影响，说明选择理由及接受的代价。
4. 保持职责清楚：同层模块使用可比较的职责粒度；将业务决策与传输、存储等外部机制分开，沿用项目已确认的分层方式。
5. 让结果可验证：明确关键状态、输入输出和失败含义；外部依赖应能用受控环境或替身验证。替身保留待验证的契约，不绕过真实入口或替代被测逻辑。

长期方案按[设计记录写法](styles/design-doc.md)保存；稳定的现行结构更新到项目 `docs/ARCHITECTURE.md`。涉及产品、UI、安全或可靠性的判断，分别按对应专项原则执行。

## 根因处理

- **根因优先**：本项目体量较小，遇到问题优先找根因并直接修复，而不是叠加容错/降级逻辑。典型反例：配置缺失时应直接指引用户补配置，而非加"配置不可用时的容错分支"
