# 任务组织与版本归档

本文规定 `docs/backlog.md` 的组织、更新与版本归档。需求与设计资料的分工见[规划模式](top/mode-planning.md#选择文档)。

## 任务总览与条目

`docs/backlog.md` 汇总当前版本工作：

- Epic：需要多阶段、多轮、多项工作承载的整体需求，概要设计确定框架、方向性决策和核心约束，关联多个 Feature。
- Feature：有明确目标、范围和验收条件的特性，详细设计确定可落地方案，关联实施条目；无需独立概要设计的需求可直接建立 Feature。
- Task：可独立执行和验收的实施项，记录操作、状态和验证结果。
- Bug：已证实的实际行为与预期不符，记录缺陷及修复验证。

Task 与 Bug 是同级 backlog 条目，均使用稳定编号；可归属 Feature，也可独立存在。总览字段为：状态、Epic、Feature、类型、编号、标题、入口；类型填写 `Task` 或 `Bug`，Epic 与 Feature 字段记录归属。

每项条目使用以下结构；共享背景引用产品规格、Feature 详细设计或 Epic 概要设计，实际检查结果在执行后填写：

```markdown
### <编号> <标题>

- 背景与目标：<解决什么问题，完成后有什么可观察变化>
- 范围：<涉及模块、约束和不做的内容>
- 方案：<实现方向与关键取舍>
- 验收条件：<输入或操作 → 预期结果>
- 验证记录：<实际命令、结果、证据与未验证项>
```

Bug 在“背景与目标”中写清预期、实际表现、复现条件与证据，在验收条件中明确如何确认缺陷已修复。

## 分组与执行顺序

Epic、Feature 的设计文档记录目标、职责划分与取舍，backlog 的归属字段关联实施条目。通过条目编号表达依赖和执行顺序，进度由条目状态反映。

具体操作、命令、预期结果和阻塞原因写在对应条目中；命令注明工作目录，需要用户操作的内容以“（用户）”开头。

### 反馈的任务归属

收到需要落实的反馈时，先定位相关 Feature 和实施条目，再根据验收范围和关单条件确定 backlog 落点。

1. 反馈补充或修正已有 Task/Bug 的验收条件，仍与原结果一并验收和关单时，在原条目追加细项，沿用任务编号。
2. 反馈属于同一 Feature，形成可单独验收和关单的结果时，新增同组 Task/Bug，在总览中单列编号和状态，按需记录依赖。
3. 反馈有独立于现有 Feature 验收范围的目标，可按自身验收条件排期和关单时，另立任务，记录相关依赖或来源。所需规格和设计按[文档选择规则](top/mode-planning.md#选择文档)判断。

同一 Feature 内的细项和新增条目共用该 Feature 的产品规格和设计文档。实施条目引用相关章节。产品行为、接口契约或长期约束发生变化时，更新对应的规格或设计。

## 按需补充与持续更新

出现关键发现时，在对应条目中记录现象及证据；方案变更时，记录决定、理由和日期。
依赖或顺序变化时更新 backlog；影响所属 Epic 或 Feature 的目标和约束时，按[设计记录写法](styles/design-doc.md)更新对应设计。

Task 可升级或聚合为 Feature，Feature 可升级或聚合为 Epic。升级与聚合时保留原编号、来源关联和验证记录，写清新增范围及形成时间；已完成的工作可作为整体能力的事实依据。

涉及风险操作时，在对应条目补充重试或恢复方式；存在明显未知点时，增加原型验证条目及采用条件。必要接口契约写入关联规格或设计，实施条目引用它们。

暂停、交接或阶段完成时更新条目。收尾记录目标达成情况、剩余事项与经验；无实际内容时不保留空章节。

## 状态与验证记录

Task 与 Bug 的状态统一写在 backlog 总览，Epic/Feature 通过关联条目查看进度。状态按“待规划 → 规划中 → 已规划 → WIP → Done”流转；“待用户验收”和“暂缓”的条件分别按[生成模式](top/mode-generation.md#任务状态)及用户决定处理。

规划阶段写验收条件和预期结果。生成阶段写实际检查证据。进入评估阶段时追加评估结论，并区分自评与独立评估。验证要求见[生成模式完成门](top/mode-generation.md#完成门)和[轻量反馈](top/mode-generation.md#轻量反馈)，评估格式见[评估模式](top/mode-evaluation.md#输出与交接)。

推迟的回归记录范围、理由和执行时点。用户确认暂缓的技术债保留为 backlog 条目，记录来源、影响、优先级和重启条件。

## 完成与归档

按全局的“任务完成标准”维护当前清单，需求与计划变化时同步更新条目和验收条件，收尾时据当前清单判断完成。

条目按生成模式的关单条件完成。版本收尾时核对推迟的回归及剩余问题，将本版本已完成条目及验证记录归入 `docs/version/v<版本号>.md`，附 Epic/Feature 的结果摘要与规格、设计入口。

backlog 移除已归档条目，保留未完成、暂缓条目和版本入口。规格、设计与参考资料继续在各自位置维护；版本记录作为历史快照保存，后续变化写入新的活动条目。

## 任务载体约定

- **规划任务落点**：方案、子任务和实施步骤必须写入 `docs/backlog.md` 对应条目，作为 Plan → Generate 的唯一交接载体；不创建独立任务计划文档或 exec plan

- **轻量方案载体**：少于 100 行的设计直接写入 `docs/backlog.md` 对应条目的「方案」字段，不创建独立设计文档；仅需长期保留且超过该规模的设计才写入 `docs/design-docs/`

- **专题中枢文档**：当一个需求及其衍生需求跨越了多个提交、多次修改、多个文档记录时，应编写一份中枢文档（`docs/design-docs/YYYY-MM-DD-<序号>-<topic>-hub.md`）集中串联所有关联产物。中枢文档包含：关联文档索引（设计/评估/backlog/提交）、完整时间线、各项完成度、下一轮建议。所有被关联的文档应在顶部反向链接到中枢文档，形成有顺序的链条。每次经过一轮评估/规划/生成后更新中枢文档

## 文档层级

冲突时，优先以高层文档为准。修改时间更新者优先。

- **L1** `CLAUDE.md` / `AGENTS.md` — 全局协作规则、文档索引、工作模式触发，两份文件内容保持一致。禁区：产品需求、技术细节、任务进度
- **L1.5** `docs/harness/top/HARNESS.md` — 工作模式的完整流程、路由规则、handoff 协议
- **L1.5** `docs/harness/eval-guide.md` — 评估模式操作指南（评分维度、检查流程、工具使用）
- **L1.5** `docs/harness/styles/code.md` — 各语言编码规范
- **L1.5** `docs/harness/styles/doc-review.md` — 文档审阅规范（两版流程）
- **L2** `README.md`（及 `README.en.md`，如存在）— 项目简介、核心价值、快速开始、文档索引。禁区：详细技术方案、任务拆解
- **L3** `docs/product-specs/` — 产品"做什么"：功能范围、用户故事、验收标准、优先级。禁区：API 设计、数据模型、部署命令
- **L4** `docs/ARCHITECTURE.md` — 当前系统的模块职责、依赖、数据流与稳定约束，关联具体设计和契约。禁区：任务拆分、估时
- **L4** `docs/harness/project-context.md` — 项目实际文档路径、运行约束、验证/评估和可观测性入口。没有独立评估或 Trace 子系统时，明确写出当前替代机制与后续触发条件。禁区：实现细节、需求池
- **L5** `docs/design-docs/*-hub.md` — 专题中枢文档：串联同一需求及其衍生需求在多次评估/规划/生成轮次中散落的所有文档、评估报告、backlog 条目、提交记录。是专题的唯一入口
- **L6** `docs/eval/baseline.md` — 量化评估基线
- **L7** `docs/backlog.md` — 需求池、演进路线图、Plan → Generate 交接；归档后只保留未完成条目。禁区：API 设计、数据模型
- **L8** `docs/version/` — 已完成版本、周期记录、一次性审查和历史产物
- **L9** 代码实现 — 最终事实来源

> 项目自行维护的文档由项目上下文或根部文档索引关联，按需读取。
>
> 文件名、各文档的最小结构、backlog 状态与归档规则以文档治理规范为准。`docs/changelog.md` 不是标准文档：版本完成后写入 `docs/version/vX.Y.Z.md`，不要新建或保留独立 changelog。

## 任务关闭与用户验收

### 状态定义

- `WIP`：AI 正在开发、运行自动验证或处理 AI 自身可解决的阻塞。必须记录 AI 的下一步和阻塞原因，不能表示等待用户。
- `待用户验收`：本次实现及按完成门选定的检查已完成，剩余工作是用户试用或在真实环境验收。
- `Done`：所有验收已完成。交付前将按完成门选定的检查写入实施记录。用户确认验收成功后标记 `Done` 并记录确认日期。

新任务所表达的前轮验收确认，以及未完成任务的阶段提交，按全局“任务切换与提交”规则执行；阶段提交保留未完成状态和实际验证缺口。

### backlog 交接模板

处于 `待用户验收` 的任务详情必须追加以下字段：

```markdown
- **（用户）验收操作**：打开 <入口>，执行 <一个快速试用或真实环境验收操作>。
- **预期结果**：<可观察的通过条件>。
- **最小回传**：回复"<任务编号> 已通过"；无需导出已有系统日志。
- **AI 自动验证**：<交付验收前已完成的回归测试/脚本/Trace 自查与结果，记入实施记录>。
- **关单方式**：用户回复确认后，AI 在同一轮直接将任务改为 `Done` 并注明确认日期，不追加核验。
```

用户已在对话中说明验收完成时，AI 必须将其视为最终关单信号：在同一轮把任务更新为 `Done` 并记录用户确认日期，不反向核验用户的验收结论，不得仅解释状态原因，也不得要求用户补充或代为收集系统已有记录。

## 角色间 Handoff：Plan → Generate

规划完成后到执行之间，通过 backlog 条目完成交接：

1. **规划产出**：Planner 将方案写入 backlog 对应条目的「方案」字段，状态更新为「已规划」。条目使用统一结构（状态 / 背景 / 方案 / 分析 / 验收），确保 `/clear` 后新会话中的 AI 能完整理解任务上下文
2. **启动执行**：用户在**新对话**中让 AI 读取「已规划」条目，进入生成模式执行
3. **交接内容**：backlog 条目本身即为交接协议，结构化字段使 AI 无需依赖对话历史即可理解要做什么、怎么做
4. **若该需求已存在中枢文档**：在方案文档中增加反向链接指向中枢，并在中枢文档中更新当前阶段状态

当前由用户手动串这个流程（结束规划对话 → 开新对话 → 指向 backlog 条目执行）。后续工作流自动化后，状态流转自然触发角色切换。

---

## 角色间 Handoff：Eval → Plan

评估完成后到规划改进之间，通过 backlog 条目完成交接：

1. **评估产出**：评估器将评分报告写入 `docs/eval/reports/`，如发现需要改进的问题，在 `docs/backlog.md` 中新增条目（状态 = 待规划，只描述问题现象和严重程度，不写方案建议）
2. **启动规划**：用户在**新对话**中让 AI 读取评估报告 + backlog 条目，进入规划模式产出改进方案
3. **交接内容**：评估报告（评分维度 + 得分点/失分点）+ backlog 条目（问题现象），使规划器无需依赖对话历史即可理解需要改进什么
4. **判断是否需要中枢文档**：评估完成后，检查当前需求是否已经历过 ≥2 轮规划/开发/评估。若是，创建或更新中枢文档，将本轮评估报告和新发现的衍生问题登记进去

与 Plan → Generate 交接形成完整闭环：**Eval → Plan → Generate → Eval**。

## 专题中枢文档

### 何时创建

当以下条件**全部满足**时，应创建专题中枢文档：

- 同一需求（如 backlog 中的一个功能条目）经历了 **≥2 轮**评估/规划/生成的循环
- 过程中产生了衍生问题（新的 backlog 条目），分散在多个文档中
- 存在多份评估报告、多份设计文档指向同一个主题

满足条件时，中枢文档由**当前轮次的操作者**（评估器/规划器/生成器）主动创建或更新。

### 中枢文档的内容

```markdown
# <编号> <主题名> — 专题中枢

> 本文档是「<主题>」改进工作的**唯一中枢**，汇总所有关联产物。
> 后续围绕本专题的新一轮规划/开发/评估，均以本文档为入口，新增产物在此登记。

## 1. 专题总览
- 问题一句话
- 核心矛盾
- 解决方案概要

## 2. 关联文档索引
- 设计文档（表：文档 / 内容 / 状态）
- 评估报告（表：报告 / 时间 / 评分 / 通过 / 关键发现）
- Backlog 条目（表：编号 / 名称 / 状态 / 说明）

## 3. 完整时间线
按时间顺序列出每个节点（产出、评分、关键发现）

## 4. 当前状态：各项完成度
- 原始方案验收标准逐项状态
- 衍生问题逐项状态及优先级判断

## 5. 下一轮优化建议
- 最优先项及理由
- 验证方式

> 本节只给**方向性指引**（先做什么、为什么、怎么验证），不承载任务拆分与实施步骤，那是 backlog 条目的事。

## 6. Git 提交记录
## 7. 设计决策记录
```

### 命名规范

`docs/design-docs/YYYY-MM-DD-<序号>-<topic-slug>-hub.md`

- 日期前缀与普通 design 文档一致，便于按时间排序时中枢文档紧邻其关联的方案文档
- `<序号>` 与同主题第一份方案文档的序号一致（如 `2026-07-27-2-suggest.md` → `2026-07-27-2-topic-discovery-hub.md`）
- `-hub` 后缀标识这是中枢文档

### 反向链接

所有被中枢文档引用的关联文档（设计文档、评估基线），应在**顶部元数据区**增加指向中枢文档的反向链接：

```markdown
> 中枢文档：[YYYY-MM-DD-<topic>-hub.md](YYYY-MM-DD-<topic>-hub.md) — 本专题全部关联产物的汇总入口
```

### 维护规则

- 中枢文档创建后，**每次经过本专题的一轮评估/规划/生成，都更新中枢文档**（新增时间线节点、更新完成度、刷新下一轮建议）
- 完成度变化时更新对应条目的状态标记
- 新产生的衍生问题追加到关联 backlog 条目表中

## 设计、任务与架构的职责分离

相关材料按职责保存信息：

- `docs/design-docs/`：**功能视角**。需求背景、设计目标、用户交互流程、概念级数据关系、关键决策理由、验收标准。面向"理解这个功能是什么、为什么这样做"。不写代码细节
- `docs/backlog.md` 条目「方案」字段：**技术视角与任务交接唯一载体**。涉及哪些模块、数据流向、模块间交互方式、迁移策略，以及任务的子阶段拆分。面向"生成模式知道该改哪里、大致怎么改"。不写伪代码和变量名；不另建独立任务计划文档或 exec plan
- 详细设计中的必要接口、数据与配置契约保存在 `docs/design-docs/`。代码落地后清理仅重复实现的片段，稳定约束由 `docs/ARCHITECTURE.md` 概括并链接。
- 简单方案直接写入 backlog，已有条目足够驱动执行时，按条目实施；需要长期保留的设计另写入 `docs/design-docs/`。

## 项目文档治理规范

> 适用于已接入 pancake harness 的项目。本文定义跨项目通用的文件名、职责和最小结构；项目特有的字段、技术栈与补充文档写在项目内。

各类文档的信息分层与维护遵循[文档治理规范](DOCUMENTATION.md)，以下约定用于项目任务及版本资料。

### 1. 标准文档集

- `README.md`：项目入口；只保留定位、核心能力、快速开始和文档索引。
- `docs/product-specs/`：稳定的产品/项目契约，说明目标、范围与验收条件。固定总规格沿用入口名，随功能迭代持续新增的专题规格采用日期前缀。库或工具项目的用户可为调用方或维护者。
- `docs/ARCHITECTURE.md`：当前有效的架构入口，说明模块职责、依赖方向、关键数据流与稳定约束，关联详细设计、接口契约和运行入口。
- `docs/harness/project-context.md`：项目实际文档路径、运行约束、验证/评估和可观测性入口，关联公共流程与项目补充。
- `docs/backlog.md`：唯一的活跃需求池，以及 Plan → Generate 的交接载体。
- `docs/design-docs/`：当前有效的专题设计，文件名按设计记录写法。经历两轮以上循环且关联物分散时，使用 `*-hub.md` 作为该专题唯一入口。
- `docs/version/vX.Y.Z.md`：已完成版本/里程碑归档；包含范围、完成事项、验证记录和遗留事项。历史版本信息在此沉淀，**不得使用 `docs/changelog.md`**。
- `docs/harness/` 保存治理规范，`docs/harness/top/` 保存顶层控制与模式，项目补充写在对应公共块之外。

按实际工作建立任务产物及索引。具体产品、设计、任务与人工资料由项目维护，公共文件的发布范围以中央模板为准。

### 2. 文档入口与索引

- 总规格索引专题规格，系统设计入口索引专题设计。架构入口概括现行架构，并链接系统设计入口供查阅专题方案。
- 版本 README 索引版本记录。历史设计分散时，从版本入口链接按专题组织的历史索引。迁移时更新活动引用，冻结快照沿用原文。
- 项目上下文关联实际路径。专题间的直接引用遵循[文档治理规范](DOCUMENTATION.md#信息分层与维护)。

### 3. 命名和职责边界

- 文件名前缀按全局 Agent 规则的「文档命名与排序」选择。英文主题名与目录名使用小写 kebab-case，固定入口沿用约定大小写。
- `docs/product-specs/` 说明产品目标、行为与验收条件。`docs/ARCHITECTURE.md` 定位当前系统，`docs/design-docs/` 记录专题方案与必要契约，backlog 承担任务状态、实施交接和任务拆分。
- 不以新文档复制现有内容。可用链接定位时只写摘要和链接；明确否决的方向记入任务关联的决策记录，完成任务移入版本归档。
- 文档中的日期、版本、代码路径和验证结论必须可追溯。代码已成为事实来源时，删去会与代码重复漂移的实现细节。

### 4. Backlog 固定格式

文件以 `# Backlog` 开头，先给出状态流和 `## 任务总览`；总览表头固定如下，即使没有任务也保留空表：

```markdown
| 状态 | 分组 | 编号 | 任务 | 评估 |
| ---- | ---- | ---- | ---- | ---- |
```

状态流转为 `待规划` → `规划中` → `已规划` → `WIP` → `待用户验收` → `Done`；`暂缓` 表示明确不在当前周期执行。任务详情按编号作为三级标题，使用 `状态 / 背景 / 方案 / 分析（按需） / 任务列表（按需） / 验收` 字段。评估模式新增的条目只写问题和证据，保持“待规划”，由规划模式补方案。完成或不再活跃的条目移入对应 `docs/version/vX.Y.Z.md`，并在总览下保留归档链接。

### 5. 新项目接入检查

1. 按项目事实建立项目上下文和 `docs/ARCHITECTURE.md`，按实际需求建立产品规格，保留有效正文及必要入口。
2. 将活跃任务迁入统一 backlog 表头和状态。已有版本与旧 changelog 内容归入 `docs/version/`。
3. 按[双入口维护](top/adoption.md#双入口维护)核对 `AGENTS.md` 与 `CLAUDE.md`。
4. 确认公共块与项目补充的边界清晰，项目内容均位于 marker 外。
