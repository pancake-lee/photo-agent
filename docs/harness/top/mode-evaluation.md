# 评估模式

评估模式独立检查产物是否满足需求，记录问题与证据，决定通过或返回哪个环节。

## 进入模式

用户表达“评估一下”“打分”“检查质量”等意图时，进入评估模式。执行对象为指定功能、任务或代码范围。

## 读取依据

读取需求、验收条件、相关代码、自检记录和 `docs/ARCHITECTURE.md`。
按需查阅 `docs/harness/DESIGN.md` 等任务原则、`docs/harness/styles/` 中的规范及任务引用的资料。

评估 Task 或 Bug 时读取 `docs/backlog.md` 对应条目；评估 Feature 或 Epic 时，读取关联条目及详细设计或概要设计。历史工作查阅对应版本记录。

## 检查与判据

使用独立上下文读取需求与产物，不沿用生成过程的推理。同一会话内检查时，标为自评，不声称已完成独立评审。

1. 功能行为：对照需求检查正常、边界与失败场景，核对测试能否识别错误结果。遗漏核心行为、结果偏离预期或测试掩盖错误时，记录缺陷；验收条件遗漏需求时，记录规格问题。
2. 架构适配：对照已确认的依赖方向、接口和适用的安全、性能要求。违反约束或破坏既有行为时，记录缺陷；不把当前任务未要求的能力当作缺陷。
3. 可维护性：对照项目规范检查重复、抽象、命名、注释和文档。指出具体维护影响或明确违反的约定；仅有个人写法偏好时，不判为缺陷。

先查功能与架构问题，再查维护问题。发现足以使后续审阅失效的严重问题时，先报告并等待修订。

复核生成自检的覆盖范围。有缺口或疑点时，按生成模式完成门选择补充验证，不默认重跑全部检查。每项发现写清位置、预期、实际表现和影响；无法证实时标为待核实。

## 问题分级与结论

总分满分 10 分，以 0.5 分为步长。结合检查判据与证据说明评分理由。证据不足时将分数标为暂定，列出待核实项，不以猜测补齐评分依据。

问题按影响分级：

- 高影响：核心流程不可用，或存在可证实的安全、数据损坏风险。
- 中影响：特定场景结果错误、违反架构约束，或造成可说明的维护障碍。
- 低影响：不影响本次需求与约束的局部改进建议。

存在高、中影响缺陷时判为“需修订”；核心验收缺少证据时判为“待核实”；核心验收证据充分且无阻断问题时判为“通过”。低影响建议不阻断通过。

问题等级和通过条件独立判断，不由总分抵消阻断问题。

## 输出与交接

将总分与理由、通过结论、问题及影响等级、证据与未验证项、反馈去向依次写入任务记录，与生成自检分别记录。

根据问题选择一个或多个出口；技术债务、外环优化可以与局部缺陷、方向修正或与人交互并行，分别记录处理状态。

需要后续处理的已证实缺陷登记为 `Bug`，改进工作登记为 `Task`，状态设为“待规划”，只写问题、影响、证据和验收目标。未证实的疑点先核实；同一问题已有条目时更新原条目。

- 局部缺陷：局部实现缺陷，返回[生成模式](mode-generation.md)，附问题与证据。
- 方向修正：规格遗漏、设计变更或多轮修复无效，返回[规划模式](mode-planning.md)，说明需要重新判断的内容。
- 与人交互：证据不足或需要用户取舍，提出待核实项或决策问题，不自行补设需求。
- 技术债务：用户确认暂缓，在 backlog 对应条目记录状态、影响与重启条件。
- 外环优化：可复用的 Harness 改进，按总纲外环流程提出候选，不自动修改规则。

收到用户对待核实项或取舍问题的反馈后，检查其中是否包含新的评估标准。可复用的判断进入“外环优化”，提出判据或评分锚点的修订候选，交用户审批后用于后续评估；一次性需求只回写当前任务。

评估模式不修改代码、不展开修复方案。通过时交付评估结论。

[评估实践参考](../../references/evaluation-practices.md)：仅在追溯来源或修订评估标准时读取。

## 触发与执行细则

**触发词**：`评估` / `评估一下` / `打分` / `检查质量`

> 具体的评分维度和操作指南见 [eval-guide.md](../eval-guide.md)。

**职责**：对代码/功能产出做质量评分。评估器是"判卷老师"，只判断好坏，不提出解决方案。

**流程**：

1. 确认评估目标（哪个功能、哪段代码、哪个 PR、哪个提交）
2. 读取相关材料：设计方案（`docs/design-docs/`）、编码规范、评估基线（`docs/eval/baseline.md`）、目标代码
3. 按「代码逻辑本身 / 与人协作的部分」两类拆分确定轮次；**范围小时一次评完，范围大时先评逻辑、再评协作**；任一轮「不通过」（标准见 eval-guide.md「评分标准速查」）即停下，先修后评
4. 按评分维度逐项打分，每个维度列出**得分点**（哪里好）和**失分点**（哪里不好）
5. 汇总输出评估报告到 `../eval/reports/`
6. 如发现需要改进的问题：在 `docs/backlog.md` 中新增条目（状态 = 待规划，**只描述问题现象，不写方案**）
7. 如涉及基线指标：更新 `docs/eval/baseline.md`

**评分维度**：维度的完整列表、两类归属与优先级（先评代码逻辑本身，再评与人协作的部分）见 eval-guide.md「评分维度」，本条不重复。

**行为边界**：

- 不修改代码，只收集信息和判断
- 不提出"应该怎么改"，只指出"哪里不够好"
- 后续由规划模式读取评估报告，产出改进方案
