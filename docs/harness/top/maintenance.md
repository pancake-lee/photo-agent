# Harness 外循环

外循环随日常任务中的反馈触发，按以下步骤维护协作规则。

1. 出现用户纠正、重复失误、规则冲突或明显协作负担时，先处理当前问题。Agent 将有复用价值的反馈及实际影响留在任务记录中。
2. 核对问题与现有规则，区分规则缺陷、执行偏差和任务特例，据此选择纠正执行或调整规则。
3. Agent 提出规则候选，写清适用范围、建议改动、理由、预期改善与代价，优先修订、合并或删除已有内容。
4. 反馈与候选可直接留档，规则采用由用户确认。已有授权覆盖的修改直接执行，应用范围随授权确定，决定与依据留在维护记录中。
5. 在后续日常任务中观察原问题是否减少、是否增加负担，据此保留、调整或撤回规则，并记录原因。尚无后续观察时标记为待观察。

## 外循环细则

外环维护检查规则是否改善协作与产物，产生待审批的改进；它不增加新的任务工作模式。

### 触发与取证

用户反馈、重复失误、规则冲突、交接困难或明显的阅读与执行负担出现时，检查相关任务与规则。版本复盘可抽样检查，不要求每个任务完整审计 Harness。

在所属范围的 `_agents/` 复用已有记录，留存规则位置或版本、变更日期、目标与原因、来源案例及实际影响。规则新增、修改或删除均保留依据，既有依据缺失时如实标明，后续补充。依据仅在维护或追溯时按需读取。

先区分需求、实现、环境、执行与规则问题，再判断是否需要改 Harness；单次业务缺陷不自动上升为通用规则。

### 形成候选

按[审批规则](RULES.md)归纳适用条件、判断依据与动作。优先修订、合并或删除已有内容；区分个人偏好、项目约定与跨项目原则。

以代表案例检查交接、证据有效性、判据一致性、上下文成本和人工负担，按适用项评价并说明依据；需要分数时沿用[质量评价方法](../QUALITY_SCORE.md)。社区资料用于对照，是否有效由本地案例验证。

候选写明问题、建议改动、预期收益、成本和验证方式。能够由确定性条件判断的要求，可提出脚本候选；先获批再实现，不为当前任务临时增加检查体系。

### 审批与生效

原始反馈直接记录，提炼后的规则及修订由用户审批，决定及授权范围记入同一依据记录。用户明确确认或按约定暂存的内容作为已审批范围，后续新增的未确认差异继续作为候选。Git 操作遵循全局授权约定。

试用记录注明候选版本与范围；试用不等于长期获批。候选、已批准规则和观察结果分别标明，避免执行者误把讨论稿当作常驻要求。

### 验证与回退

获批后选择同类任务验证预期行为，检查原问题是否减少，以及是否新增阅读、执行或审批负担。在同一依据记录中补充任务证据、用户反馈与观察结果，尚无后续样本时标为“待观察”。

无改善或代价过高时提出修订或回退，保留原因；历史记录与归档快照不回写。

### 推广与维护

项目经验进入公共规则前，至少用另一种任务场景检查适用性，移除私有路径、依赖和仅本项目成立的假设。项目接入按[接入与迁移](adoption.md)执行，向其他项目或全局位置发布须有明确目标与授权。

规则膨胀时按审批规则拆分，并核对入口、职责与链接；删除要求时同步清理对应重复检查和引用。
