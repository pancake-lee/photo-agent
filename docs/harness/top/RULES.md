# Harness 审批规则

## Agent/Harness 规则编写

- 从案例提炼原则：将触发问题转化为适用于一类任务的判断依据与行动要求，不把当次对话、特定术语或临时处理方式直接固化为通用规则。
- 保持适当抽象：规则应说明何时适用、依据什么判断、如何行动；既不堆砌个案例外，也不抽象成无法指导行为的口号。具体路径、工具和参数仅在其本身属于稳定约束时保留。
- 检查跨案例适用性：定稿前，用不同主题或场景检验规则是否仍然成立；若依赖原案例才能理解或执行，应重新提炼，或将其限定为局部约定。
- 控制规则增量：优先修订或合并已有原则，不因每次纠正就新增一条禁令。案例可用于解释和验证规则，但不代替规则，也不默认写入常驻指令。

## 规则写法

编写或修订规则时，逐句判断其对理解或执行的作用，合并重复约束，删去冗余解释与枚举，保留适用条件、行为要求和必要边界。篇幅与条目数量随内容需要确定，案例和推导按需另存。

1. 直接写出主体和动作，减少长修饰语，每句表达一个主要意思。
2. 按用途选择简短句式：职责用“谁负责什么”，条件用“满足什么条件时，执行什么动作”，分工用“A 做什么，B 做什么”。
3. 同类条目使用相同句式，同一概念使用相同术语；不为统一形式改变原意。

## 内容组织

遵循全局的“金字塔原理与工作组织”原则，以下约定用于 Harness 文档的具体组织。

1. 按当前内容和查找需要组织文档与目录。
   - 按稳定性与使用者组织层级。根部 `AGENTS.md` 提供入口，`docs/` 面向开发者常用资料和持续增长的任务产物，`docs/harness/` 保存治理规范，`docs/harness/top/` 保存顶层控制规则。
   - 同一文档的并列主题或专项细则增多，影响定位或导致无关内容随任务加载时，按职责拆为多个文档。有后续查阅需要时，原处保留概括、适用条件和入口，支持按需读取。
   - 父目录子项较少、子目录只有一两个文件时，优先平铺到父目录，待实际规模或查找需要明确分组时再增加层级。
2. 规则按目标状态编写，删除搭建或迁移期间的临时兼容要求、已被正向规则覆盖的反例和纠正痕迹。必要背景留在讨论记录中。关联修改尚未完成时，用 `TODO xxx` 写明待办。

## 文档与链接类型

1. 受众分为 `HumanOnly`、`Shared`、`AgentOnly`，分别表示仅供人阅读、人和 Agent 共用、供 Agent 使用。默认采用 `Shared`，一般省略标记。
2. 需要标记时，文档类型放在标题下，如 `[HumanOnly]`；链接类型放在链接前，如 `[HumanOnly] [标题](../路径)`。链接标记说明本次引用的用途，不改变目标文档的整体受众。
3. Agent 不将 `HumanOnly` 内容作为任务上下文读取；用户明确要求审阅或维护该内容时可读取。`Shared` 和 `AgentOnly` 按任务需要及注明条件读取，标记本身不要求立即加载。
