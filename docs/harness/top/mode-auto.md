# 全流程模式

触发方式包括用户明确要求全自动或完整执行，以及[反馈路由](HARNESS.md#反馈路由)判定为较大改动或多项独立改动。

在同一会话串联规划、生成和评估。按可独立验收的结果划分任务，并按依赖顺序逐项完成。每项先完成评估和本地提交，再开始下一项。设计与验证的篇幅随任务范围和风险确定。

## 阶段 1 · 规划

1. 查阅相关需求、代码和已有任务，逐项在 backlog 记录目标、依赖、方案和验收条件。设计载体按[规划模式](mode-planning.md#选择文档)选择。
2. 有重要方案取舍时依照[总纲](HARNESS.md#通用协作约定)请求用户选择，可继续处理已明确的独立任务。方案明确时完成规划并进入生成。

## 阶段 2 · 生成

按方案完成当前任务，依照[生成完成门](mode-generation.md#完成门)验证核心路径、受影响的边界和失败场景。同步 backlog 的状态与证据，以及受到影响的设计或使用说明。

## 阶段 3 · 评估与提交

1. 按[评估模式的检查判据](mode-evaluation.md#检查与判据)对照需求与验收条件检查产物。记录结论、证据和缺口。同一会话的检查标为自评。问题影响当前验收时，返回相应阶段修正后再评估。
2. 自动验证和文档同步结束后，按[生成模式](mode-generation.md#任务状态)更新状态。真实环境需用户验收时，记录操作和预期，并将当前实现提交供验收。
3. 本模式按总纲自动路由或由用户明确启用时，可为当前任务执行 `git add` 和 `git commit`。检查暂存范围，共用文件按改动范围选取。保留其他任务的未提交改动和原有的暂存状态。每项一个本地提交，推送按用户授权另行处理。
4. 交付时列出各任务的提交、验证结论和待验收项。评估发现其他任务的问题时，在 backlog 对应条目记录，决策交用户。

接手已经混在工作区的改动时，先从现有差异重建每个任务的提交边界并核对依赖。逐个检查拆分后的版本能按顺序独立验证，再按上述范围提交。
