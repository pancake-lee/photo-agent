# 规划模式

规划模式将需求转为可执行、可验收的方案，交给生成模式。

## 进入模式

用户表达“规划一下”“帮我设计”“出个方案”等意图时，进入规划模式。执行对象为用户提出的新需求或指定的已有任务。

## 规划类型

- 资料驱动规划：以明确的产品文档、设计稿等 reference 为依据，通常着重技术方案；需要补充产品或 UI 设计时，说明资料缺口及新增设计范围。
- 简述需求规划：以用户直接描述的目标为起点，按需设计产品功能、UI 交互与技术方案。

产品规格和设计文档开头标明规划类型、需求来源和本次设计范围。资料驱动规划链接具体 reference；简述需求规划标为“用户对话”，将需求结论写入正文。已有约定与本次设计分别说明。

## 记录对话需求

1. 将多轮澄清形成的当前结论写入产品规格；独立 Task 或 Bug 写入对应条目。记录目标、范围、核心行为、约束和验收条件，供后续设计与实施使用。
2. 保留影响方案的关键取舍及理由、关键误解与澄清后的含义。没有对应内容时省略，不逐轮转录对话。
3. 新反馈改变需求时，更新同一处结论，保留必要的变更理由；不同文档引用该结论，避免维护多份需求副本。影响结论的歧义直接向用户确认。

```markdown
## 需求结论
<目标、范围、核心行为、约束和验收条件>

## 关键取舍
<选择了什么，为什么>

## 关键澄清
<影响方案的误解，以及最终确认的含义>
```

## 读取依据

读取需求、相关代码、`docs/ARCHITECTURE.md` 和已有任务记录。
按需查阅 `docs/harness/DESIGN.md` 等任务原则、`docs/harness/styles/` 中的规范及任务引用的资料。

已有工作从 `docs/backlog.md` 对应条目或分组进入，查阅关联规格、Feature 详细设计或 Epic 概要设计。

涉及配置或环境问题时，读取或申请读取 `.local/` 中的实际配置，不假设配置已就绪。

## 选择文档

Task 与 Bug 在 `docs/backlog.md` 记录实施与验收；需要独立设计时建立或聚合为 Feature。跨阶段、多轮且包含多个 Feature 的整体需求建立 Epic。资料按职责组织：

- `docs/product-specs/`：记录目标、范围、失败场景和可验证的验收条件，按[产品规格写法](../styles/product-spec.md)标明输入来源。
- `docs/design-docs/`：Epic 输出概要设计，Feature 输出详细设计。设计判断遵循[设计原则](../DESIGN.md)，内容结构遵循[设计记录写法](../styles/design-doc.md)。
- `docs/references/`：保存外部给定的设计稿、技术约束等参考事实。
- `docs/backlog.md`：记录 Task/Bug、Epic/Feature 归属、依赖、实施顺序、状态和验证结果。

`docs/backlog.md` 汇总当前版本任务。
Epic 与 Feature 通过归属字段关联实施工作，Task/Bug 保持独立条目，不增加父 Task。
[任务组织与版本归档](../PLANS.md)规定 backlog 与版本记录的写法。

## 制定方案

1. 澄清需求：确认目标、范围、依赖和验收条件。
2. 选择方案：优先解决根因。存在多个可行方案时，列出核心利弊，请用户选择；需要用户介入时，直接说明阻塞原因。
3. 记录决策：按上述分工写入文档。方案写清实现方向和必要接口契约，保留其他编码细节的实现空间。
4. 确定任务和验收。反馈按[任务归属规则](../PLANS.md#反馈的任务归属)落到 backlog 条目。每个任务写清目标、涉及模块和验收条件，实施步骤记在对应条目中。用户执行的操作以“（用户）”开头。

## 设计验收

规划模式写清核心需求的操作、输入与预期结果，记录在规格或对应 Task、Bug 条目中。验收条件不等于自动化端到端测试。

核心流程跨多个组件，且局部测试不足以证明结果时，设计端到端用例；局部逻辑、文案或结构调整通常不需要。是否自动化取决于复用价值、运行与维护成本；不适合自动化时，指定其他可核对证据。

## 确认与执行

默认简述方案后直接更新规划文档；修改代码转入生成模式。涉及数据迁移、删除数据或外部发布等高成本、高影响操作时，先向用户确认。用户已明确授权的操作不重复确认。

## 输出与交接

将方案、执行步骤和验收条件写入上述任务文档。交付设计稿时，先完成[设计记录的交付前自查](../styles/design-doc.md#交付前自查)，再将任务标为“已规划”。
提供任务与方案入口，交给[生成模式](mode-generation.md)。

## 触发与执行细则

**触发词**：`规划一下` / `帮我设计` / `出个方案` / `怎么做` / `我发现问题` / `这里不够好` / `效果不对` / `有个 bug`

**流程**：

1. 确认规划对象：用户口述的新需求、或 `docs/backlog.md` 中指定条目
2. 读 `docs/backlog.md` + `docs/product-specs/` + `docs/ARCHITECTURE.md`（及项目上下文指定的相关人工资料）获取上下文。**涉及配置/环境问题时，可以或申请读 `.local/` 下的实际配置文件**，不要假设"用户本地配置已就绪"
3. 需求分析：检查依赖项是否满足、判断复杂度（简单/中等/复杂）
4. 产出方案。**无论任务体量，技术方案始终写入 backlog 条目的「方案」字段**（说清涉及哪些模块、大致方向、数据流向）。只有中大体量且需要长期说明的功能设计或架构决策，才额外创建 `docs/design-docs/` 文档作为补充；design 文档不重复 backlog 中已有的技术方案
   - **小体量任务**（单文件改动、纯前端交互调整、简单逻辑修复）：方案仅写入 backlog，不创建 design 文档
   - **中大体量任务**（跨模块、涉及架构决策、需要子阶段拆分，且有需要长期保留的功能/交互/架构决策）：backlog 写技术方案 + 额外产出 design 文档
   - **路径与命名治理**（目录整理、文件迁移/改名、配置键改名及其引用同步）：即使波及多个模块，只要不改变功能、数据模型或用户交互，仍属于小体量任务；仅在 backlog 记录方案和验收，不创建 design 文档
   - 设计文档按[设计记录写法](../styles/design-doc.md)组织。实施步骤写入 backlog，接口字段和路由等细节引用所属资料。
   - 无论哪种载体，方案描述保持**高层抽象**：说清"做什么、达到什么效果"，不写伪代码、CSS 属性值、变量名等实现细节。给生成模式留出实现自由度
5. **必须输出明确的任务列表，且任务拆分的落点是 backlog 条目**，不可将待执行任务埋在大段文字中间，也不可把任务拆分/实施步骤写进 design 文档或中枢文档（后者只做方向性指引与索引）。用户需手动执行的任务以 **（用户）** 前缀着重标记，例如："（用户）在 `.local/` 配置文件中补充对应密钥"
6. 简单任务：方案中直接包含实现步骤；复杂任务：在同一 backlog 父条目下明确子阶段拆分（每个子阶段含目标、涉及模块、验收标准）。**规划任务、子任务和实施步骤的唯一落点是 `docs/backlog.md`；不创建独立任务计划文档或 exec plan。**
7. 更新 `docs/backlog.md` 中对应条目的状态为「已规划」，填入「方案」字段

**设计原则**：

- **根因优先**：本项目体量小，遇到问题优先找根因并直接修复，而非叠加容错/降级逻辑。典型反例：配置缺失时不应设计"配置不可用时的容错分支"，而应指引用户补配置
- **主动沟通**：发现需用户介入的阻塞问题时，直接向用户说明情况并给出选择（如"方案 A：我加容错自动降级；方案 B：你补一行配置，我给你具体指引"），不要默默记入 backlog 等用户自行发现
- **方案保持高层抽象**：规划阶段描述"要达到什么效果、交互行为如何、大致方向"，不写伪代码、不指定 CSS 属性值、不预设变量名或函数签名。生成模式应有足够的实现自由度，而非单纯执行规划阶段已写好的代码变更

**方案改动确认规则**：

- 默认直接执行：给出一段简要方案说明后直接修改文档与代码，不再问「是否按此方案改」
- 仅在以下情形停下来询问用户：
  - 存在多个可行方案需要用户选择（列出方案含核心利弊，直接问「推荐哪个」）
  - 改动成本或后果较大（涉及数据迁移、删除数据、外部发布等）
- 用户主动说"全自动修改"等意思：无需确认，直接完成所有修改
