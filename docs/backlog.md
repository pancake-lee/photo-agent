### BQ5 Embedding 外部调用缺少受控时限

- **状态**：Done
- **背景**：Embedding 代理使用 `http.DefaultClient` 调用外部服务，未设置显式超时且未传播调用方取消；多条输入逐条串行处理，外部服务无响应时请求时长不可控。
- **严重程度**：P1，外部依赖阻塞风险。
- **证据**：[后端代码质量基线评估](../data/eval_reports/2026-08-29-backend-code-quality-baseline.md)。
- **方案**：为 Embedding 外部客户端建立唯一受控调用边界：请求继承入站 HTTP 上下文，客户端使用固定的显式时限；每条输入复用同一个受限上下文，保持现有串行执行和结果顺序。超时、调用方取消和非成功响应统一返回可定位错误，不改变 OpenAI 兼容响应的成功格式。
- **实施任务**：
  - 后端：收敛 Embedding 请求构造与执行入口，传递入站取消信号并配置有限时 HTTP 客户端。
  - 测试：使用本地模拟外部服务覆盖成功响应、超时、调用方取消和失败响应；断言后续输入不会在请求已终止后继续发出。
  - 验证：运行目标测试、全量 Go 测试、`go vet` 与受影响包的 race 检查。
- **验收**：外部服务不响应时请求在确定时限内结束；调用方取消会停止下游调用；多输入成功时返回顺序、索引、向量和用量统计保持兼容。

- **实施记录**：Embedding 调用使用 15 秒 HTTP 客户端和继承入站请求的受限上下文；新增本地 HTTP 测试覆盖成功顺序与用量、失败后停止后续请求、超时和取消。`GOTOOLCHAIN=local go test ./...`、`go vet ./...` 和受影响包 race 检查通过。

### BQ8 数据访问边界与 Go 格式统一

- **状态**：Done
- **背景**：`internal/pkg/perr/err.go` 未通过 `gofmt` 检查，仍保留 CRLF 格式差异；此外，`svc_photo.go`、`svc_vlm.go`、`svc_storage.go`、`svc_query.go` 和 `ai_quality.go` 仍有 Service 直接使用 GORM、只读数据库连接或生成查询对象的情况，数据访问边界不一致。
- **严重程度**：P2，可读性与格式一致性问题。
- **证据**：[后端代码质量基线评估](../data/eval_reports/2026-08-29-backend-code-quality-baseline.md)。
- **方案**：将所有 Service 直接 ORM/只读 SQL/生成查询访问迁入 `data`，按业务动作或返回对象命名：单表访问使用明确的查询、更新或删除动作，跨表和聚合访问使用业务结果命名。Service 只编排业务规则、文件和外部调用，不再自行定义查表细节。同步把这条约束写入 Go 编码规范和后端评分标准，并格式化现有手写 Go 文件；不为减少少量代码而引入泛化 DAO。
- **实施任务**：
  - 规范：在 Go 编码规范和评分标准中加入“ORM 仅限 `data` 层、以业务语义封装”的判定、正反例及检查范围。
  - 后端：为当前直接访问点补齐有意义的 `data` 函数，迁移照片审查/覆盖、VLM 描述写回与处理履历、存储最新同步时间、只读 SQL 执行及照片 schema 的数据访问责任；Service 保持既有接口语义。
  - 格式：对 `perr/err.go` 和本轮手写 Go 修改文件执行 `gofmt`，统一换行与格式。
  - 验证：搜索确认 `service` 不再直接调用 ORM、`pdb` 或生成查询对象；为新增 DAO 行为补充合适的临时 SQLite 测试，运行全量 Go 测试、`go vet` 与 `gofmt` 检查。
- **验收**：数据访问只出现在 `data` 层且函数名称表达业务意图；Service 接口行为不变；手写 Go 文件通过 `gofmt` 检查；规范和评分标准可用于后续评审。

- **实施记录**：照片审查、单张校验、覆盖写回、VLM 描述写回和履历、最新同步时间、只读 SQL 执行及 schema 反射均已收敛到 `data`；Service 仅保留业务编排与 API 转换。`perr/err.go` 与本轮文件已格式化；静态检查确认生产 Service 不再直接调用 ORM、`pdb` 或生成查询对象，`gofmt`、`go test`、`go vet` 和 race 检查均通过。

### BQ10 用户路径测试修改表结构

- **状态**：已规划
- **父任务**：BQ6。
- **背景**：`backend/internal/defaultService/service/user_paths_test.go:25-44` 的测试夹具通过 `Migrator().CreateTable` 和原始 `CREATE TABLE` 初始化临时 SQLite。项目 Go 规范明确禁止测试修改表结构；该做法还绕过了实际启动迁移，无法证明测试用表与运行时迁移后的表一致。
- **严重程度**：P1，关键用户路径验证可能掩盖迁移或 schema 漂移问题。
- **证据**：[后端代码质量复评](../data/eval_reports/2026-08-30-backend-code-quality-reassessment.md)。
- **方案**：新增版本化的空 SQLite schema 基线，其唯一生成来源是生产启动迁移。测试运行时只复制该基线到临时目录，不执行直接 DDL；随后调用启动迁移并校验 schema 未变化，以同时证明当前基线与迁移兼容。基线需要更新时，由显式维护入口重新以生产迁移生成，而非由测试隐式修补。将该公共夹具用于用户路径测试及现有直接建表的 DAO 测试，彻底移除手写测试中的 `CreateTable`/`CREATE TABLE`。
- **实施任务**：
  - 测试资产：提供可审阅、无业务数据的 SQLite schema 基线及显式刷新方式，记录其与生产迁移的对应关系。
  - 测试夹具：复制基线、隔离连接与配置，并在迁移后断言 schema 不漂移；不允许测试以 DDL 补齐表或列。
  - 迁移：迁移新增或变更 schema 时，必须先刷新基线，再运行全部用户路径和 DAO 用例；基线落后时测试应失败并给出明确维护指引。
  - 验证：静态搜索确认手写 Go 测试不含直接建表 DDL；运行受影响用例、全量 Go 测试、`go vet` 与相关 race 检查。
- **验收**：用户路径和 DAO 用例均从真实迁移产出的基线运行；正常测试运行不修改表结构；迁移与基线不一致可自动发现；手写测试不再直接执行建表 DDL。

### BQ11 VLM 队列缺少端到端自动闭环

- **状态**：已规划
- **父任务**：BQ6（依赖 BQ10）。
- **背景**：`TestVlmQueueLifecycle` 只直接调用 `vlmQueueManager` 的启动、停止和待处理状态；VLM 写回在另一段独立测试中验证。测试没有经由 `StartVlmQueue` 或 `runVlmQueue` 使用本地 VLM 响应，因此无法自动证明队列成功、失败、停止后的最终状态和处理履历。
- **严重程度**：P1，VLM 队列关键用户路径仍缺少可重复的自动闭环。
- **证据**：[后端代码质量复评](../data/eval_reports/2026-08-30-backend-code-quality-reassessment.md)。
- **方案**：复用 BQ10 的 schema 基线和临时照片目录，以本地 HTTP VLM 替身替代云端调用，不改变生产 API 或外部协议。测试必须从 `StartVlmQueue` 启动真实 worker，等待其退出后经状态查询和 DAO 读取验证：有效响应写入描述与健康履历；外部失败写入失败履历并计入失败数；停止请求保留在途任务的明确最终结果、不再领取新任务，队列退出并清理运行态。保留轻量管理器单测作为同步原语回归，不再将它作为用户路径证据。
- **实施任务**：
  - 成功/失败闭环：本地 VLM 分别返回有效描述和受控错误，断言启动响应、队列计数、照片描述及处理履历的最终值。
  - 停止闭环：以可控阻塞的本地 VLM 固定在途请求，调用公开停止入口后释放响应，断言没有新照片被领取、队列最终退出且未处理照片保持可重试状态。
  - 隔离与回归：测试结束等待 worker 退出并恢复全局队列、配置和 HTTP 客户端；运行 race 检查，避免异步残留影响其他用例。
- **验收**：无需真实 VLM 或外网即可重复覆盖成功、失败、停止三种队列路径；每种路径均经公开启动/停止入口证明最终队列状态、照片写回和处理履历；并发 race 检查通过。

### CQ4 创作型查询（Compose）专用管线

- **状态**：已规划
- **背景**：「找山西旅游第一天的照片并生成发布文案」这类"选照片 + 做发布内容"的请求，现有四条路由都不匹配：进 `tool` 时自由循环绕路且收敛慢（CQ2 复测），进 `combined` 时 SQL∩RAG 语义错位（23:55 复测）。用户明确期望的确定性流程：SQL 查候选 → 连拍去重 → 交给 LLM 挑选发布照片并生成标题文案；候选过多时逐级收缩，最终引导用户进图文工坊自选。
- **分析**：
  - 分类器对同一问题的分类不稳定（21:23 `tool` / 23:55 `combined`），说明该请求落在现有类别判据的缝隙里，需要独立类别承接。
  - 数据基础已具备：照片表含时间线、拍摄日期、精细/粗略连拍组列；照片列表接口返回连拍封面标记与组内数量；「第一天」可由「该时间线最早拍摄日期」子查询在 SQL 内推导。
  - 图文工坊已支持携带照片的深链入口（单张与连拍组 token），超限兜底不需要新造页面。
  - 会话已有检索粒度概念（photo / fine / coarse），创作型管线的连拍折叠与其语义一致，但由管线自身控制，不依赖会话粒度。
- **方案**：技术方案详见 [2026-08-28-1 创作型查询设计](design/2026-08-28-1-compose-query-design.md)。要点：
  1. 分类器新增第五类「创作型」（判据：用户要求挑选照片并产出发布内容），路由到新增的专用节点；与现有四类判据正交，不改既有分支行为。
  2. 专用节点内为确定性阶段管线：创作导向的 SQL 生成（引导时间线/日期/序数日条件）→ 执行取候选 → 批量取照片详情 → 按连拍组折叠（组以封面为代表，保留组规模信息）。
  3. 逐级收缩，两个可配置阈值（新增 `compose:` 配置段，缺省值在代码侧给出）：折叠后条目数在一级阈值内，带组信息进 LLM；超出则收缩为仅封面条目；超出二级阈值则不硬答，返回"照片过多"说明并附图文工坊深链（候选照片作为预选带入）。
  4. LLM 挑选与创作：输入候选条目（文件名、描述、拍摄时间、连拍信息），输出所选照片、标题与文案；回复以照片卡片呈现选中结果，连拍组条目携带组信息。
  5. 阶段日志沿用 `[前缀] 阶段` 风格，使用 `[compose]`，记录每阶段条目数变化，与 CQ1 诊断约定一致。
  6. 前端仅一处小改动：对话中深链若无法以 markdown 链接完成页内跳转，则在消息中提供进图文工坊的入口。
- **实施任务**：
  - Agent：分类提示词扩展与第五类路由；创作型节点（SQL 生成、连拍折叠、逐级收缩、LLM 挑选创作、超限兜底）。
  - 配置：`compose:` 段两个阈值，模板与用户本地配置补齐。
  - 测试：连拍折叠、两级收缩、超限兜底的单元测试（mock 数据）；分类回归用例。
  - 前端（如需）：对话消息中的图文工坊入口。
  - 验收：（用户）重启服务后重发原始山西请求。
- **验收**：
  - 单元测试覆盖折叠与收缩/兜底分支，全量测试通过。
  - （用户）重发山西请求：回复含第一天照片、标题与文案，无同连拍组重复照片；`logs/agent.log` 呈现 `[compose]` 各阶段日志。
- **（用户）验收操作**：CQ4 实现完成后，重启 Agent 服务，在对话页重发原始山西提问一次。
- **预期结果**：路由到创作型节点；回复包含第一天照片（照片卡片）、标题和文案；日志出现 `[compose]` 阶段记录。
- **最小回传**：回复“CQ4 已验收”，或附上实际回复内容。
- **AI 自动验证**：单元测试覆盖连拍折叠、两级收缩与超限兜底分支，全量测试通过；`[compose]` 各阶段日志行为有测试断言。
- **关单方式**：用户回复确认后，AI 在同一轮直接将任务改为 `Done` 并注明确认日期，不追加核验。

## 产品定位决策

**从**：“个人摄影资产 AI 助手”（泛化，容易堆砌技术）
**到**：「AI 选题助手」，AI 像员工提案，用户像主编审阅。

核心 workflow：拍摄→入库→AI 定期推送选题建议（推荐照片组合 + 发角度）→用户判断选哪个、如何微调→用户自己发布。

**主动不做的事**：

- 不自动发布到社交平台（发送由用户操作）
- 不替代审美判断（AI 推荐，用户决策）
- 不做多模态检索/以图搜图（选题场景不需要）

## 拒绝清单

- 混合检索、RAG 重排序、本地 Embedding、异步后台同步、Prometheus 监控
- proto-first 迁移、语音输入、多语言支持、负样本学习优化
