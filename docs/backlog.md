## 产品定位决策

**从**："个人摄影资产 AI 助手"（泛化，容易堆砌技术）
**到**：「AI 选题助手」，AI 像员工提案，用户像主编审阅。

核心 workflow：拍摄→入库→AI 定期推送选题建议（推荐照片组合 + 发角度）→用户判断选哪个、如何微调→用户自己发布。

**主动不做的事**：

- 不自动发布到社交平台（发送由用户操作）
- 不替代审美判断（AI 推荐，用户决策）
- 不做多模态检索/以图搜图（选题场景不需要）

---

## 拒绝清单（明确砍掉的技术点及其理由）

以下方向已判定为"展示驱动"而非"需求驱动"，明确不做：

- **混合检索**：个人照片库检索准确率够用，混合检索的额外复杂度对选题场景无收益
- **RAG 重排序**：Top-K 精度不足前不做优化。先建评估基线再看是否必要
- **异步后台同步**：300 张照片，启动同步耗时可接受
- **Prometheus 监控**：单机个人工具，出问题看日志足够
- **本地 Embedding 模型**：300 张 Embedding 费用极低，无降本需求
- **proto-first 迁移**：API 数量少，手写维护成本低
- **语音输入**：选题场景无移动端需求
- **多语言支持**：中文用户不需要
- **负样本学习优化 Embedding**：数据量不足以支撑

### 3.11 管线产出简化：每次仅生成 1 个选题

- **状态**：Done
- **背景**：当前一次 `POST /api/suggest/run` 生成 2-4 个选题直觉→2-4 个提案，每个提案被存储为独立的历史记录（共享同一个 trace_id）。这导致：(1) 一次运行产生多条记录，存储和展示维度不统一；(2) 3 张照片足够 LLM 挖掘 1 个好选题，6-9 张采样出 2-4 个直觉的性价比不高；(3) 前端展示时多条记录共享 trace_id，用户容易困惑。用户希望简化：每次随机 3 张照片→1 个直觉→1 个提案→1 条历史记录。
- **方案**：[2026-07-31-2-suggest-pipeline-optimizations.md §7](2026-07-31-2-suggest-pipeline-optimizations.md#7-311管线产出简化)
  - 采样参数：`_STAGE1_SAMPLE_MIN = _STAGE1_SAMPLE_MAX = 3`（固定 3 张）
  - Prompt 调整：系统 prompt 和用户 prompt 改为要求输出 1 个直觉（而非 2-4 个）
  - `run` 端点：将 `for s in suggestions` 循环中的多记录写入改为单记录
  - 手动选题：保持现有行为（用户可自定照片数量）
  - 备选路径：保持现有逻辑（仅在 embedding 不可用时触发，产出量不变）
- **分析**：小体量改动。影响集中在 `suggest.py`（常量 + prompt 调整）和 `server.py`（run 端点简化为单记录写入）。核心逻辑不变，只是参数收窄。前端无需改动（本来就能正确展示单条记录）。
- **验收**：
  - [x] 每次 run 随机采样恰好 3 张照片
  - [x] Stage 1 输出恰好 1 个直觉
  - [x] 最终输出恰好 1 条历史记录（1 个卡片）
  - [x] 手动选题不受影响
  - [x] 备选路径功能不受影响

### B12 手动选题直觉模式下照片被忽略

- **状态**：Done
- **背景**：3.8 评估发现，手动选题流程中，用户在 Step 1 选择了照片、Step 2 填写了直觉后提交，选择的 `photo_ids` 被静默丢弃（因为 `_stage1_generate_intuitions` 在 `intuitions_override` 非空时走 early return，忽略 `photo_ids_override`）。虽然设计文档 2.5 节明确说明此行为（「若提供了直觉，跳过 Stage 1 LLM」），但用户视角是先选照片再填直觉，期望两者都生效。当前交互语义不清晰：用户不知道填了直觉后照片就不会被用到。

### B13 双存储写入冗余

- **状态**：Done
- **背景**：3.8 评估发现，选题历史同时维护 v1（`suggest_history.json`）和 v2（`suggest_history_v2.json`）两份文件，每次写入操作（run / rating / manual-run / rerun）需同步更新两份数据，增加写入复杂度和出错风险。v1 存储为纯兼容层，当前无实际消费者依赖旧格式。
- **方案**：[2026-07-31-2-suggest-pipeline-optimizations.md §2](2026-07-31-2-suggest-pipeline-optimizations.md#2-b13双存储写入冗余)
  - v2 成为唯一数据源，移除所有 v1 写入调用
  - v1 列表接口从 v2 数据动态生成（v2 记录投影为 v1 扁平格式）
  - 合并存储函数（去掉 v2 后缀），锁统一为一个
  - 保留旧 v1 文件不删（方便回退）
- **分析**：中等体量。翻转依赖方向（v1 从独立存储变为 v2 的只读视图），12 处写入点缩减为 5 处（仅 v2）。前端无改动。
- **验收**：
  - [x] GET /api/suggest/history 返回数据一致
  - [x] 五个写入端点功能正常
  - [x] 旧 v1 数据懒迁移正常
  - [x] 无并发写入问题
