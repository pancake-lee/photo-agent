## 产品定位决策

**从**："个人摄影资产 AI 助手"（泛化，容易堆砌技术）
**到**：「AI 选题助手」—— AI 像员工提案，用户像主编审阅。

核心 workflow：拍摄 → 入库 → AI 定期推送选题建议（推荐照片组合 + 发角度）→ 用户判断选哪个、如何微调 → 用户自己发布。

**主动不做的事**：

- 不自动发布到社交平台（发送由用户操作）
- 不替代审美判断（AI 推荐，用户决策）
- 不做多模态检索/以图搜图（选题场景不需要）

---

## 拒绝清单（明确砍掉的技术点及其理由）

以下方向已判定为"展示驱动"而非"需求驱动"，明确不做：

- **混合检索**：个人照片库检索准确率够用，混合检索的额外复杂度对选题场景无收益
- **RAG 重排序**：Top-K 精度不足前不做优化。先建评估基线再看是否必要
- **异步后台同步**：300 张照片，启动同步耗时可接受
- **Prometheus 监控**：单机个人工具，出问题看日志足够
- **本地 Embedding 模型**：300 张 Embedding 费用极低，无降本需求
- **proto-first 迁移**：API 数量少，手写维护成本低
- **语音输入**：选题场景无移动端需求
- **多语言支持**：中文用户不需要
- **负样本学习优化 Embedding**：数据量不足以支撑

### Phase 1 — 让照片「可被多维检索」

**问题**：现在能搜"雪山"，搜不到"蓝调时刻的人像""高对比度的黑白"。缺少结构化的检索维度。

**目标**：建立多维标签体系，让用户按色调/光线/构图/情绪/主体筛选照片，为选题提供素材维度。

#### 1.1 VLM 描述结构化提取

**现状**：VLM 描述是纯文本（`descriptions.json`），Tags 字段空置，无法按维度精确检索。

**做什么**：

- 新建 `extract_attributes.py`：LLM 从 VLM 描述中提取结构化属性
  - 维度：主色/色调、光线类型、构图特点、情绪氛围、主体类型
- 属性存入 `attributes.json`，回写 SQLite（通过 Go 后端 API）
- 向量检索（ChromaDB）仅负责文本描述相似度，不参与元数据过滤

**提升了什么**：

- 从"记得拍过什么"到"发现我还有这类照片"
- 用户能问"帮我找所有逆光人像""有哪些红绿色调的照片"并返回有效结果

**验收**：5 个以上维度可筛选（色/光/构图/情绪/主体），每个维度检索结果合理

#### 1.2 Text-to-SQL 结构化过滤

**现状**：结构化属性（色彩/光线/构图/情绪/主体）存入 SQLite 后，Text-to-SQL 已可查询；ChromaDB 已按[设计决策](../design/chroma-metadata-design.md)精简为仅存 `photo_id` + `chunk_index`，不冗余存储元数据。

**做什么**：

- 确保 Text-to-SQL 的 Schema 描述覆盖 1.1 提取的所有结构化维度
- 用户查询"蓝调时刻的街拍"时，LLM 路由到 Text-to-SQL 过滤 `lighting = 'blue_hour'`，结果与向量检索的语义结果取交集
- 向量检索（ChromaDB）仅负责文本描述相似度，不参与元数据过滤

**提升了什么**：

- 职责边界清晰：向量库只管语义相似度，SQL 只管结构化过滤，Go 是唯一数据源
- 避免 ChromaDB metadata 与 SQLite 数据冗余及同步问题

**验收**：组合查询（色调+光线+语义）返回结果明显精准于纯文本搜索

#### 1.3 黄金查询用例管理（长期任务，Ongoing）

**现状**：黄金查询用例定义在 `agent/chain/evaluation.py` 的 `DEFAULT_EVAL_QUERIES`（当前 7 条），硬编码在代码中，覆盖不足且难以维护。

**目标**：将黄金查询用例从"代码写死"转变为"数据驱动"，提供 Web 管理界面，支持从日常对话中一键保存为黄金用例，逐步积累高质量评估集。

**数据存储**（Agent 层 JSON 文件 `agent/data/golden_queries.json`）：

```json
[
  {
    "id": "uuid",
    "query_text": "...",
    "relevant_photo_ids": ["photo_001"],
    "category": "场景",
    "notes": "",
    "created_at": "2026-06-24T...",
    "updated_at": "2026-06-24T..."
  }
]
```

**Python Agent 新增 API**（挂在已有 FastAPI 服务下，`/api/golden-queries`）：

- `GET    /api/golden-queries` — 列表
- `POST   /api/golden-queries` — 创建（传入 query_text + relevant_photo_ids）
- `DELETE /api/golden-queries/{id}` — 删除

**Web 前端改动**：

1. **对话页（ChatView.vue）**：每条 AI 回复消息旁增加"保存为黄金用例"按钮
   - 点击后自动解析回复中引用的照片 ID，弹出确认框（可编辑查询文本、增删关联照片、填写备注和分类）
2. **新增独立页面"黄金用例管理"**（路由 `#/golden-queries`，放在侧边菜单"图片管理"下方）：
   - 表格列表展示所有用例（查询文本摘要、关联照片数、分类标签、创建时间）
   - 点击行展开查看详情（关联照片缩略图列表）

3. **侧边菜单（SideMenu.vue）**：在"图片管理"分组下新增"黄金用例"菜单项

**Python Agent 适配**：

### Phase 2 — 让照片「可被组合」

**问题**：发一组图时纠结"哪些适合放一起"——按时间还是按主题？怎么组合有故事感？

**目标**：AI 推荐照片组合方案，用户作为主编判断"这个组合好，但换掉第 3 张"。

#### 2.1 相似照片聚类

**做什么**：

- 基于 Chroma 向量库做聚类（HDBSCAN + UMAP）
- 同一聚类内按视觉连贯性排序（颜色/亮度/构图梯度）
- 简单规则：同色调/同场景/同情绪 → 成组
- web中提供新的功能页面“组图发现”
  - 把聚类的入口放到web上，允许用户主动进行一次聚类
    - 我还不知道聚类计算具体需要什么参数，先把可用参数都放到web上，下一版本再来优化交互
  - 聚类结果也展示出来，列表形式，提供标题和图片列表，以及更多算法过程核心参数/数据，以及耗时/创建时间的展示
    - 聚类结果列表只展示图片数量，点击整行可以查看详情，详情中图片列表用“3张预览图+其他文件名”的方式
    - 操作按钮提供详情/删除按钮
    - 整体交互都可以参考黄金用例页面的列表

**提升了什么**：

- AI 推荐"这组 6 张都是蓝调时刻，从远景到特写，适合发一组"
- 用户从"完全靠自己组合"变为"AI 提方案，我调整"

**验收**：输入"海边照片"，AI 返回 3 套不同组合方案，每套有简要说明

#### 2.2 主题标签自动生成

**做什么**：

- 每个聚类用 LLM 生成主题标签（如"云南雪山系列""城市蓝调时刻"）
- 不修改数据库 schema，主题为**动态生成**（运行时聚类）

**提升了什么**：

- 用户不需要手工打标签，AI 自动发现照片库中的主题模式
- 为 Phase 3 的选题生成提供"主题池"

**验收**：300 张照片聚类生成 5~15 个有意义的主题，每个有 1 句描述

### Phase 3 — 让选题「有角度」

**问题**：不知道发什么，经常没灵感就断更。

**目标**：AI 定期扫描照片库，主动推送选题建议，像员工提案一样给"主编"审阅。

**区别于P2**：一句话总结：P2 是把照片按长相分堆并起名（静态快照），
  P3.1是跨时间线发现趋势、缺口、亮点，主动给用户提"选题建议"（动态洞察）。
  P3.1 会复用 P2 的聚类结果作为基础数据，
  但分析层次更高——它关注的不再是"这几张像不像"，
  而是"这些照片能构成什么有价值的故事/系列"。

#### 3.1 潜在主题识别

**做什么**：

- 定期扫描照片库，识别"潜在主题"：
  - 高频出现但未成组发布的场景/色调/题材
  - 结合时间线："你每年春天都拍花，今年还没发"
  - 结合稀缺性："你很少拍夜景，但这几张质量很高"
- CLI 新增 `--suggest` 模式，输出选题建议列表

**提升了什么**：

- 从"我有什么"到"我可以讲什么故事"
- AI 主动推送打破"没灵感"状态

**验收**：运行 `--suggest` 返回 3-5 个选题建议，每个包含推荐照片组合 + 发布角度简述

#### 3.2 多轮对话上下文感知

**做什么**：

- `RouterState` 扩展 `history` 字段
- 支持指代消解："上一组"→ 引用上一轮结果
- 支持条件追加："只要有人物的" → 在当前基础上叠加

**提升了什么**：

- 选题讨论更自然："这个组合太大，帮我精简到 5 张"
- 从"单一查询"升级为"对话式协作"

**验收**：支持 4 类追问（指代/追加/否定/扩展），准确率 ≥ 80%

#### 3.3 摄影报告生成（从 task_3 吸收）

**做什么**：

- 复用 Go 后端 `/api/photos/stats` + Chroma 聚类结果
- 设计报告模板（Markdown）：概览/器材/时间/风格/创作建议
- CLI 新增 `--report [year]` 模式

**提升了什么**：

- 用户可周期性复盘"我这一年拍了什么、风格怎么变的"
- 可演示产品从问答到生成结构化报告的演进

**验收**：输出完整 Markdown 报告，引用具体数据和照片示例

### Phase 4 — 让选题「有策略」

**问题**：发了很多组后，整体账号是什么调性？缺什么类型？长期发展没有方向。

**目标**：基于发布历史分析，提供账号级内容策略建议。

#### 4.1 发布历史分析

**做什么**：

- 新增"已发布"标记机制（用户手动标记哪些照片/组合已发布）
- 统计分析：已发主题分布、频率、时间规律
- 缺口识别："风光 70%、人像 20%、街拍 10%，建议补一组街拍"

**提升了什么**：

- 从"每次发啥"到"整体账号调性如何发展"
- 用户像主编看"季度选题板"

**验收**：可查看发布历史主题分布，AI 建议"下个月的选题方向"

#### 4.2 系列感维护

**做什么**：

- 跨时间线主题提取（LLM 总结同一季节不同年份的共同主题）
- 系列发现："上个月发了'雨天'系列，这个月可以补'晴天的同一场景'对比"

**提升了什么**：

- 账号内容从散装发布到有系列感
- 挖掘"对比/延续/变奏"等更有深度的选题角度

**验收**：AI 能识别并建议"对比系列"（如雨天 vs 晴天、2023 vs 2024 同一地点）

### 工程小改进（穿插推行）
