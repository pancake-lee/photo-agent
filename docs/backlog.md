### AR18 入口分类封闭集，新开放目标静默降级

- **状态**：待规划
- **背景**：入口为一次性 LLM 分类器，输出七类封闭标签（sql / rag / tool / combined / runtime_post / runtime_comparison / runtime_topics），未命中时静默兜底到 `rag`；Runtime 目标空间固定三种（social_post / photo_comparison / topic_discovery）。不属于既有类别的新开放请求（如废片整理、年度报告）会被降级为单步检索或误配目标契约，用户得不到"系统不认识该目标"的信号。注意：这是 V3 设计文档明示的兼容性边界（刻意取舍），但开放目标侧确实没有出口。修正一点：匹配是 LLM 分类而非字面关键词，泛化能力强于规则匹配，问题在结构不在形式。
- **严重程度**：P2，单步请求走封闭类别+兜底是合理设计（V5 也保留）；缺口仅在开放目标侧扩展性与可感知性。
- **归属**：V4/V5 完成后独立评估（2026-09-07 决策）。V4 多轮落地时会被迫触及入口的最小跟进识别切片（跟进消息不走七类分类），该切片归 V4，不改变 AR18 整体延后。
- **证据**：[V0–V3 目标达成回顾](eval/reports/2026-09-07-v0-v3-goal-retrospective.md)。

### OBS2 V5 优化缺少请求级成本、结果关联证据链

- **状态**：Done
- **背景**：当前 Runtime Trace 已记录能力调用、恢复、终态和局部执行信息，聊天请求也有 `trace_id`；但入口分类依据、直接 SQL/RAG/Tool/Combined 路径的结构化执行与终态、端到端耗时、LLM 成本及用户接受/大幅重做结果分散在不同记录中，或根本未被结构化记录。`token_usage` 只能按时间与模型汇总，无法关联 `trace_id`、路由和任务结果；2026-09-07 样本的 15 条 Runtime 汇总成本均为 0，而同日存在 78 次模型调用记录。因而无法可靠计算 V5 所需的 Route Quality、Cost per Successful Task、p50/p95 Latency、User Acceptance/Edit Rate，也不能依据生产轨迹判断某条开放路径是否高频稳定到应沉淀为 Workflow。
- **严重程度**：P2，当前单次 Runtime 故障诊断不受阻；但 V5 的数据驱动优化决策缺少可比较依据。
- **方案**：以现有 `trace_id` 作为唯一关联键，在一次聊天请求内记录入口分类原始结果、最终执行结构、技术终态、端到端耗时、LLM 输入/输出 Token 与成本；将汇总同时写入 Trace 和助手消息。为助手结果增加可选的有帮助/需改进反馈，反馈与原消息、Trace、路由和用量关联。Trace 回放保留聊天层关键事件，并将有效查询窗口扩展为可支持趋势分析的周期。
- **分析**：不引入外部监控平台或新的 Agent 编排。运行时 LLM 调用经工厂统一附加请求级用量回调，避免只覆盖 Runtime 或只覆盖部分直接路径；用户反馈是显式可选事件，技术终态不替代用户接受。
- **验收**：
  - [x] 一次 SQL、RAG、Tool、Combined 或 Runtime 请求均可在同一 `trace_id` 下看到路由决策与执行汇总。
  - [x] 执行汇总含执行结构、技术终态、端到端耗时、输入/输出 Token 与成本。
  - [x] 助手消息持久化请求用量，用户可提交有帮助或需改进反馈，反馈能关联原 Trace。
  - [x] Trace 回放包含聊天层事件；自动化测试覆盖请求用量、汇总事件和反馈关联。
- **评估**：8.4（Runtime 轨迹可复盘性 9.0、全路径执行可观测性 8.5、成本与延迟可归因性 8.5、结果与用户反馈可判定性 8.0、长期趋势可用性 8.0），详见 [闭环评估报告](eval/reports/2026-09-07-obs2-request-evidence-loop.md)。
- **实施与验证**：请求级用量回调经 LLM 工厂统一注入，入口和收尾事件写入同一 Trace，助手消息保存用量并可记录显式反馈；Trace 有效回放窗口为 30 天。Agent 离线全量 402/402、Web Vitest 14/14 与生产构建通过，未调用真实 LLM 或修改真实数据。
- **证据**：[初始评估](eval/reports/2026-09-07-v5-observability-readiness.md)、[闭环评估](eval/reports/2026-09-07-obs2-request-evidence-loop.md)。

### BQ3 未鉴权服务暴露任意 SQL 查询

- **状态**：暂缓
- **背景**：默认服务全局调用 `SetIgnoreAuth`，同时注册了接收调用方 SQL 文本的 QueryService。当前服务监听全部网络接口；虽使用只读数据库连接，调用方仍可读取任意可访问表和元数据。
- **严重程度**：P0，未授权数据访问风险。
- **证据**：[后端代码质量基线评估](eval/reports/2026-08-29-backend-code-quality-baseline.md)。
- **方案**：当前开发阶段保留 `SetIgnoreAuth` 与自由只读 SQL 查询，不改变接口、监听方式或开发调试效率。将风险、启动条件和后续收敛方向迁入 FR-11；当服务需要被非受信任网络、多人或真实用户访问时，必须先恢复鉴权并收紧查询能力，再继续发布。
- **验收**：FR-11 可独立追溯本决策及后续启动条件；BQ3 不进入当前开发队列。

## 产品定位决策

**从**：“个人摄影资产 AI 助手”（泛化，容易堆砌技术）
**到**：「AI 选题助手」，AI 像员工提案，用户像主编审阅。

核心 workflow：拍摄→入库→AI 定期推送选题建议（推荐照片组合 + 发角度）→用户判断选哪个、如何微调→用户自己发布。

**主动不做的事**：

- 不自动发布到社交平台（发送由用户操作）
- 不替代审美判断（AI 推荐，用户决策）
- 不做多模态检索/以图搜图（选题场景不需要）

- proto-first 迁移、语音输入、多语言支持、负样本学习优化
