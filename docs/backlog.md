## 产品定位决策

**从**："个人摄影资产 AI 助手"（泛化，容易堆砌技术）
**到**：「AI 选题助手」，AI 像员工提案，用户像主编审阅。

核心 workflow：拍摄→入库→AI 定期推送选题建议（推荐照片组合 + 发角度）→用户判断选哪个、如何微调→用户自己发布。

**主动不做的事**：

- 不自动发布到社交平台（发送由用户操作）
- 不替代审美判断（AI 推荐，用户决策）
- 不做多模态检索/以图搜图（选题场景不需要）

---

## 拒绝清单（明确砍掉的技术点及其理由）

以下方向已判定为"展示驱动"而非"需求驱动"，明确不做：

- **混合检索**：个人照片库检索准确率够用，混合检索的额外复杂度对选题场景无收益
- **RAG 重排序**：Top-K 精度不足前不做优化。先建评估基线再看是否必要
- **异步后台同步**：300 张照片，启动同步耗时可接受
- **Prometheus 监控**：单机个人工具，出问题看日志足够
- **本地 Embedding 模型**：300 张 Embedding 费用极低，无降本需求
- **proto-first 迁移**：API 数量少，手写维护成本低
- **语音输入**：选题场景无移动端需求
- **多语言支持**：中文用户不需要
- **负样本学习优化 Embedding**：数据量不足以支撑

### W5 配置模板 StorageRoot 分叉

- **状态**：Done
- **背景**：`configs/config.yaml` 模板中 `Storage.PhotoSrc` 为 `./data/photos/src`，而新增的 `Storage.StorageRoot` 为 `./data/photos_src`。上传落盘走 `PhotoSrc`，`storage/info` 扫描走 `StorageRoot`，两者指向不同目录。当前用户实际 `.local/pancake.yaml` 里两者同为 `/root/share/photo-agent/pic-like/` 才未暴露，若按模板部署会导致「总文件数」与「本次新增」对不上。

- **分析**：PhotoSrc 本就是「照片按月/活动组织」的源文件根目录，StorageRoot 与之语义重复；分叉源于模板只更新了 PhotoSrc 未同步 StorageRoot。
- **验收**：
  - [x] storage/info 扫描目录与上传落盘目录一致（都走 PhotoSrc）

### W7 NEF EXIF 读取策略前后端不一致

- **状态**：Done
- **背景**：客户端 `client/sync.go` 为避免 goexif 对 NEF 卡死，跳过 NEF 的 EXIF 读取（注释明确）。但服务端 `createPhotoRecord` 对 NEF 仍调用 `getExifInfo`（内部 `exif.Decode`）。若 goexif 真会卡死某些 NEF，服务端上传时同样会卡死；当前 113 个 NEF 未触发，属潜在风险。
- **方案**：保留服务端入库时读 NEF EXIF 的现状（实测 113 个 NEF 均成功、无卡死），仅修正客户端注释里「防 goexif 卡死」的误导理由，改为说明服务端已读、客户端无需重复读。客户端行为不变。
- **分析**：实测 113 个 NEF 的 shot_at 均成功提取，说明 goexif 对当前 NEF 安全；客户端跳过本身合理（服务端会读），但注释理由不成立，易误导后续维护者。
- **验收**：
  - [x] 客户端注释理由修正，前后端对「谁读 NEF EXIF」的说明一致

### W9 上传阶段无进度反馈

- **状态**：Done
- **背景**：步骤 3 上传大量文件（本次实测 259 个，含约 16MB 的 NEF）时仅按钮 loading 转圈，无逐文件/百分比进度。长等待下用户难以判断是否卡死，只能等最终结果。
- **方案**：客户端上传循环中每完成一个文件向前端推送一次进度事件（Wails 事件机制），前端监听并展示「已完成 X/N」进度条，同步完成后替换为现有结果统计。
- **分析**：同步是客户端阻塞调用，前端 await 期间拿不到中间态，需靠 Wails 事件异步推送进度。改动跨客户端 Go（事件推送）与前端（监听 + 进度条 UI）。
- **验收**：
  - [x] 上传过程有可感知的进度反馈（已完成 X/N）
  - [x] 同步完成后进度条替换为成功/失败/耗时统计

### W10 上传无重试机制

- **状态**：Done
- **评估**：三轮 8.4（正确性 9 健壮性 8 简洁性 9），详见 [三轮报告](../data/eval_reports/eval-import-workflow-v3-2026-08-18.json)。单测锚定重试成功/耗尽两路径，Hijacker 断连还原真实网络抖动。
- **背景**：客户端 `uploadOneFile` 无重试，网络抖动导致单文件 failed 后需用户手动重新同步。skip 模式可跳过已上传文件、部分缓解，但非真正重试。
- **方案**：从简处理：单文件上传失败后自动重试 1 次（共 2 次尝试），重试前固定等待 2 秒，不做指数退避、不区分错误类型，重试仍失败才计入失败列表。前端同步完成提示按结果区分：全部成功 success 提示；有失败 warning 提示「可再次点击开始同步重试」，手动重试走既有 skip 流程（已传文件自动跳过），结果统计整体刷新。同步完成后自动刷新一次 storage/info，更新服务器总文件数等展示。
- **分析**：重试深度 1 次覆盖瞬时网络抖动即可，用户手动「开始同步」+ skip 模式天然构成第二层重试（只传失败文件），无需复杂退避策略。收尾刷新 storage/info 让「上次同步时间」与本次上传对齐。
- **验收**：
  - [x] 单文件失败自动重试 1 次，重试成功不计入失败
  - [x] 重试仍失败计入失败列表，前端有「手动重试」提示
  - [x] 同步完成后 storage/info 展示自动刷新
  - [ ] 实机验证（需 Windows 图形环境）

### W11 上传完成后无清空中转收尾

- **状态**：Done
- **评估**：三轮 8.4（准确性 9 完整性 9 一致性 9 交互体验 9），详见 [三轮报告](../data/eval_reports/eval-import-workflow-v3-2026-08-18.json)。文案与三目录真实语义对齐，恪守「仅复制不删除」原则。
- **背景**：设计原文（第三步）有「确认后清空中转目录（full/like/nef）或归档」意图，当前 UI 上传完成后无此收尾步骤，闭环靠用户自觉。
- **方案**：程序不删除任何用户文件，只在上传完成后展示「收尾建议」文本区块。提示只指向本次导入的归档子目录 `full/like/nef/<归档名>/`（无活动时为日期文件夹），不涉及中转根目录整体。按目录区分：like/ 全部同步成功后提示可安全删除，有失败时提示先重试；nef/ 在收藏 NEF 已迁移且 like 全部同步后提示可删（留存/废弃 NEF 未上传，需自行确认）；full/ 的留存照片不上传服务器，提示确认设备仍保留后再删。
- **分析**：原设计的「清空中转目录」若由程序执行会违背 W3 确立的「仅复制不删除」原则（删除交还用户），改为文本建议既补全设计闭环意图又避免误删风险。限定归档子目录是因为中转根目录下可能有其他活动的归档目录，整体删除会误伤。
- **验收**：
  - [x] 上传完成后展示收尾建议区块，程序不删除任何文件
  - [x] 提示路径限定为本次归档子目录（full/like/nef/<归档名>/）
  - [x] 三目录提示文案按同步结果区分
  - [ ] 实机验证（需 Windows 图形环境）
