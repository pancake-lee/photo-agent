# 评估模式新增「用户价值」维度

> 日期：2026-07-27
> 关联：[[2026-07-26-harness-design#Harness 评估模式的修正/优化]]

## 问题

B1 评估中，功能效果维度「准确性」得了 9/10。评分依据是：

- API 返回了合法的 JSON 结构
- 数据库属性填充率 99.7%
- 每条建议包含标题/角度/理由/照片 ID

但从用户视角看，这些建议的质量其实很低：

- 5 条建议全部是把同一场景下连续拍摄的多张相似照片组成合集，配上标题和描述
- 没有跨场景、跨时间的非显性关联（如"同一座城市在不同季节的色彩变化"）
- 这种"按场景分组 + 起标题"的事，用户每次拍完照自己就会做，不需要 AI

**根因**：评估模式的 7 个维度全部是内部/技术视角（代码写得好不好、输出格式对不对），没有一个维度问"这个输出对用户有没有价值？"

## 方案

### 新增维度类别：用户价值

在现有「代码质量」「功能效果」之外，增加第三类维度「用户价值」。四个子维度：

- **惊喜度 (Insight / Surprise)**：输出是否揭示了用户自己不会发现的关联？用户看到结果会不会觉得"这个角度我没想到"？反面信号：输出只是对已有聚类/分组的重新标签化，没有跨越场景/时间/主题的意外连接。证据来源：人工审视输出内容，判断每个建议的"意外程度"
- **可用性 (Actionability)**：用户能否直接基于输出采取行动（如一键发布）？还是需要大量二次加工？反面信号：建议过于泛化（如"静谧时光集"可以套在任何一组安静照片上），缺乏具体可执行的叙事角度。证据来源：审视建议的标题和 angle 字段，判断是否具体、可操作
- **交互体验 (Interaction Experience)**：操作流程是否顺畅？等待时间是否可接受？状态反馈是否及时清晰？结果呈现是否易于扫读和理解？反面信号：点击后长时间无反馈、结果密集堆砌无信息层级、异常状态无引导。证据来源：实际操作功能流程，记录等待时间、加载状态、结果布局
- **AI 增量 (AI Value-Add)** — 可选维度：仅适用于依赖 AI/LLM 的功能。纯规则/逻辑实现的功能（如排序、过滤、文件管理）不评此维度。评分要点：这个输出需要 AI 才能产生吗？还是一个简单脚本就能得到同等质量的结果？反面信号：建议的来源只是对频率统计结果的 LLM 润色，AI 没有做任何"发现"层面的智能工作。证据来源：理解功能的内部实现逻辑，判断 AI 在哪个环节真正增加了价值

### 新增评估步骤：理解产品定义

在现有流程的「确认评估目标」之前，增加一个前置步骤：

1. 读取功能的 PRD 定义（`docs/prd.md` 对应章节）、设计方案（`docs/design/`）、或 backlog 条目中的背景描述
2. 提炼出功能对用户的承诺：它解决什么用户问题？提供什么价值？
3. 如果 PRD 中缺少该功能的定义，在评估报告的 `findings_for_backlog` 中记录

这个步骤是用户价值评分的基准。没有产品定义，评估器就无法判断"这个输出有没有达成产品承诺"。

### 用户价值维度的适用范围

- **必须评估（惊喜度 + 可用性 + 交互体验）**：面向终端用户的功能（如 suggest、聚类、对话检索），用户价值是核心评估目标
- **AI 增量仅在含 AI/LLM 的功能上评估**：纯规则/逻辑实现的功能（排序、过滤、文件管理等）标注 N/A
- **基础设施/工程改进**（如 AutoSync 性能优化、日志轮转）：用户价值维度整体可跳过，标注 N/A 并说明原因

## 决策理由

- **不合并到现有「功能效果」中**：功能效果衡量的是"输出是否符合规格"（格式正确、覆盖完整、风格一致），用户价值衡量的是"输出是否解决用户问题"。两者正交：一个功能可以功能效果满分但用户价值零分（B1 就是例子）
- **惊喜度放在第一位**：对于 AI 创意类功能（如 suggest），"发现意外关联"是核心产品承诺。如果惊喜度低，即使其他维度高，功能也没有达到目的
- **AI 增量降为可选维度**：纯规则/逻辑实现的功能不存在"AI 增量"的概念，强制评估会制造无意义的低分。仅在功能确实依赖 AI/LLM 时才启用
