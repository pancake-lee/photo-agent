# AI 资产实时状态设计

> 状态：已实现，待 Web 验收。
> 专题中枢：[AI 照片资产质量闭环中枢](2026-08-26-4-ai-asset-quality-loop-hub.md)。

## 1. 需求校正

AI 描述质量校验和向量一致性检查都足够轻量，应在用户打开详情、照片列表或批量审查时实时执行并得到当前结论。照片库不保存 VLM、Embedding 或整体健康的“状态/原因/是否已校验”结果，也不由这些历史字段阻断操作。

## 2. 设计目标

- 所有用户可见状态都由当前描述、当前向量内容和当前处理进度实时推导，不依赖 SQLite 历史状态。
- 正常照片即使数据库残留旧状态，也不显示警告、不被批量操作错误列出或阻断。
- 描述或向量真正异常时，详情、缩略图、批量审查、Embedding 队列和检索在同一次检查中得到一致结论。
- 不删除既有数据库列，代码层面停止将其作为状态来源或继续写入，避免破坏现有用户数据。

## 3. 当前方案

### 3.1 描述质量

Go 在提供照片数据、批量 VLM 审查和 Embedding 准入前，对当前描述运行同一套本地规则。结果仅用于本次响应或任务判断，不写回数据库。

### 3.2 向量状态

Agent 直接查询当前 Chroma 向量：检查照片是否有向量，并校验该向量记录对应当前描述版本。向量记录携带其输入描述的版本标识，作为向量本身的来源信息，而非 SQLite 中独立的健康状态。

照片详情、缩略图、批量 Embedding 审查和检索准入均使用这项实时向量检查。批量审查一次获取全库结果，避免逐张网络往返。

### 3.3 处理进度与失败反馈

队列运行中的进度继续由内存队列实时提供。单次调用失败可在当前操作中显示，但不形成会在后续页面中继续冒充当前状态的照片健康字段。

## 4. 用户体验

- 打开 `DSC_0051.jpg` 时，若当前 Chroma 已存在与当前描述一致的向量，直接显示可用；若没有或版本不一致，才显示重建入口。
- 批量 Embedding 审查只列出当前描述可信、且当前 Chroma 缺失/版本不一致的照片。
- “重新校验”不再作为恢复历史状态的步骤；刷新详情或审查即可获得当前结论。

## 5. 验收标准

- 清空或修改 SQLite 旧健康字段不改变任一照片的实时展示、批量候选或检索准入。
- `DSC_0051.jpg` 与 `DSC_0054.jpg` 的结果仅由当前描述和当前 Chroma 向量决定，不再受历史 `stale` 影响。
- 向量被删除、或描述重新生成后，详情与批量 Embedding 审查立即判为需重建；重建完成后立即恢复正常。
- 当前描述命中质量规则时，即使旧向量仍在 Chroma，也不允许 Embedding 或检索使用。
- 审查过程不调用 VLM，不改写照片质量状态。

## 6. 实现状态

- ✅ Go 仅即时推导当前描述质量，不再迁移、读取或回写照片健康状态。
- ✅ Agent 为新向量记录输入描述版本，并以当前 Chroma 内容实时筛选队列与批量审查候选。
- ✅ 照片列表将当前描述提交给 Agent 检查向量，照片详情直接读取当前 Chroma 信息。
- ✅ 检索只接受当前描述通过质量规则且版本一致的向量。
- ⏳ （用户）重启 Go 后端、Python Agent 和前端后，验证 `DSC_0051.jpg`、`DSC_0054.jpg` 的详情与批量 Embedding 审查不再受 SQLite 历史字段影响。
