# Harness 工作模式设计：三角色 + 项目管理

> 状态：进行中，持续更新
> 日期：2026-07-26

## 一、交互流程：你只需要做一件事

假设你现在发现产品有个问题——"搜蓝调时刻的街拍，结果里雪山照片排在了街拍前面"。

### 现在的做法

```
你说："这里排序有问题，查一下 combined_query 的排序逻辑"
AI 读代码 → 分析 → 告诉你原因
你说："改一下，让语义相似度权重更高"
AI 改代码 → 你验证 → 结束
```

整个过程依赖你**自己判断该查哪个模块、自己决定怎么修**。AI 只是一个听话的打字员。

### Harness 模式下的做法

```
你说："评估：组合查询结果排序不准确，搜「蓝调时刻的街拍」，雪山照片排在了街拍前面"
             │
             ▼
     ┌─── AI 自动执行以下步骤 ───────────────────────────────────────┐
     │                                                                │
     │  1. 识别「评估」关键词 → 进入评估模式                           │
     │  2. 读 docs/backlog.md → 了解当前需求池和评估状态                    │
     │  3. 把你说的话结构化记录为 backlog 条目                │
     │  4. 分析：这不是 bug，是效果问题 → 需要调整方案，不只是改代码     │
     │  5. 读 docs/design/chroma-metadata-design.md → 找到排序逻辑      │
     │  6. 判断：方案本身没问题，是权重参数的默认值不合理                │
     │  7. 给出分析结论和建议 → 等你确认（或直接修改，如果你授权了）     │
     │                                                                │
     └────────────────────────────────────────────────────────────────┘

你确认："改"

             │
             ▼
     ┌─── AI 继续 ───────────────────────────────────────────────────┐
     │                                                                │
     │  8. 修改权重参数                                               │
     │  9. 自检（跑黄金用例 / 重新查询验证）                           │
     │  10. 验证通过 → 更新 backlog 条目状态为「Done」               │
     │  11. 反馈归档到 docs/archive/                             │
     │  12. 无需额外操作（backlog 条目状态即状态）                                   │
     │                                                                │
     └────────────────────────────────────────────────────────────────┘
```

你只需要做两件事：**说一句话描述问题**，然后**确认 AI 的分析**。

你不用管哪个模块、什么原因、怎么修、修完怎么验证。这些由工作流驱动。

### 如果问题更复杂（涉及方案变更）

假设问题是"Text-to-SQL 生成的 WHERE 条件总是漏掉 mood 维度"。

AI 分析后发现这是方案层面的问题：当前 Prompt 对多维度组合查询的描述不够明确，需要调整 Text-to-SQL 的 System Prompt 设计。

这时 AI 的路由是：

```
评估器（记录问题）
    │
    ▼
规划器（修改 text_to_sql 的设计方案）
    │
    ▼
生成器（按新方案改代码）
    │
    ▼
评估器（验证修复效果 → 关闭反馈）
```

还是那句话：你只需要描述问题，确认分析结论。方案调整和代码修改由 AI 自己完成。

## 二、背后的机制：三角色 + 文档通信

### 2.1 三角色的分工

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│   规划器      │    │   生成器      │    │   评估器      │
│   Planner    │    │  Generator   │    │  Evaluator   │
├──────────────┤    ├──────────────┤    ├──────────────┤
│ 做什么：       │    │ 做什么：       │    │ 做什么：       │
│ 把需求变成     │    │ 按方案写代码   │    │ 接收产品缺陷   │
│ 可执行的方案   │    │ 自检/测试     │    │ 和效果反馈     │
│              │    │              │    │ 分析问题类型   │
│ 产出：         │    │ 产出：         │    │ 路由到对应角色 │
│ design/*.md  │    │ 代码变更      │    │ 验证修复效果   │
│ plans/*.md   │    │              │    │              │
├──────────────┤    ├──────────────┤    ├──────────────┤
│ 读什么：       │    │ 读什么：       │    │ 读什么：       │
│ backlog.md   │    │ design/*.md  │    │ backlog.md  │
│ prd.md       │    │ plans/*.md   │    │ backlog.md  │
│ tech.md      │    │ CLAUDE.md    │    │ design/*.md   │
│ note.md      │    │              │    │              │
├──────────────┤    ├──────────────┤    ├──────────────┤
│ 写什么：       │    │ 写什么：       │    │ 写什么：       │
│ design/*.md  │    │ 代码文件      │    │ backlog.md  │
│ plans/*.md   │    │              │    │ docs/archive │
│ backlog.md   │    │              │    │ backlog.md  │
│ (更新状态)    │    │              │    │              │
└──────────────┘    └──────────────┘    └──────────────┘
```

三角色不是三个 Agent 进程。它们是**三个交互模式**，每个模式定义了一套"读什么文档 → 做什么事 → 写什么文档"的规则。目前三个模式都由你的一句话触发，AI 执行。

### 2.2 角色间如何通信：文件

参考 Anthropic 文章的做法——"一个代理写入文件，另一个代理读取并响应"。

```
评估器发现效果问题
    │
    │  写入 docs/backlog.md:
    │  "F-003: Text-to-SQL 漏掉 mood 维度, 类型=效果问题, 状态=待分析"
    │
    ▼
规划器读取 backlog.md
    │
    │  发现 F-003 状态为"待分析"且类型为"效果问题"
    │  → 读取相关设计文档
    │  → 分析根因
    │  → 更新反馈条目: "分析结论=Prompt 对多维度组合描述的引导不足"
    │  → 更新设计文档 docs/design/xxx-text-to-sql-design.md
    │  → 更新反馈条目: "状态=待修复"
    │
    ▼
生成器读取 backlog.md
    │
    │  发现 F-003 状态为"待修复"
    │  → 读取更新后的设计文档
    │  → 修改 Prompt 代码
    │  → 更新反馈条目: "状态=待验证"
    │
    ▼
评估器验证
    │
    │  重新跑查询 → mood 维度正确出现
    │  → 更新反馈条目: "状态=已关闭"
    │  → 归档
    │
    ▼
  闭环
```

**文件就是通信协议**。角色不直接调用另一个角色，而是通过读写文件来传递信息和状态。这样每个角色可以独立触发（人或 Agent），不需要同时在线。

### 2.3 角色触发方式：人 vs Agent

同一个规划器，两种触发方式：

- **入口**：人工 — 你说"帮我规划 Phase 3.2" / Agent — 扫描 backlog，找到状态「待规划」的条目
- **Triage**：人工 — 你选了条目，隐含完成了 triage / Agent — 按优先级和依赖关系选条目
- **方案设计**：人工 — AI 输出方案，你审核 / Agent — AI 输出方案，AI 按 CLAUDE.md 规范自审
- **执行计划**：人工 — 你判断是否要拆 exec plan / Agent — AI 按复杂度规则自动判断
- **文档产物**：相同

**文档结构不变，变的只是触发器**。这正是你笔记里说的思路：前期人工触发每个节点保证方向不偏，等某环节稳定后就逐步交给 Agent 自主。

### 2.4 路由规则：评估器如何决定下一步

```
用户输入反馈
      │
      ▼
┌─ 问题类型判断 ─────────────────────────────┐
│                                            │
│  缺陷（功能不符合预期）                       │
│    → 生成器直接修复                          │
│    → 不涉及方案变更                          │
│                                            │
│  效果问题（功能能跑但输出不够好）               │
│    → 规划器分析是否需要调整方案                │
│    → 如果是参数/阈值问题 → 生成器直接调        │
│    → 如果是方案层面问题 → 规划器改方案 → 生成器 │
│                                            │
│  体验问题（交互流程不顺畅）                     │
│    → 规划器调整 UI/交互方案 → 生成器          │
│                                            │
│  需求变更（用户改变了对功能的期望）              │
│    → 更新 backlog → 规划器 → 生成器           │
│                                            │
└────────────────────────────────────────────┘
```

### 2.5 项目管理模式：第四维度

三角色面向**产品开发**（需求→方案→代码→验证），项目管理面向**版本生命周期**（规划迭代→治理 backlog→归档版本）。

两者的关系：项目管理为三角色提供"什么时候该做什么"的节拍。一次版本归档后，backlog 中剩余条目就是下一轮三角色闭环的输入。

```
项目管理模式
    │
    │  触发场景：版本归档、里程碑规划、backlog 治理
    │
    ├── 做什么：
    │    ├── 版本归档：将 Done 条目从 backlog 迁至 archive/，标记版本号
    │    ├── 里程碑规划：梳理剩余 backlog，排定下一版本范围
    │    └── backlog 治理：清理过时条目，补充遗漏，调整优先级
    │
    ├── 读什么：backlog.md、archive/
    │
    ├── 写什么：archive/vX.Y.Z-*.md、backlog.md（精简+更新决策历史）
    │
    └── 触发词：版本归档 / 归档 / 里程碑 / 版本规划 / 迭代计划
```

项目管理任务类型记录在下方 3.4 节，随实践逐步扩充。

## 三、支撑文档：零新增

交互流程和角色协作不需要新建文档。利用现有的 `docs/backlog.md` 统一承载需求规划与反馈追踪。

### 3.1 backlog.md：统一的需求+反馈池

`docs/backlog.md` 是项目统一的需求+反馈池，包含状态流转（待规划→规划中→已规划→WIP→Done）和详细的条目说明。反馈条目与功能需求以同一套格式记录，区别仅在于"阶段"列标记为"缺陷修复"。角色通过更新条目的状态字段来交接工作：

- **评估器**发现/接收问题 → 在 backlog 中新增条目（状态=待规划，或直接标记为待修复）
- **规划器**扫描 backlog → 找到待规划的条目 → 分析产出方案 → 更新状态为"已规划"
- **生成器**读取已规划条目 → 按方案实现 → 更新状态为"WIP"→"Done"
- **评估器**验证 Done 条目 → 确认修复有效 → 条目保持 Done（后续版本归档时迁至 archive/）

### 3.2 eval/baseline.md：基线指标参考

`docs/eval/baseline.md` 记录 P@10 / R@10 / MRR 等指标的当前值和趋势。评估器验证修复效果时参考基线判断是否退化。

### 3.3 项目管理相关

当前已识别的项目管理任务类型：

- **版本归档**：将 backlog 中 Done 条目迁至 `docs/archive/vX.Y.Z-completed-backlog.md`，精简 backlog 至仅剩未完成条目，更新决策历史。
- **里程碑规划**（待实践）：梳理剩余 backlog，评估优先级和依赖关系，排定下一版本范围。
- **backlog 治理**（待实践）：交叉比对 backlog.md 和实际代码，识别过时/遗漏条目，给出清理建议。

## 四、从人工到自主的渐进路径

文档和角色就位后，不是一次性切换到全自主模式。按以下步骤渐进：

### 第一步：先在人工触发下跑通一次闭环

找一个真实的、小的问题（比如已经发现但还没修的缺陷），完整走一遍：

```
你说"评估：XXX 有问题"
    → AI 记录到 backlog.md，分析原因，给出建议
你确认
    → AI 修复代码，自检，更新条目状态为 Done，归档
```

这一步验证的是：**交互入口是否顺畅，backlog 条目的状态流转是否够用**。

### 第二步：跑通一次涉及方案调整的闭环

找一个效果问题（不是简单 bug），比如"Text-to-SQL 的查询准确率不够高"：

```
你说"评估：XXX 效果不好"
    → AI 记录，分析后发现需要调整方案
    → AI 修改设计文档
你确认方案
    → AI 按新方案改代码，自检
    → AI 更新反馈状态，归档
```

这一步验证的是：**评估器 → 规划器 → 生成器的串联是否顺畅**。

### 第三步：积累 3-5 轮后，放开生成器

生成器是最容易自主化的角色（按方案写代码，编译+测试自检）。在跑了几轮后，你对 AI 的执行质量有了判断，可以把生成器的"停靠点"去掉——AI 按方案执行后直接提交结果，不再每步等你确认。

### 第四步：放开评估器

评估器可以在每次生成器完成工作后自动触发：跑黄金用例、检查是否有明显退化、自动记录结果到 baseline.md。只在指标退化超过阈值时才暂停等你介入。

### 第五步：放开规划器

规划器自主扫描 backlog，找到下一个「待规划」条目，自动产出方案。你只需要审核方案（因为方案涉及方向判断，这一步的停靠点可能长期保留）。

### 最终态

```
Agent 自主循环：
  扫描 backlog → 规划 → 执行 → 评估 → 发现新方向 → 写回 backlog → 循环
  
人介入点：
  - 方案审核（方向性判断）
  - schema/API 破坏性变更
  - 随时说"停，这个方向不对"
```

### 二、落地与设计的一致性确认

落地过程中，以下几个点初看像是设计偏差，实际上是设计意图的正确体现：

**文件通信是明确的架构选择，不是临时妥协。**

设计文档 2.2 节明确写道”文件就是通信协议”。在落地中，角色切换的实际流程是：用户 `/clear` 清空上下文 → 输入新关键词触发另一个角色 → AI 读文件（backlog、design）获取上一环节的产出 → 继续工作。这不是”单 Agent 内给自己看的状态记录”，而是文件作为交接协议的完整实践。即使将来多个 Agent 进程自主运行，它们之间仍然通过读写同一套文件来完成交接。文件是唯一的通信媒介，这个原则不会因为触发方式（人工 vs 自动）而改变。

**三角色定义在 `docs/handbook/work-modes.md` 中，与设计文档 2.1 节一致。**

设计文档 2.1 节已经写明：”三角色不是三个 Agent 进程。它们是三个交互模式，每个模式定义了一套'读什么文档 → 做什么事 → 写什么文档'的规则。”CLAUDE.md 仅保留触发词表 + 简短描述，完整流程在 `docs/handbook/work-modes.md`。2026-07-27 文档重组时将工作模式详情、编码规范、文档审阅规范从 CLAUDE.md 拆分至 `docs/handbook/` 目录，CLAUDE.md 精简为 ~100 行的全局规则 + 文档索引。

**角色间通过文件交接的价值。**

保留文件作为通信方式的核心原因：当需要回顾”AI 输出了什么方案、做了什么实现”时，文件是阅读入口。对话记录会消失，但 backlog.md 的状态流转、design/*.md 的方案内容、eval/baseline.md 的指标变化，这些文件构成了可追溯、可审查的完整记录。

### 四、对话记录策略

**结论：不需要记录每次对话。**

理由三层：

1. **harness 的设计哲学已经给了答案**：文件就是通信协议，也是评估入口。backlog 的状态流转是对话过程的压缩摘要，design 文档的内容变更是方案决策的记录。对话记录的价值在于调试 harness 本身，而非评估产品代码质量。
2. **Git 提交 + 结构化文件足以覆盖三个角色的评估**：
   - Generator 输出质量 → git diff + 测试结果

## 2026-08-21 评估报告双格式规范

### 问题

评估报告此前只有 JSON 单一载体，同一份内容要同时满足机器解析与人工阅读：strengths/weaknesses 等大段自然语言占据 JSON 主要篇幅，程序解析用不上；人工复盘读 JSON 的成本又很高。

### 规范：按读者拆分双格式

- **JSON**：面向程序化处理（通过判定、基线更新、趋势追踪），只保留结构化可计算字段
- **Markdown**：面向人工阅读（复盘、代码审查参考），完整保留描述性内容
- 两个文件同目录（`data/eval_reports/`）同名：`eval-xxx.json` + `eval-xxx.md`

**JSON 保留**：

- `report_id` / `backlog_id` / `created_at` / `target`：元数据，索引与追溯
- `overall` + `dimension_scores`（维度名 → 分数）：核心结构化数据，用于趋势线与基线刷新
- `per_task`：多任务报告的每任务评分
- `findings_for_backlog`：可直接导入 backlog 的结构化问题条目
- `verification_runtime` / `verification_commits`：关键验证标识（短字符串，不展开证据链）

**JSON 去掉（移入 Markdown）**：各维度 `strengths` / `weaknesses`、`summary`、完整证据链描述

精简后 JSON 示例：

```json
{
  "report_id": "2026-08-21-photo-list-lb-series",
  "backlog_id": "LB1-LB6",
  "created_at": "2026-08-21T23:30:00+08:00",
  "target": "LB 系列整体评估",
  "overall": 8.1,
  "per_task": { "LB1": 8.3, "LB2": 7.9 },
  "dimension_scores": { "正确性": 8.5, "健壮性": 7.5 },
  "findings_for_backlog": ["问题描述，可直接导入 backlog"],
  "verification_runtime": ["go test PASS", "Playwright 导航跳转实测"],
  "verification_commits": { "LB1": "f19b2e4" }
}
```

**Markdown 结构**：摘要（总分 + 通过结论 + 一句话总结）→ 分维度评分（得分 + 得分点/失分点，完整保留 strengths/weaknesses）→ per_task 评分与简评 → 执行证据（运行时验证、commits 完整证据链）→ 下一步建议（由 findings 提炼方向）

### 工作流

1. 评估器一次产出两个文件（同目录同名，仅扩展名不同）
2. JSON 供程序判断是否通过、自动更新基线、生成趋势
3. Markdown 供人工审阅与复盘；回顾旧报告时阅读成本远低于 JSON

### 存量迁移

规范确立后，`data/eval_reports/` 下已有的单 JSON 报告需补齐精简 JSON + 拆出 Markdown。分两批执行：先迁移 2 份供用户确认格式，再迁移全部。
