# Future Requirements

> 临时记录未来可能要做但当前不急于启动完整设计的需求点。
> 当项目进展到合适阶段时，从中选取条目，走完整的 规划→生成→评估 流程。
>
> 来源：backlog.md 任务审阅（2026-08-22），基于 v1.0.10 归档后的代码现状重新评估。

## FR-1 评估体系扩展

- **来源**：backlog 1.4
- **原始背景**：当前评估仅覆盖 RAG 检索（Precision@K / Recall@K / MRR）和聚类主题质量（启发式规则），需探索更多 use case 并建立对应评估方法。
- **现状审视**：项目已有成熟的人工评估框架（eval-guide.md + 双格式报告），但自动化评估仍只覆盖两条路径。SQL 路由、Tool 调用、Combined 查询、多轮对话均无自动化评估。需要的是为这些路径设计黄金用例集和对应指标。
- **备注**：优先级取决于路由路径的稳定程度，可在 SQL/Tool 路径不再大改后再建集。

## FR-2 多轮对话上下文感知

- **来源**：backlog 3.2
- **原始背景**：选题讨论需要更自然的对话体验，当前每次查询独立，不支持指代上一轮结果或叠加条件。
- **现状审视**：基础设施已就位（SessionStore 持久化消息历史、会话恢复），但 PhotoAgent.route() 仍是单轮处理——每条消息独立分类、独立路由，不将历史消息传入 LLM。需要的是在路由和 LLM 调用中注入上下文，支持指代消解（"上一组"→引用上一轮结果）、条件追加（"只要有人物的"→叠加）、否定和扩展。
- **备注**：基础设施已有，核心工作在路由层和 prompt 层的上下文注入设计。

## FR-3 摄影报告生成

- **来源**：backlog 3.3
- **原始背景**：用户需周期性复盘"我这一年拍了什么、风格怎么变的"。
- **现状审视**：Go 后端已有 `/api/photos/stats`（品牌/镜头/焦距/GPS/月度/小时统计），Python 端有 Chroma 聚类结果，但无叙事性报告生成。需要的是将这些数据源组合为结构化 Markdown 报告（概览/器材/时间/风格/创作建议），引用具体数据和照片示例。
- **备注**：数据基础已具备，核心工作在报告模板设计和 LLM 叙事生成。

## FR-4 发布历史分析

- **来源**：backlog 4.1
- **原始背景**：用户标记"已发布"后，统计分析已发主题分布、频率、时间规律，识别缺口，让用户像主编看"季度选题板"。
- **现状审视**：项目中完全没有发布跟踪功能。无数据模型、无 API、无 UI。选题系统（suggest）只负责发现主题，不跟踪哪些主题被实际采用。这是 Phase 4"让选题有策略"的基础设施。
- **备注**：依赖产品层面确定"发布"的标记方式（手动标记 vs 选题采纳自动标记）。

---

## FR-5 系列感维护

- **来源**：backlog 4.2
- **原始背景**：跨时间线主题提取，发现"对比/延续/变奏"系列，让账号内容从散装发布到有系列感。
- **现状审视**：完全没有系列检测功能。当前主题发现（suggest）每次独立运行，不感知历史选题记录之间的关联。需要的是在选题历史之上建立跨次关联分析——例如"去年3月拍了花，今年3月要不要继续"、"上次发了雨天，下次可以配一组晴天同场景对比"。
- **备注**：依赖 FR-4（发布历史）提供数据基础，或至少依赖选题历史的积累。可考虑在 suggest 管线中增加"历史感知"步骤。

## FR-6 时间线规律维度重新设计

- **来源**：backlog B2
- **原始背景**：原三维度分析路径中时间线规律维度始终返回 0 个候选（shot_at 覆盖率问题）。该维度已随三维度分析代码一并删除。
- **现状审视**：核心需求仍有效——发现用户在不同年份同一时段的拍摄习惯（如每年3月拍花），主动提醒"今年要不要继续拍一组"。当前时间线系统已重建（timeline_events 表、散片分组、重算接口），shot_at 覆盖率因 EXIF 缺失兜底机制有所改善，但无高层时间规律分析。需要以当前三阶段管线架构重新设计实现方式。
- **备注**：与 FR-5（系列感维护）有交叉——时间规律可作为系列检测的一个输入维度。

## 图片管理的卡片大小

提供一个滑块，提供的是预设的多个卡片大小等级，一行1/2/3/5/8/12共6个预设的大小。
但是还要根据当前页面宽度做兜底限制，比如网页被拉伸缩放到1080宽的纵向放置的1080分辨率屏幕，
再去掉左菜单右导航以及边缘距离等，实际展示空间可能只有700（根据代码获取实际值计算），
这是显然没必要使用一行12个图片这种尺寸，所以应该为我考虑一个卡片尺寸的兜底限制，
计算后超过限制的等级，滑块操作不做限制，但大小无需调整，功能不生效。

## FR-7 详情面板读写模式区分

- **来源**：图文工坊 PS5 评估讨论
- **原始背景**：当前图片详情组件同时服务于图片管理和图文工坊。两处都需要查看原图、EXIF、AI 描述和 Embedding，但未来可能需要区分“查看详情”和“编辑详情”的使用场景。
- **现状审视**：当前图文工坊仅隐藏 VLM/Embed 处理入口，详情面板仍沿用共享组件中的部分元数据编辑能力。这个差异暂不作为当前缺陷处理，也不改变现有交互。
- **未来方向**：后续明确详情面板的读写模式边界，按调用场景控制拍摄时间等元数据是否可编辑，并保持查看、处理、编辑权限之间的界面反馈一致。
- **备注**：启动前需先确认哪些字段允许编辑、编辑后的保存责任归属，以及图片管理与图文工坊是否需要不同的默认模式。

## FR-8 草稿字段清空能力

- **来源**：图文工坊 PS1 评估讨论
- **原始背景**：当前草稿更新会保留空字符串字段对应的既有值，因此不支持把已填写的标题、正文等内容清空。
- **现状审视**：用户当前只需要修改后保存，现有行为满足使用需求，不构成缺陷。
- **未来方向**：若后续出现清空草稿字段的明确场景，再决定是否提供完整字段覆盖或独立清空操作。
- **优先级**：低。

---

## FR-9 图文工坊提示词默认内容策略

- **来源**：图文工坊 PS6 评估讨论
- **原始背景**：提示词模式当前预填一段通用行程要求；PS6 的系统提示词已承载通用平台约束。
- **现状审视**：预填文案能给用户提供起步参考，也会占用输入框。当前不影响生成正确性或核心使用流程。
- **未来方向**：以后结合实际使用反馈，再决定保留预填范例、改为仅 placeholder，或提供可选模板。
- **优先级**：低。
