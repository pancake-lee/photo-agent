# Harness 工作模式设计：三角色闭环

> 状态：进行中，持续更新
> 日期：2026-07-26

## 一、交互流程：你只需要做一件事

假设你现在发现产品有个问题——"搜蓝调时刻的街拍，结果里雪山照片排在了街拍前面"。

### 现在的做法

```
你说："这里排序有问题，查一下 combined_query 的排序逻辑"
AI 读代码 → 分析 → 告诉你原因
你说："改一下，让语义相似度权重更高"
AI 改代码 → 你验证 → 结束
```

整个过程依赖你**自己判断该查哪个模块、自己决定怎么修**。AI 只是一个听话的打字员。

### Harness 模式下的做法

```
你说："评估：组合查询结果排序不准确，搜「蓝调时刻的街拍」，雪山照片排在了街拍前面"
             │
             ▼
     ┌─── AI 自动执行以下步骤 ───────────────────────────────────────┐
     │                                                                │
     │  1. 识别「评估」关键词 → 进入评估模式                           │
     │  2. 读 docs/eval/INDEX.md → 了解当前评估状态                    │
     │  3. 把你说的话结构化记录到 docs/eval/feedback.md                │
     │  4. 分析：这不是 bug，是效果问题 → 需要调整方案，不只是改代码     │
     │  5. 读 docs/design/chroma-metadata-design.md → 找到排序逻辑      │
     │  6. 判断：方案本身没问题，是权重参数的默认值不合理                │
     │  7. 给出分析结论和建议 → 等你确认（或直接修改，如果你授权了）     │
     │                                                                │
     └────────────────────────────────────────────────────────────────┘

你确认："改"

             │
             ▼
     ┌─── AI 继续 ───────────────────────────────────────────────────┐
     │                                                                │
     │  8. 修改权重参数                                               │
     │  9. 自检（跑黄金用例 / 重新查询验证）                           │
     │  10. 验证通过 → 更新 feedback.md 状态为「已关闭」               │
     │  11. 反馈归档到 docs/eval/archive/                             │
     │  12. 更新 INDEX.md 的状态摘要                                   │
     │                                                                │
     └────────────────────────────────────────────────────────────────┘
```

你只需要做两件事：**说一句话描述问题**，然后**确认 AI 的分析**。

你不用管哪个模块、什么原因、怎么修、修完怎么验证。这些由工作流驱动。

### 如果问题更复杂（涉及方案变更）

假设问题是"Text-to-SQL 生成的 WHERE 条件总是漏掉 mood 维度"。

AI 分析后发现这是方案层面的问题：当前 Prompt 对多维度组合查询的描述不够明确，需要调整 Text-to-SQL 的 System Prompt 设计。

这时 AI 的路由是：

```
评估器（记录问题）
    │
    ▼
规划器（修改 text_to_sql 的设计方案）
    │
    ▼
生成器（按新方案改代码）
    │
    ▼
评估器（验证修复效果 → 关闭反馈）
```

还是那句话：你只需要描述问题，确认分析结论。方案调整和代码修改由 AI 自己完成。

## 二、背后的机制：三角色 + 文档通信

### 2.1 三角色的分工

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│   规划器      │    │   生成器      │    │   评估器      │
│   Planner    │    │  Generator   │    │  Evaluator   │
├──────────────┤    ├──────────────┤    ├──────────────┤
│ 做什么：       │    │ 做什么：       │    │ 做什么：       │
│ 把需求变成     │    │ 按方案写代码   │    │ 接收产品缺陷   │
│ 可执行的方案   │    │ 自检/测试     │    │ 和效果反馈     │
│              │    │              │    │ 分析问题类型   │
│ 产出：         │    │ 产出：         │    │ 路由到对应角色 │
│ design/*.md  │    │ 代码变更      │    │ 验证修复效果   │
│ plans/*.md   │    │              │    │              │
├──────────────┤    ├──────────────┤    ├──────────────┤
│ 读什么：       │    │ 读什么：       │    │ 读什么：       │
│ backlog.md   │    │ design/*.md  │    │ eval/INDEX   │
│ prd.md       │    │ plans/*.md   │    │ eval/feedback│
│ tech.md      │    │ CLAUDE.md    │    │ design/*.md   │
│ note.md      │    │              │    │              │
├──────────────┤    ├──────────────┤    ├──────────────┤
│ 写什么：       │    │ 写什么：       │    │ 写什么：       │
│ design/*.md  │    │ 代码文件      │    │ eval/feedback│
│ plans/*.md   │    │              │    │ eval/archive │
│ backlog.md   │    │              │    │ eval/INDEX   │
│ (更新状态)    │    │              │    │              │
└──────────────┘    └──────────────┘    └──────────────┘
```

三角色不是三个 Agent 进程。它们是**三个交互模式**，每个模式定义了一套"读什么文档 → 做什么事 → 写什么文档"的规则。目前三个模式都由你的一句话触发，AI 执行。

### 2.2 角色间如何通信：文件

参考 Anthropic 文章的做法——"一个代理写入文件，另一个代理读取并响应"。

```
评估器发现效果问题
    │
    │  写入 docs/eval/feedback.md:
    │  "F-003: Text-to-SQL 漏掉 mood 维度, 类型=效果问题, 状态=待分析"
    │
    ▼
规划器读取 feedback.md
    │
    │  发现 F-003 状态为"待分析"且类型为"效果问题"
    │  → 读取相关设计文档
    │  → 分析根因
    │  → 更新反馈条目: "分析结论=Prompt 对多维度组合描述的引导不足"
    │  → 更新设计文档 docs/design/xxx-text-to-sql-design.md
    │  → 更新反馈条目: "状态=待修复"
    │
    ▼
生成器读取 feedback.md
    │
    │  发现 F-003 状态为"待修复"
    │  → 读取更新后的设计文档
    │  → 修改 Prompt 代码
    │  → 更新反馈条目: "状态=待验证"
    │
    ▼
评估器验证
    │
    │  重新跑查询 → mood 维度正确出现
    │  → 更新反馈条目: "状态=已关闭"
    │  → 归档
    │
    ▼
  闭环
```

**文件就是通信协议**。角色不直接调用另一个角色，而是通过读写文件来传递信息和状态。这样每个角色可以独立触发（人或 Agent），不需要同时在线。

### 2.3 角色触发方式：人 vs Agent

同一个规划器，两种触发方式：

|          | 人工触发                      | Agent 触发                                   |
| -------- | ----------------------------- | -------------------------------------------- |
| 入口     | 你说"帮我规划 Phase 3.2"      | Agent 扫描 backlog，找到状态「待规划」的条目 |
| Triage   | 你选了条目，隐含完成了 triage | Agent 按优先级和依赖关系选条目               |
| 方案设计 | AI 输出方案，你审核           | AI 输出方案，AI 按 CLAUDE.md 规范自审        |
| 执行计划 | 你判断是否要拆 exec plan      | AI 按复杂度规则自动判断                      |
| 文档产物 | 相同                          | 相同                                         |

**文档结构不变，变的只是触发器**。这正是你笔记里说的思路：前期人工触发每个节点保证方向不偏，等某环节稳定后就逐步交给 Agent 自主。

### 2.4 路由规则：评估器如何决定下一步

```
用户输入反馈
      │
      ▼
┌─ 问题类型判断 ─────────────────────────────┐
│                                            │
│  缺陷（功能不符合预期）                       │
│    → 生成器直接修复                          │
│    → 不涉及方案变更                          │
│                                            │
│  效果问题（功能能跑但输出不够好）               │
│    → 规划器分析是否需要调整方案                │
│    → 如果是参数/阈值问题 → 生成器直接调        │
│    → 如果是方案层面问题 → 规划器改方案 → 生成器 │
│                                            │
│  体验问题（交互流程不顺畅）                     │
│    → 规划器调整 UI/交互方案 → 生成器          │
│                                            │
│  需求变更（用户改变了对功能的期望）              │
│    → 更新 backlog → 规划器 → 生成器           │
│                                            │
└────────────────────────────────────────────┘
```

## 三、支撑文档：最少新增

交互流程和角色协作不需要复杂的文档体系。只需要**三个新增文件**和**两处现有文档修改**。

### 3.1 新增文件（3 个）

#### `docs/eval/feedback.md` — 反馈收件箱

唯一真正"工作"的文件。每条反馈是一个带状态的条目，角色通过更新条目状态来交接工作。

```markdown
# 反馈列表

## F-003: Text-to-SQL 漏掉 mood 维度

- **类型**：效果问题
- **发现时间**：2026-07-26
- **描述**：查询"暖色调的人像"，SQL 只用了 color_tone 条件，漏掉了 mood 维度
- **期望**：多维度组合查询时，所有相关维度都应出现在 WHERE 中
- **关联文档**：[[docs/design/xxx-text-to-sql-design]]
- **状态**：待修复
- **分析结论**：System Prompt 对多维度组合的描述不够明确，LLM 倾向只用一个维度
- **解决方案**：（修复后回填）

---

## F-002: 组合查询排序不准确

- **类型**：效果问题 → **已关闭**
- **发现时间**：2026-07-25
- **描述**：...
- **关闭时间**：2026-07-26
```

#### `docs/eval/INDEX.md` — AI 入口路标

AI 进入评估模式时先读这个。控制在一屏以内（约 30 行），只包含：当前摘要、活跃反馈索引、使用说明。

#### `docs/eval/baseline.md` — 基线指标

从 `agent/chain/evaluation.py` 的 `DEFAULT_EVAL_QUERIES` 迁移，记录 P@10 / R@10 / MRR 等指标的当前值和趋势。评估器验证修复效果时可以参考基线判断是否退化。

### 3.2 修改现有文件（2 处）

#### `CLAUDE.md` — 新增三个模式的触发规则

```markdown
## 评估模式

触发词：评估 / 我发现问题 / 这里不够好 / 效果不对 / 有个 bug

流程：
1. 读 docs/eval/INDEX.md
2. 结构化记录到 docs/eval/feedback.md
3. 分析问题类型，给出路由建议
4. 等你确认后执行

## 规划模式

触发词：规划一下 / 帮我设计 / 出个方案 / 怎么做

流程：
1. 确认规划对象（backlog 条目或口述需求）
2. 读 backlog + prd + tech 获取上下文
3. 输出方案到 docs/design/
4. 复杂任务拆 exec plan 到 docs/plans/
5. 更新 backlog 规划状态

## 生成模式

触发词：按方案执行 / 开始开发 / 实现这个

流程：
1. 确认执行对象（方案文档或 exec plan 子阶段）
2. 按方案逐步实现
3. 每步编译+测试自检
```

#### `docs/backlog.md` — 扩展状态枚举值

在原有状态（Done/Pending/WIP/Ongoing/Rejected/Abandoned）基础上扩充，让状态列覆盖完整生命周期：`待规划` → `规划中` → `已规划` → `WIP` → `Done`。不新增列，Agent 扫描状态为「待规划」的条目即可知道下一个该规划什么。

### 3.3 不需要新增的

- **不需要独立的 `docs/plans/` 目录**：复杂任务的 exec plan 可以直接写在设计文档的"实现步骤"章节里。除非执行计划本身复杂到需要独立管理，才拆出单独文件。前期先不建这个目录，遇到第一个真正需要拆 exec plan 的任务时再建。
- **不需要评估器独立的大套文档**：`feedback.md` 做收件箱，`INDEX.md` 做入口，`baseline.md` 做参考基线。三个文件就够了。
- **不需要改 `docs/design/` 的格式**：现有设计文档已经是规划器的产出，保持不动。

## 四、从人工到自主的渐进路径

文档和角色就位后，不是一次性切换到全自主模式。按以下步骤渐进：

### 第一步：先在人工触发下跑通一次闭环

找一个真实的、小的问题（比如已经发现但还没修的缺陷），完整走一遍：

```
你说"评估：XXX 有问题"
    → AI 记录到 feedback.md，分析原因，给出建议
你确认
    → AI 修复代码，自检，更新反馈状态，归档
```

这一步验证的是：**交互入口是否顺畅，feedback.md 的条目格式是否够用**。

### 第二步：跑通一次涉及方案调整的闭环

找一个效果问题（不是简单 bug），比如"Text-to-SQL 的查询准确率不够高"：

```
你说"评估：XXX 效果不好"
    → AI 记录，分析后发现需要调整方案
    → AI 修改设计文档
你确认方案
    → AI 按新方案改代码，自检
    → AI 更新反馈状态，归档
```

这一步验证的是：**评估器 → 规划器 → 生成器的串联是否顺畅**。

### 第三步：积累 3-5 轮后，放开生成器

生成器是最容易自主化的角色（按方案写代码，编译+测试自检）。在跑了几轮后，你对 AI 的执行质量有了判断，可以把生成器的"停靠点"去掉——AI 按方案执行后直接提交结果，不再每步等你确认。

### 第四步：放开评估器

评估器可以在每次生成器完成工作后自动触发：跑黄金用例、检查是否有明显退化、自动记录结果到 baseline.md。只在指标退化超过阈值时才暂停等你介入。

### 第五步：放开规划器

规划器自主扫描 backlog，找到下一个「待规划」条目，自动产出方案。你只需要审核方案（因为方案涉及方向判断，这一步的停靠点可能长期保留）。

### 最终态

```
Agent 自主循环：
  扫描 backlog → 规划 → 执行 → 评估 → 发现新方向 → 写回 backlog → 循环
  
人介入点：
  - 方案审核（方向性判断）
  - schema/API 破坏性变更
  - 随时说"停，这个方向不对"
```
