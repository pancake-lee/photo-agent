# 聚类结果详情页 UI 优化设计

> 状态：已实现（2026-07-26 第三轮优化，含布局整合 + 报告存储改造）
> 关联：backlog 2.2（聚类标题生成效果差）、评估系统设计（2026-07-26-eval-system-design.md）

## 一、问题描述

当前聚类结果详情弹窗存在两个体验问题：

1. **评估结果与簇卡片分离**：评估结果展示在弹窗底部独立区域，用户需要在簇卡片和底部评估结果之间来回对照，无法直观看到每个簇的标题质量
2. **缺少批量操作入口**：只有单个"评估标题"按钮，没有批量生成主题、批量评估的能力，处理多个簇时操作繁琐
3. **评估报告持久化过度**：每次评估生成独立 JSON 文件存储，但页面刷新后不重新加载，文件无实际复用价值，浪费磁盘空间

## 二、方案设计

### 2.1 整体布局：两区结构

弹窗内分为两个区域：

**区域一（列表外）：汇总信息 + 批量操作入口**

- 保留现有统计指标卡片（簇数/已聚类/噪声/总计/耗时/聚类率）+ 参数标签
- 新增评估汇总条：评估通过率概览 + 跨簇规则（diverse_labels）结果
- 批量操作按钮从 header-extra 移至汇总区域，作为独立的"工具栏"行

**区域二（列表内）：每个簇卡片自包含全部信息**

- 每个簇卡片内部展示：标题、主题描述、照片、元信息（照片数、凝聚度）
- 评估数据关联到对应簇卡片内展示，不再在底部单独列出
- 每个卡片内有独立的「重新评估」入口

### 2.2 弹窗尺寸调整

当前宽度 800px 在加入评估内嵌展示后偏窄。弹窗宽度调整为 900px，簇卡片内部采用更清晰的区块分隔。

### 2.3 汇总信息区设计

工具栏与 6 个统计指标卡片放在同一行：左侧为统计卡片，右侧为评估汇总 + 操作按钮，中间自然隔开。

```
┌──────────────────────────────────────────────────────────────┐
│  [6 个指标卡片]                    标题通过  ┌──────┐       │
│                                    14/20    │重新生成│       │
│                                             ├──────┤       │
│                                             │重新评估│       │
│                                             └──────┘       │
│  参数：min_cluster_size=5  umap_n_neighbors=15  ...          │
└──────────────────────────────────────────────────────────────┘
```

工具栏说明：

- 与统计指标卡片同一行，靠右对齐，`justify-content: space-between` 自然隔开
- 评估通过率汇总：复用 `detail-metric` 样式（大数值 + 小标签），标签文字为"标题通过"。**始终显示**，无评估数据时显示 `0/0`
- 两个按钮上下堆叠摆放（`flex-direction: column`）：
  - 「重新生成」（primary 风格）：批量重新生成所有簇的主题
  - 「重新评估」（warning 风格）：批量重新执行启发式规则检查
- 跨簇规则失败警告：显示在右侧区域最左边（评估汇总之前），仅在有失败时出现

### 2.4 单个簇卡片设计

每个簇卡片按从上到下的信息层级重组：

```
┌──────────────────────────────────────────────────────────────┐
│  🏷 阳光下的街拍瞬间                                         │
│     城市街道的自然光拍摄，人物与建筑的光影对比...             │
│                                                              │
│  [标题校验 1/4 通过] [12 张] [凝聚度 87%] [展开全部]         │
│  [生成标题] [评估标题]                                       │
│                                                              │
│  ┌ 评估详情 ───────────────────────────────────────────────┐ │
│  │ [错误] 标题长度：4 字，期望 6-16 字                     │ │
│  │ [警告] 描述不足：5 字，期望 ≥10 字                      │ │
│  └─────────────────────────────────────────────────────────┘ │
│                                                              │
│  [照片缩略图...]                                             │
└──────────────────────────────────────────────────────────────┘
```

簇卡片各区块说明：

- **标题区**：cluster label + theme_description，保持现有样式
- **标签/操作栏**：
  - 「标题校验 X/Y 通过」tag：有评估数据时显示，位于照片数 tag 之前。配色：全部通过用 success，有失败用 warning
  - 照片数 tag、凝聚度 tag、展开/收起按钮（同现有）
  - 「生成标题」按钮：始终为此文案，不随是否已有标题而变化
  - 「评估标题」按钮：始终为此文案，放在「生成标题」后面。当 label 为空字符串时失灰禁点
- **评估详情区**（仅当有未通过条目时才显示）：
  - 不再显示通过状态行（已移至标签栏）
  - 列出所有未通过条目：每条含 severity tag（错误/警告）+ 规则描述
  - 不包含「评估标题」按钮（已移至标签/操作栏）
- **照片区**：PhotoThumbList，保持现有逻辑

### 2.5 批量操作二次确认弹窗

点击「重新生成」或「重新评估」后弹出确认对话框，结构统一：

```
┌─────────────────────────────────────────────┐
│  确认批量生成主题                       [X] │
├─────────────────────────────────────────────┤
│                                             │
│  将为聚类结果批量生成主题描述。              │
│  共 N 个聚类簇。                            │
│                                             │
│  处理范围：                                 │
│  ● 全部处理 — 对所有 N 个聚类执行          │
│  ○ 仅处理含错误的结果 — 对 M 个当前评估    │
│     含错误的聚类执行                        │
│                                             │
│  ⚠️ 尚未评估，无法筛选含错误的结果。        │  ← 仅在无评估数据时显示
│                                             │
├─────────────────────────────────────────────┤
│                      [取消]  [确认生成]     │
└─────────────────────────────────────────────┘
```

交互规则：

- 「全部处理」始终可选，显示当前簇总数
- 「仅处理含错误的结果」仅在已有评估数据且存在含错误的簇时可操作，否则置灰并显示提示文案
- 两个选项为 radio 单选，默认选中「全部处理」
- 点击「取消」或右上角 X 关闭弹窗不执行操作
- 点击「确认生成/确认评估」执行操作，弹窗关闭，对应按钮进入 loading 状态

### 2.6 单个簇操作按钮

每个簇卡片头部有两个操作按钮：

- **「生成标题」**（在"展开全部"按钮之后）：始终为此文案，不随是否已有标题而变化。调用单簇主题生成 API
- **「评估标题」**（在「生成标题」之后）：始终为此文案。当 cluster label 为空字符串时按钮失灰禁点。仅对该簇执行单簇启发式规则检查（调用 API 3.3），不执行跨簇规则
- 执行期间对应按钮 loading，完成后更新卡片状态

注意：单簇评估不包含跨簇规则（diverse_labels），跨簇规则只在批量「重新评估」时执行。

## 三、API 变更

### 3.1 批量生成主题（新增）

```
POST /api/cluster/results/{result_id}/generate-all-themes
Body: { "cluster_ids": [1, 2, 3] | null }
```

- `cluster_ids` 为 null 或不传时，生成所有簇的主题
- `cluster_ids` 为数组时，仅生成指定簇的主题
- 返回完整的 ClusterResultDetail（与 GET detail 结构一致）

### 3.2 批量评估扩展（修改已有）

```
POST /api/cluster/results/{result_id}/evaluate-themes
Body: { "cluster_ids": [1, 2, 3] | null }  ← 新增可选参数
```

- `cluster_ids` 为 null 或不传时，评估所有簇（保持向后兼容）
- `cluster_ids` 为数组时，仅评估指定簇，且跳过跨簇规则（diverse_labels）
- 响应结构不变

### 3.3 单簇评估（新增）

```
POST /api/cluster/results/{result_id}/clusters/{cluster_id}/evaluate-theme
```

- 对该簇的 label 和 theme_description 执行单簇启发式规则
- 不执行跨簇规则
- 返回该簇的评估结果：`{ cluster_id, checks: [...], passed, failed }`

### 3.4 评估报告按簇分组（可选优化）

在 `evaluate-themes` 响应中增加 `cluster_results` 字段：

```json
{
  "heuristic": { ... },
  "cluster_results": [
    { "cluster_id": 1, "passed": 3, "failed": 1, "failures": [...] },
    { "cluster_id": 2, "passed": 4, "failed": 0, "failures": [] }
  ]
}
```

此字段可由前端自行分组计算得到（当前 failures 已含 cluster_id），视实现复杂度决定是否在 API 层预计算。优先由前端计算，避免不必要后端改动。

## 五、关键决策

### 5.1 评估结果展示位置

**决策**：每个簇卡片的标题评估结果展示在该卡片内部，作为卡片的一个独立区块。不再保留弹窗底部的全局评估结果列表。

**理由**：用户评估单个簇的标题质量时，需要同时看到标题文本、照片内容、评估反馈。三者放在同一个卡片内，视线不需要频繁跳转。

### 5.2 跨簇规则的展示

**决策**：跨簇规则（diverse_labels）的检查结果展示在汇总信息区的工具栏行中，不在任何簇卡片内显示。

**理由**：跨簇规则描述的是簇间关系，不属于任何一个簇。放在汇总区最自然。

### 5.3 确认弹窗 vs 直接执行

**决策**：批量「重新生成」和「重新评估」使用二次确认弹窗，单簇操作（生成标题、评估标题）不弹确认。

**理由**：批量操作影响范围大且有不可逆副作用（覆盖已有生成结果、触发 LLM 调用），需要二次确认。单簇操作影响范围明确，用户意图清晰。

### 5.4 批量操作执行方式

**决策**：全部处理时后端一次批量执行（调用 3.1/3.2 的 batch API），前端等待完成后统一刷新。仅处理含错误时前端传入筛选后的 cluster_ids 列表。

**理由**：批量 API 可以在后端做并发控制、错误聚合，比前端逐个调用更可靠。前端界面只需一个 loading 状态。

### 5.5 评估数据不持久保留在 detailItem 中

**决策**：`evalReport` 保持独立的 ref，不合并到 `detailItem` 中。簇评估状态通过 `clusterEvalMap`（computed）从 `evalReport` 派生。

**理由**：评估报告是独立实体（有独立存储和 API），与聚类结果详情是两种数据。分离维护避免数据一致性问题和类型污染。

### 5.6 评估报告存储：按天追加 JSONL

**决策**：评估报告不再每次生成独立 JSON 文件（`data/eval_reports/<uuid>.json`），改为以 JSONL 行追加到 `data/traces/YYYY-MM-DD.jsonl`，与其他 trace 事件统一管理。

**理由**：
- 评估是快速规则检查，页面刷新后不需要重新加载历史报告。独立文件无复用价值
- 按天合并到 trace 文件，减少小文件碎片，与已有的 LLM 调用 trace 统一存储和清理策略
- `list_reports` / `load_report` API 仍保留，改为从每日 JSONL 文件流式扫描

### 5.7 评估汇总始终可见

**决策**：工具栏中"标题通过 X/Y"汇总始终展示，无评估数据时显示 `0/0`。

**理由**：让用户明确知道当前评估状态为空（而非功能缺失），引导用户执行评估操作。
