# BQ6 剩余关键用户路径闭环

> 专题中枢：[后端代码质量治理](2026-08-30-1-backend-code-quality-hub.md)。
>
> 本文档补充 BQ6 的 BQ10、BQ11 实施方向；具体任务拆分、依赖和验收以 [backlog BQ6–BQ11](../backlog.md) 为准。

## 1. 背景与目标

复评已确认草稿 HTTP、上传/删除、VLM 描述写回和 Embedding 异常路径具备自动证据，但其共同测试夹具自行创建 schema，且 VLM 队列没有从公开启动入口到 worker 最终状态的证据。

本轮目标是在不访问真实 VLM 或外网的条件下，让关键用户路径运行在可证明与生产迁移一致的 schema 上，并补齐 VLM 队列的真实处理闭环。

## 2. 设计

### 2.1 迁移兼容的测试起点

- 维护一个不含业务数据、由生产启动迁移生成的 SQLite schema 基线，作为关键用户路径与 DAO 测试的共同起点。
- 每个测试复制独立基线，避免互相污染；正常测试不通过 DDL 补表或补列。
- 启动迁移在基线上必须保持 schema 不变。发现变化时，测试明确失败，要求通过受控维护流程更新基线，防止测试夹具悄悄掩盖 schema 漂移。

这样，测试覆盖的是与运行时相同的迁移结果，而非 GORM 模型或手写 SQL 的局部近似。

### 2.2 VLM 队列闭环

- 本地 VLM 替身提供成功、受控失败及可阻塞响应，不改生产 API 协议，也不依赖云端配置。
- 测试从公开队列启动入口进入真实 worker；完成后通过队列状态、照片记录和处理履历共同判断结果。
- 停止场景遵守既有语义：在途处理获得明确结果，尚未领取的照片不继续处理，之后可再次进入队列。

## 3. 验证流程

1. 复制迁移产出的 schema 基线，完成迁移兼容检查。
2. 运行既有草稿、上传/删除与 Embedding 自动用例，确认基线切换未改变其行为。
3. 启动本地 VLM 驱动的真实队列，分别完成成功、失败和停止用例。
4. 运行全量测试、静态检查和受影响包 race 检查；以结果更新 BQ6 复评。

## 4. 关键决策

- **选择版本化 schema 基线，而不是测试时建表**：既满足“测试不修改表结构”的约定，也使用户路径直接依赖生产迁移的实际结果。
- **选择本地 HTTP 替身，而不是只替换队列管理器**：公开入口、并发 worker、VLM 响应处理和持久化写回必须在同一条自动路径内被证明。
- **BQ10 优先于 BQ11**：队列闭环的数据库断言依赖可信测试 schema；先固定契约，才能避免新证据建立在错误夹具上。

## 5. 验收标准

- 关键用户路径与 DAO 测试不含直接建表 DDL，且可自动发现迁移与 schema 基线不一致。
- VLM 队列的成功、失败和停止路径均从公开入口执行，并可重复断言最终队列、照片与履历状态。
- BQ6 所有既有和新增用例在同一验证轮次通过，复评不再因 BQ10 或 BQ11 扣分。
