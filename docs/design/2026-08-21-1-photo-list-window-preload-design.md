# 照片列表滑动窗口预加载设计文档

> 状态：第一轮已生成（2026-08-21，编译/单测/build 自检通过，滚动基础功能验收通过）；第二轮已生成（2026-08-21，LB4/LB5/LB6 全部完成，见第 9 节，运行时验证项待用户执行）
> 关联：[2026-08-20-1-photo-list-segmented-browse-design.md](2026-08-20-1-photo-list-segmented-browse-design.md)（LB1 分段浏览，本文在其基础上修订跳转策略并新增窗口预加载）
> 本文是本轮四个 bug 修复 + 滑动窗口预加载方向的统合方案，并作为「照片列表浏览」专题的滚动载体文档。

## 1. 需求背景

LB1 分段浏览已生成，但实际使用暴露出四个问题，同时用户提出了一个新的浏览体验方向。

**四个 bug：**

1. **导航点击后上下无法滚动**：点击右侧月份后，列表被锁定为筛选重置式跳转（设置 shotAt 起止/timeline 重新拉取），无法继续向上/向下滚动加载相邻月份。导航本应只是定位跳转，不应影响持续的加载。
2. **分割线完全不可见**：分割线组件已写，但被网格渲染丢弃，屏幕上一条都看不到。
3. **整个网页会滚动**：在照片列表空白处滚动会带动整个页面框架滚动，滚到渲染区域外露出空白。滚动本应只在照片列表内发生。
4. **照片 hover 气泡体验差**：鼠标在照片上停留几乎没有延迟就弹出元数据气泡；在气泡上滚动会滚动整个网页，而不是照片列表。

**体验方向（用户提出）：** 滑动窗口预加载。当前屏幕展示已加载内容，上一屏和下一屏在内存中预加载；滚动时不停滑动窗口，加载滚动方向的内容；点击跳转时加载目标位置的窗口数据（当屏 + 上下预加载）；右侧导航由后端提供专用接口加载。

## 2. 设计目标

- 上下双向无限滚动：向上可加载更早照片，向下可加载更新照片，流始终连续
- 预加载：窗口两端各预留缓冲，滚动接近边界时向滚动方向取下一页
- 导航跳转 = 窗口重定位：加载目标段所在窗口 + 上下预加载 + 锚点滚动，不改变任何筛选
- 后端提供专用导航接口，返回每个分段的 offset + count，前端据此定位窗口
- 修复分割线不可见 / 整页滚动 / 气泡延迟三个 UI bug

## 3. 核心方案：滑动窗口预加载

### 3.1 数据模型

把当前「page + 只追加」的加载模型，改为「完整排序过滤列表上的一个连续窗口」。

- **完整列表**：按当前排序（仅拍摄时间升/降）与筛选（日期/活动/搜索）确定的照片序列，总长度 total。列表本身保持连拍折叠前的全量照片（折叠在渲染层处理，见 3.5）
- **窗口**：内存中已加载的照片，是完整列表上的连续区间。窗口有起点和终点两个游标
- **预加载**：窗口两端各预留一页（pageSize=100）缓冲；滚动接近窗口上沿/下沿时，向滚动方向取下一页，窗口随之滑动
- **内存上界**：窗口超过一定页数（如 10 页）后，从滚动反方向淘汰最远的一页，控制内存不随滚动无界增长

### 3.2 后端：专用导航接口 ListPhotoSegments

新增一个分段导航接口，返回当前排序 + 筛选下每个分段的 `key / label / count / offset`，其中 offset 是该分段首张照片在完整列表中的 0 基位置。

- 分段方式支持 month（月）与 activity（活动）；按天模式的导航仍复用月粒度（与 LB1 一致）
- 月分段：按月份分组，offset = 该月之前所有照片数（依排序方向累加）
- 活动分段：按 timeline 分组，未分类（空标签）排最后，offset 同理累加
- 接口复用 SearchPhotos 的全部筛选/排序参数，保证 offset 与窗口拉取结果对齐（含筛选生效时导航收窄到筛选结果）

前端点击导航某段时，拿到该段 offset，即可算出覆盖它的窗口（目标页 + 前后各一页），拉取后锚点滚动到该段分割线。

### 3.3 前端：窗口缓冲与双向滚动

- **初始化/跳转**：根据目标 offset 计算起始页，拉取覆盖目标段及其上下预加载的页区间，作为初始窗口
- **向下滚动**：底部哨兵进入视口时拉取下一页追加，窗口下沿前移
- **向上滚动**：顶部哨兵进入视口时拉取上一页前插，插入后补偿滚动位置，保证视口内容不跳变
- **淘汰**：窗口超上限时从滚动反方向淘汰最远页

### 3.4 导航跳转 = 窗口重定位

替换原筛选重置式跳转（这是对 LB1 4.2 节「筛选重置式跳转」决策的修订）：

- 点击导航段 → 从 ListPhotoSegments 结果取该段 offset → 拉取覆盖该 offset 的窗口（含上下预加载）→ 锚点滚动到该段分割线 → 高亮跟随
- 不再设置 shotAt 起止或 timeline 筛选，筛选状态全程不变
- 跳转后向上/向下滚动仍可继续加载相邻月份/活动，流连续
- 「回到最新」清空窗口重定位，回到最新一页并重建窗口

### 3.5 与连拍折叠的正交性

- 后端列表返回全量照片（含连拍组封面标记），折叠由渲染层按展示级别（全部展开/精细/模糊）过滤封面
- 窗口的 offset 针对全量列表计算，不随折叠级别变化；分割线基于折叠后的实际渲染照片计算，与 LB1 一致
- 分段导航的 offset 与窗口拉取共用全量口径，折叠仅影响渲染，不影响定位正确性

## 4. 三个 UI bug 修复

### 4.1 分割线不可见

根因：网格组件在渲染时会丢弃非网格项的直接子节点，裸的分割线节点被丢弃，所以一条都看不到。

修复：改用普通 CSS 网格布局承载照片与分割线，分割线跨整行渲染，同时保留响应式列数。

### 4.2 整页滚动

根因：布局使用了会整体滚动的外层容器，sider 与内容区一起滚动，滚到底露出渲染区外的空白。

修复：把照片列表区做成有界滚动容器（固定高度 + 内部纵向滚动），工具栏/统计栏/筛选栏固定，只有照片列表自身滚动。

**修订（2026-08-21，见 backlog LB3）**：上述修复当时只给列表区写了 `height:100% / overflow-y:auto`，高度链并未闭合，实际未生效。UI 组件库 Layout 的内层滚动容器是 block 布局，其 Content 子组件自带的 `flex` 属性因此失效、高度塌成 auto，下游各级 `height:100%` 逐层解析为 auto，列表区高度等于自身内容高度，`overflow-y:auto` 永不生效。连带后果：整页仍在滚动、右侧分段导航跟随滚走、滚动高亮不跟随，而且滚动加载彻底失效——列表区不产生 `scroll` 事件（早期的 IntersectionObserver 写法同因失败：root 不是滚动容器时哨兵恒定相交，回调只在 observe 那一刻触发一次）。

补充修复：把 Layout 内层滚动容器改为纵向 flex，header 不收缩、content 取 `flex:1 + min-height:0`，补齐高度链，列表区才真正成为有界滚动容器。

### 4.3 气泡延迟与滚动穿透

根因：气泡默认无延迟、且默认挂载到 body，导致几乎瞬时弹出，且在气泡上滚动时事件落到 body 而非列表容器。

修复：给气泡加触发延迟（约 300ms），并改为就地渲染，使气泡上的滚轮事件冒泡到照片列表容器，随列表一起滚动。

## 5. 已确认决策

- **导航接口实现方式**：新增 proto RPC，走既有 proto → pb.go → OpenAPI → TS SDK 管线，前端调用保持类型化（codegen 工具链已确认可用）。
- **筛选语义**：ListPhotoSegments 接收与 SearchPhotos 相同的筛选参数，导航随筛选收窄，offset 始终对齐筛选结果，点击跳转落在筛选结果内。

## 6. 边界情况

- shot_at 零值的照片：不归入月/活动段，排在流末尾，不进导航（沿用 LB1 约定）
- 未分类（空 timeline）散图：活动导航排最后，offset 按空标签分组累加
- 删除照片导致某段清空：重新拉取 ListPhotoSegments 刷新导航与 offset
- 窗口触及列表两端：offset 越界时收敛到 0 或 total，不再向越界方向加载
- 排序方向切换：全量列表顺序反转，窗口清空重建并回到最新
- 分段方式切换：照片不重拉，仅重新计算分割线与导航（沿用 LB1），offset 仍按当前全量列表
- 筛选变化：重新拉取 ListPhotoSegments 刷新导航，窗口重建

## 7. 验收标准

- [x] 预加载：滚动接近边界时提前加载，无明显等待
- [x] 后端导航接口返回正确的分段 offset + count，前端据此定位正确
- [x] 分割线按天/月/活动三种方式可见、正确跨行
- [x] 只有照片列表滚动，整页框架不滚动，无渲染区外空白（当时误判为通过，2026-08-21 补齐高度链后才实际生效，见 4.2 修订）

## 9. 第二轮：导航精度 + 散片时间线 + 时间线管理页 + 顶栏重排

> 2026-08-21 规划。第一轮滚动基础功能验收通过后暴露的四个问题，拆为 LB4（导航精度，纯 bug 修复）、LB5（散片自动时间线 + 时间线管理页，后端数据模型变更）、LB6（顶栏 UI 重排，纯前端）三个条目。LB4/LB6 无依赖可先行，LB5 内部后端先行、前端管理页随后。

### 9.1 LB4：导航跳转不准确

**现象**：点击右侧导航跳转后落点有偏差，高亮跟随也不准。

**根因分析**（两处独立缺陷）：

1. **高亮跟随的坐标系错误**：`updateActiveNav` 用 `getBoundingClientRect().top <= 80` 判断分割线是否越过视口顶部，但 rect 是浏览器视口坐标，而照片列表顶端在视口下方约 200px（工具栏 + 统计栏 + 筛选栏总高）。阈值 80 永远不成立，函数每次都走兜底分支「取 top 最小的分割线」，即 DOM 中最靠上的一条，跳转后高亮落在目标段之前的段上，滚动时高亮滞后。修法：阈值改为相对滚动容器顶端换算（`el.top - scrollRootRect.top <= 80`）。
2. **跳转锚点误差**：`handleNavJump` 以分割线 `scrollIntoView` 落位，但分割线在流中的位置受连拍折叠影响（折叠时只渲染封面），且窗口重定位后 DOM 需等渲染完成才能定位。表现为落点与目标段首屏有数行偏差。修法：以目标照片卡（分段首张渲染照片）为锚点定位，且在 `await relocateTo` 后等待流渲染完成再滚动。

**方案**：修 `PhotoManagement.vue` 的 `updateActiveNav` 坐标换算与 `handleNavJump` 锚点选择，不涉及后端。

### 9.2 LB5：散片自动时间线 + 时间线管理页

**现象与需求**：部分照片没有活动时间线，当前归入「未分类」，在活动分段导航中无锚点（空键不可导航）。用户要求：

- 后端为无活动的照片自动填充散片时间线（如 `2026-08-散片1`），提供新拍摄活动后重算时刷新该值
- 时间线的查看/编辑/保存/重算做成独立页面

**散片分组规则**（与用户确认）：按时间排序后，两个相邻活动（时间线事件）之间的散片连成一串，串内按月份切开，每段命名 `YYYY-MM-散片N`，N 为该月内散片段序号（同月多段递增）。例：活动 1 与活动 2 之间有 100 张散片，前 50 张 1 月、后 50 张 2 月，则分别为 `2026-01-散片1`、`2026-02-散片1`。

**重算语义**（与用户确认）：保留人工值。

- photo 表新增 `timeline_manual` 布尔列，页面改 timeline 时置 true
- 重算规则：手动标记的照片不动；其余按事件表匹配，匹配不上给散片名；现值既不在事件表、也不匹配散片命名、也非手动的（如事件已改名/删除），视为过期，重算
- 散片名是自动产物，重算时整组重新计算（上月散片吸收新照片后 N 变化）

**数据存储**（与用户确认）：时间线事件从 `data/timeline.json` 迁移到数据库表。

- 新表 `timeline_event`：id、date、event 名、备注、创建/更新时间。遵循项目约定不建外键
- 保留一次性的 JSON 导入迁移（启动时检测表空且 JSON 存在则导入，之后 JSON 文件退役）
- `loadTimeline` 改为读表；`findEventByTime` 匹配算法不变（窗口天数沿用配置）

**后端接口**（走 proto → pb.go → OpenAPI → TS SDK 管线，沿用 ListPhotoSegments 的确认决策）：

- TimelineService 扩展 CRUD：ListEvents / SaveEvent（新建与更新合一）/ DeleteEvent
- 新增 RecomputeTimelines：全量重算照片 timeline（异步后台执行 + 进度轮询，复用 RebuildBurstGroups 的运行状态模式），返回 running / already_running
- 散片生成逻辑放在重算流程内：事件匹配不上的照片按上述规则生成散片名

**前端独立页面**（`/timelines`，侧边菜单新增入口）：

- 事件列表：日期、活动名、该活动照片数，按日期排序，支持增删改
- 「重算时间线」按钮：触发 RecomputeTimelines，进度展示，完成后提示刷新照片库
- 散片组只读展示（在列表中以区分样式呈现，不可编辑，重算自动生成）

**照片库侧联动**：

- 时间线筛选下拉的数据源改为 ListEvents（散片名混入其中，不再需要「未分类」sentinel：散片填充后理论上不存在空 timeline 照片）
- 保留 sentinel 兼容一小段时间（历史照片尚未重算时仍可能为空），前端下拉仍显示「未分类」项

### 9.3 LB6：图片管理顶栏重排

**现象**：功能叠加后顶部三行（动作行 / 统计 + 视图控制行 / 筛选行）拥挤错乱。

**方案**（最终版：单行顶栏，2026-08-21 按用户两次反馈定型）：

- 顶栏单行，左侧从左到右：「图片管理」标题 + 总数（`共 N 张`，只读）+ 视图控制（展示级别 / 分段方式 / 排序方向）+「更多」弹出触发器（信息 i 图标）；右侧四个动作按钮（VLM / Embed / 连拍分组 / 上传）
- 「更多」弹出面板（NPopover，就地渲染）收纳：文件名搜索、筛选组（拍摄日期范围、活动）、统计组（数据完整 / VLM待处理 / Embed待处理，只读）、「重置」
- 弹出面板中的操作即时生效（改日期即触发筛选、搜索回车即过滤）
- 筛选/搜索生效时「更多」触发器上显示角标（搜索 / 日期 / 活动计数），提示有激活条件
- 布局遵循 `docs/ui-rules.md`：8px 网格间距、单焦点、左信息右操作

> 修订说明（2026-08-21）：初版把视图控制、统计摘要、搜索都收进「筛选·视图」弹窗，用户第一次反馈视图功能与统计应直接可见，仅筛选收纳；第二次反馈进一步明确：不要另起一行，改为单行，标题右侧只放总数（`共 N 张`），其余统计数据与搜索仍收在「更多」里，视图控制放「更多」左侧。最终定型为上述单行结构，弹窗改名「更多」、图标改为信息 i 图标。
