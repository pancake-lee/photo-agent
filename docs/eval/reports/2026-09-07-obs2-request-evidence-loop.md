# OBS2 请求级 V5 优化证据链闭环评估

> 评估对象：OBS2 的请求级路由、执行、成本、时延、结果与反馈关联。  
> 评估日期：2026-09-07  
> 范围：代码、离线测试与前端构建；未调用真实 LLM 或修改真实照片数据。

## 摘要

**8.4/10，通过。**

每个聊天请求现在以同一 `trace_id` 串联 `chat.request`、`chat.route_decision`、`chat.execution_summary`、`chat.answer` 与可选 `chat.feedback`。执行汇总记录路由类型、执行结构、技术状态、端到端时延、LLM 调用次数、输入/输出 Token 与成本；同一用量快照也写入助手消息。SQL/RAG/Tool/Combined/Runtime 均经过统一入口与 LLM 工厂，因此具备相同的请求级度量口径。

## 评分

### Runtime 轨迹可复盘性：9.0/10

得分点：

- 原有 Runtime 的决策、执行、恢复、归约、检查和终态事件保持完整。
- Trace 回放新增聊天层事件，并与 Runtime 事件共同展示，单次请求不再只呈现循环内部片段。

失分点：

- 非 Runtime 直接路径的内部工具步骤仍以执行汇总而非逐步事件表达，适合路径比较但不等同于 Runtime 级逐步诊断。

### 全路径执行可观测性：8.5/10

得分点：

- 分类原始输出、最终 `query_type`、执行结构与技术终态均写入结构化 Trace。
- 统一入口保证 SQL、RAG、Tool、Combined、Runtime 的请求汇总字段同构；异常抛出时也写入失败汇总。

失分点：

- 分类器当前输出的是封闭类别，尚不包含可独立验证的复杂度特征解释；这不阻碍记录 V5 路由结果，但 Route Quality 仍需在积累样本后结合用户反馈判断。

### 成本与延迟可归因性：8.5/10

得分点：

- LLM 工厂为当前请求自动附加用量回调，覆盖原先未接入全局 Token 回调的 Text-to-SQL 与 RAG 调用。
- `chat.execution_summary` 和助手消息的 `usage_json` 均保存输入/输出 Token、调用次数、成本、是否有价格表和端到端 `duration_ms`。

失分点：

- 模型供应方若不返回标准 `token_usage`，调用次数仍可记录，但 Token 与成本只能为零；记录明确保留 `cost_tracked` 状态。

### 结果与用户反馈可判定性：8.0/10

得分点：

- 技术终态随执行汇总保存，助手消息持久化该请求用量和 Trace。
- 聊天界面提供“有帮助”和“需改进”两个显式反馈入口；反馈写入独立记录并回写原 Trace，关联消息、会话、路由和用量。

失分点：

- 未反馈不等于接受或拒绝，后续分析必须把无反馈单独统计，不能把它直接计为成功。

### 长期趋势可用性：8.0/10

得分点：

- Trace 回放有效窗口由 7 天扩展为 30 天，足以承载近期高频路径、p50/p95 与成本趋势的采样。
- 每条请求已有可按执行结构、技术状态和反馈聚合的原始字段。

失分点：

- 当前没有历史生产样本，因此还不能下结论称某个路径已经高频稳定；本项评估的是采集能力而非样本规模。

## 验收核验

- [x] 同一 `trace_id` 下可记录路由决策与执行汇总。
- [x] 执行汇总含执行结构、技术终态、端到端耗时、输入/输出 Token 与成本。
- [x] 助手消息保存请求用量，用户反馈可关联原 Trace。
- [x] Trace 回放包含聊天层事件；定向测试覆盖请求用量、工厂自动回调、汇总事件与反馈关联。
