# V0–V3 目标达成回顾与对话能力专项核验

> 报告 ID：`2026-09-07-v0-v3-goal-retrospective`
> 评估对象：V0–V3 各版本退出条件的实际达成情况，以及用户提出的三个对话能力疑问（多轮连续性、历史压缩、预设问答+兜底路由）。
> 评估方式：设计文档（`docs/design/architecture/00–07`）与源码走查对照。未启动服务、未调用 LLM、未读取真实照片数据。
> 参照系说明：本报告有两个参照系。「版本目标达成」对照的是各版本自己声明的退出条件；「对话能力现状」对照的是通用 Agent 对话产品应有的能力。两者结论分开陈述，不互相折算。

## 摘要

- **V0–V3 既定目标：达成（8.0/10，通过）**。四个版本各自的退出条件都有可追溯证据（测试、trace、复评报告），V3 最终复评 8.3/10 已闭合。
- **用户三个疑问全部属实**：无多轮连续性、无历史压缩、入口仍是封闭类别分类 + 默认兜底。这与架构文档的规划一致：这些缺口被明确划在 V4（Planning + Context）范围，V3 设计文档写明"本轮不引入 Planner、Memory"。
- **"是否走出预设问答"的答案是分层的**：Runtime 执行层走出了（循环内按 Goal+State+Observation 选能力，新目标只需契约+能力组合）；入口目标层没有走出（一次性的 7 类封闭分类，Runtime 目标空间固定 3 种，类别外开放请求静默降级为单步检索）。
- **进入 V4 的判断**：V4 文档的进入条件（"新组合请求主要靠复用；任务变长、上下文开始过载"）前半已由 V3 满足；后半的实际痛点不是单任务过长，而是对话不连续，这正好落在 V4 的 Context Engineering 与"多轮修改"设计范围内。V4 方向成立。

## 分维度评分

### 维度 1：V0–V3 版本目标达成 — 8.0/10

得分点：

- 每个版本有明确的退出条件，且都有量化证据链，不是"感觉做完了"：
  - V0 退出（量化固定路由边界）：Runtime 通用性专项评估（4.9/10 通用框架视角）确认窄化定位并登记 AR15，即"已知道自己不能做什么"。
  - V1 退出（多步任务稳定走到目标）：AR6/AR7 山西请求闭环 + 确定性终态，单测 52→177。
  - V2 退出（注入失败仍能恢复或正确停止）：AR2-7 九个图级故障注入场景，恢复成功率 100%、正确停止率 100% 基线锚定；两次真实质量门误判（trace `d36e7fe3f912`、`17f974291b1f`）均定位到根因修复而非叠容错。
  - V3 退出（两目标复用同一 Runtime、主题发现 Workflow 化、无新增端到端 Pipeline）：AR3-6~8 闭环复评 8.3/10。
- 演进纪律执行得好：每次只验证一个架构假设（AR15 拆分、跨期对比选为无写操作的压力测试）、简单请求不被迫走 Runtime、真实数据/LLM 回归授权制。

失分点：

- 版本间的"能力现状"没有向用户可见层收敛：架构文档说清了 V4 才做多轮，但产品界面上"会话"先于能力存在（会话列表、历史消息 UI 都有），用户预期与实际能力之间出现落差。这个落差没有在任何用户可见处声明（如产品文案或界面提示）。
- V3 的 New-Pipeline Rate 等指标靠离线替身回归锚定，真实流量下的复用证据仍单薄（真实回归仅两个授权用例）。

### 维度 2：会话多轮连续性（现状能力）— 2/10

> 阶段适配说明：该项在 V0–V3 范围内从未被承诺，低分描述的是现状能力水位，不判 V3 交付失败。

得分点：

- 存在一个真实可用的会话内续跑机制：Runtime 澄清槽位（AR11）。`needs_clarification` 终态会保存原目标，用户短回复日期/时间线后拼回原目标续跑（`server.py:792-798`），且 `confirm_kind` 区分回复标签。这是多轮交互的最小雏形，方向正确。

失分点：

- **无历史拼接，确认属实**。`send_message` 只把当前问题（或澄清拼接串）传给 `agent.route()`（`server.py:814-819`）；`PhotoAgent.route(question, granularity, tracer, progress_callback)` 完全无状态（`photo_agent.py:683-722`），`RouterState` 无任何历史字段；SQL/RAG/Tool/Combined/Runtime 五个下游节点全部只消费 `state["question"]`。
- 澄清槽位是单槽、单场景（相对日/时间线歧义），一次对话内的其他任何指代（"刚才那组""不要那么文艺"）都无法解析。
- CLI 的 `sessions resume` 只是把历史打印给人看，随后的每条消息依旧独立路由（`photo_agent.py:986-987`）。
- 请求体 `SendMessageRequest` 仅 `question + granularity`（`server.py:417-420`），前端也未传历史，前后端都没有承担这件事。

### 维度 3：历史压缩与上下文组装（现状能力）— 1/10

> 阶段适配说明：同上，属 V4 Context Builder 范围。

失分点：

- 全仓 grep 确认不存在任何针对对话历史的选择、压缩、摘要逻辑。命中的"摘要"全部是照片描述提取（`post_studio.py`）、无进展状态签名（`state.py:505`）、SQL 结果格式化（`text_to_sql.py`），与对话历史无关。
- 会话消息在 `session_store` 中只作为展示数据持久化（messages 表），推理路径上从未被读取。
- 由于历史根本不进入上下文，"有策略的压缩"无从谈起——缺的是整条链路，而不只是压缩策略。

### 维度 4：开放目标覆盖（是否走出预设问答）— 5/10

分层评估：

- **Runtime 执行层：7/10，走出了**。循环内每步按 Goal + State + 最近 Observation 选择能力（V3 核心）；能力有 Tool/Skill/Workflow 契约；跨期对比复用了检索/详情/范围解析能力而未新增端到端 Pipeline——"预设固定管线"在执行层已被打破。
- **入口目标层：3/10，没有走出**。确认属实但有一处需要修正用户表述：入口不是字面关键词匹配，而是 LLM 分类器（temperature=0），泛化能力强于规则匹配。但结构上仍是 V0 形态的 Intent Routing：
  - 一次性决策、决策单位是整个 Query、输出离散类别（`photo_agent.py:77-147` 的 `CLASSIFY_SYSTEM` 七类：sql / rag / tool / combined / runtime_post / runtime_comparison / runtime_topics）；
  - 未命中任何类别时 `else → rag` 静默兜底（`photo_agent.py:142-143`）；
  - Runtime 目标空间固定 3 种（`state.py:22-24`：social_post / photo_comparison / topic_discovery）。
  - 后果：一个不在三类开放目标内的新开放请求（如"帮我整理废片打分排序""生成年度摄影报告"）要么被塞进 sql/rag/tool/combined 得到浅层单步回答，要么被误标为某个 runtime goal 后违反其目标契约，用户得不到任何"系统不认识这个目标"的信号。
  - 缓解因素：这是 V3 设计文档明示的兼容性边界（"目标或交付变体必须来自入口识别或显式结构化选择"），是刻意取舍而非疏漏；且"封闭类别 + 兜底"对单步请求是合理设计（V5 也保留 Direct Tool 路径），问题只在于开放目标侧没有出口。

## 专项核验结论（对用户三问的直接回答）

1. **"没有连续对话能力，每次请求独立工作流，没有拼接历史"** — 属实。唯一例外是 Runtime 澄清续跑单槽。
2. **"没有对历史记录做有策略的压缩加入上下文"** — 属实，且程度更深：历史完全不进入推理路径，压缩只是缺失链路的一环。
3. **"对话设定在几个特定问题上，先匹配、匹配不到走默认兜底"** — 基本属实，一处修正：匹配是 LLM 分类器而非字面关键词；兜底是 `rag`。"是否真正走出预设问答"：执行层走出，入口层没有，目标空间仍是 3 个枚举值。

## 对进入 V4/V5 的方向性判断（不构成方案）

- 三个缺口（多轮连续性、上下文组装与压缩、入口开放性）与 V4 文档已规划的三块（Context Builder、Memory、多轮修改）高度对应，V4 方向不需要重新论证，需要的是把范围按痛点排序。
- 入口封闭分类（AR18）在 V4 文档中没有直接对应章节（V4 假设目标已确定，处理的是任务内计划与上下文），规划 V4 时需要单独决策它属于 V4 还是 V5（Adaptive Routing）。
- V4 的验收指标表已有 Multi-turn Task Success / Constraint Retention 等项，可直接承接本报告登记的问题。

## findings_for_backlog

1. AR16：同一会话内每条消息都是无状态独立工作流，除 Runtime 澄清单槽外不读取任何会话历史，指代与追加修改全部按新请求处理。
2. AR17：对话历史只作展示持久化，推理链路无任何历史选择、压缩、组装机制，前后端请求契约也仅携带当前问题。
3. AR18：入口为七类封闭 LLM 分类 + rag 静默兜底，Runtime 目标空间固定三种；类别外的新开放目标会被降级为单步检索或误配目标契约，且用户无感知信号。
