# 后端代码质量评分标准

> 可执行范围：以 [`tools/list_backend_eval_files.go`](../../tools/list_backend_eval_files.go) 的输出为唯一文件清单。运行 `GOTOOLCHAIN=local go run ./tools/list_backend_eval_files.go` 后，人工确认其输出再开始评估。
>
> 用途：在后端功能开发前、功能完成后或日常治理时，统一判断代码是否可继续演进。本文是评估准则，不包含具体重构方案；评估发现的问题按评估模式写入 backlog，再由规划模式决定修复方式。

> 范围维护：新增、移动或改变生成方式的文件时，只修改清单脚本及其自检用例；本评分标准不重复维护路径、后缀和模板排除规则。

## 1. 评分方式与结论

- 总分 100，按八个维度加权；评估报告同时记录 `总分 ÷ 10` 的十分制分数，以兼容现有评估报告。
- 每个维度必须列出可复查的得分点、失分点和证据位置（文件、测试输出、接口响应或日志）。不能以“感觉良好”给分。
- 80–100：可作为后续功能的稳定基础；60–79：可用，但应将明显问题列入 backlog；低于 60：不建议在相同边界继续叠加功能，应先规划治理。
- 以下任一情况属于阻断项：核心用户用例失败、数据写入错误或不可逆丢失、未授权的 SQL/文件访问风险、并发数据竞争、已知的生产 panic。存在阻断项时，结论为不通过，综合分最高 59。

| 维度 | 权重 | 核心问题 |
| --- | ---: | --- |
| 功能正确性与数据完整性 | 18 | 行为、接口契约和数据状态是否正确 |
| 分层与职责边界 | 14 | 业务逻辑是否位于恰当层次 |
| 风格一致性与可读性 | 10 | 是否易读并遵循既有约定 |
| 抽象、复用与复杂度控制 | 10 | 是否消除重复且不过度设计 |
| 健壮性、并发与可观测性 | 12 | 失败路径是否可控、可定位 |
| API、安全与兼容性 | 10 | 输入、权限、文件和迁移是否安全 |
| 测试策略与用户用例闭环 | 16 | 是否以合适粒度证明核心行为 |
| 废弃代码与文档同步 | 10 | 是否不存在误导性的遗留实现 |

## 2. 评分维度

### 2.1 功能正确性与数据完整性（18）

检查实现是否符合 PRD、设计文档和 API 契约，且数据库、文件与逻辑关联的数据最终一致。

- 高分：主路径、边界输入和失败写入均有证据；分页、筛选、排序、连拍组等业务语义在接口与存储之间保持一致；删除、迁移和异步队列能完整处理关联资源。
- 扣分：接口响应与实际落库不一致；更新只改一侧状态；错误输入被静默接受；迁移不可重复执行；把数据库外键约束当作业务一致性的唯一保障。
- 重点证据：Service/DAO 调用链、API 契约、SQLite 查询结果、相关 Go 测试和用户用例的前后状态。

### 2.2 分层与职责边界（14）

检查传输、业务、持久化、文件/外部服务职责是否清晰，依赖方向是否符合 Go Backend 的职责边界。

- 高分：HTTP/Proto 层只完成参数和响应适配；Service 组织业务规则和事务性流程；`data` 层以业务语义函数封装全部 ORM、生成查询对象、原始 SQL 和只读数据库连接；外部 VLM、Embedding、EXIF、文件操作有明确边界。Python Agent 仅通过 Go API 访问数据与文件。
- 扣分：handler 或 DAO 承担完整业务流程；SQL、文件写入或 HTTP 调用散落在多个业务入口；循环依赖；Service 直接使用 ORM、生成查询对象、原始 SQL 或只读数据库连接；为一次性流程新增与现有 Service 平行、重叠的实现。
- 命名检查：单表访问以明确动作命名，例如 `GetPhotoByID`；跨表、聚合或组装访问以返回的业务对象命名，例如 `GetUserInfo`。仅为复用 ORM 调用而暴露泛化 DAO，或让 Service 自行传入任意查询条件，均不符合此边界。
- 注意：具体纳入与排除结果以清单脚本为准；人工 Proto/SQL 需要检查路由、字段、默认值和表关联是否与手写调用层一致。

### 2.3 风格一致性与可读性（10）

检查命名、文件组织、错误处理、日志和注释是否与项目现有 Go 规范一致。

- 高分：命名说明业务语义；函数保持单一目的；复杂判断可从代码直接理解；注释说明“为什么”而非复述代码；日志有稳定前缀、关键上下文和恰当级别。
- 扣分：同一概念多种命名；大函数混合解析、查询、写入和响应组装；魔法数字/字符串散落；复制粘贴后遗留旧名称；无意义注释或注释与代码不符。
- 参考：`docs/handbook/coding-conventions.md` 的 Go 规范优先于个人偏好；格式化问题可由 `gofmt` 直接验证，但不以格式化通过代替可读性评审。

### 2.4 抽象、复用与复杂度控制（10）

判断重复是否被恰当收敛，且抽象没有脱离当前业务语义。

- 高分：重复的业务规则、解析逻辑和资源清理有单一可信实现；复用已有 pgo 工具和现有 Service 能力；类型、接口和 helper 的边界清晰且被多个真实调用点需要。
- 扣分：同一规则在多个 handler/Service 各写一遍；无实际复用的接口、通用框架或“万能 helper”；为了少量相似代码引入过深层级；把不同业务强行合并导致条件分支膨胀。
- 判断原则：先看变化原因是否相同，再决定是否抽象；“代码行数更少”不是抽象成功的充分证据。

### 2.5 健壮性、并发与可观测性（12）

检查异常输入、外部依赖失败、并发访问和运行诊断能力。

- 高分：错误被原样保留或带上下文返回；超时、取消、文件句柄、临时文件和 goroutine 生命周期明确；共享状态受同步保护；后台/队列任务有可理解的进度、失败原因和阶段日志。
- 扣分：忽略 `error`；以宽泛 `recover` 掩盖根因；不受控的 goroutine；重复请求可能破坏状态；外部调用无超时；失败只有“操作失败”而无定位信息；以容错分支掩盖应修复的配置或数据问题。
- 重点检查：上传/删除、VLM/Embedding 调用、SQLite 写入、批处理队列、文件路径和并发 map。

### 2.6 API、安全与兼容性（10）

检查接口演进是否安全，用户输入是否被正确限制，存量数据是否可平滑读取。

- 高分：API 保持响应字段和状态码语义一致；SQL 仅允许预期的只读/写入路径；文件名和路径不能越界；敏感配置不进入日志或仓库；增量迁移幂等，旧数据有明确兼容语义。
- 扣分：字符串拼接 SQL 或路径；将内部错误/密钥返回给调用方；破坏现有 API 而无迁移；配置模板与实际读取项分叉；迁移依赖危险的表结构变更或未验证的执行顺序。
- 项目约束：表关联使用普通列与 Service 层一致性，不新增数据库外键；安全与一致性应由代码和验证证明。

### 2.7 测试策略与用户用例闭环（16）

目标是以最低必要成本建立可信闭环，不追求机械的 100% 单元测试覆盖率。

- 高分：测试分层合理，独立逻辑有快速单测，关键用户路径有高层验证；失败时能定位到明确层级；测试数据自行清理且不修改表结构。
- 扣分：只测 mock 而未证明用户可见结果；只跑编译；为薄适配层堆叠无价值单测；依赖真实 LLM/外网导致测试不稳定；未覆盖最重要的异常或数据状态。

测试选择规则：

- **必须写单元测试**：纯函数、解析/转换、连拍折叠、筛选和阈值决策、SQL 安全校验、路径处理、可替换的外部客户端边界等独立功能逻辑。每项至少覆盖正常、边界和异常输入。
- **优先写 Service 集成测试**：涉及 DAO、SQLite 或多个业务步骤的一致性规则。测试通过公开 Service 行为断言数据状态，使用清理函数移除测试数据，禁止修改表结构。
- **必须建立用户用例闭环**：每个关键功能至少有一个从用户动作到可观察结果的高层用例，例如“上传照片 → 元数据和缩略图可读取”“修改拍摄时间 → 列表排序与 EXIF 一致”“启动队列 → 状态推进且失败可见”。可用 HTTP/API、CLI 或稳定的脚本完成，不要求为每个业务分支都写单测。
- **不纳入测试与评分**：清单脚本未列出的文件。人工 Proto/SQL 应由编译、契约测试或用户用例间接覆盖。
- **可不单测**：单纯 DTO 映射、无分支的路由注册、第三方库自身行为；但仍须由编译、契约测试或用户用例间接覆盖，并在评估报告说明理由。
- **最低自动证据**：在 `backend/` 下运行 `GOTOOLCHAIN=local go test ./...`；必要时增加目标包的 `go vet`、竞争条件测试或 API/CLI 闭环。新增测试应先证明此次风险最高的逻辑，而非追求覆盖率数字。

### 2.8 废弃代码与文档同步（10）

检查是否存在已经失效、无调用、与当前架构矛盾或会误导下一次开发的手写代码、配置、脚本和文档。

- 高分：删除旧实现及其无效入口、测试、配置和文档引用；保留仍有效的迁移兼容代码时有明确期限和存在理由；API、技术文档与实际实现一致。
- 扣分：无调用的 Service/路由/组件仍留在构建中；同时存在两套相同业务流程；`abandon`、`legacy`、过期注释或旧配置持续误导；文档宣称的端点、数据流和测试入口与代码不一致。
- 清理判定必须有证据：确认构建内无引用、路由/OpenAPI/配置/脚本无入口、无存量兼容承诺。不能只凭文件名或一次文本搜索删除。
- 评估模式只记录问题，不删除代码；经规划确认的清理任务必须同步移除关联测试、配置和文档，并以全量测试及关键用户用例证明没有回归。

## 3. 后端评估执行清单

1. 明确范围：运行 `GOTOOLCHAIN=local go run ./tools/list_backend_eval_files.go --self-check`，人工确认输出的完整文件清单，再确定本轮目标 Service/API、数据表、配置和用户用例。
2. 建立调用图：从人工维护的 Proto 路由到手写 Service、DAO、外部客户端和数据文件；生成接口只作为边界节点，不展开到生成物。
3. 收集静态证据：阅读实现与规范，搜索调用点、重复实现、过期路由/配置/文档；执行 `gofmt` 检查和必要的静态检查。
4. 收集自动证据：运行 `GOTOOLCHAIN=local go test ./...`，并针对高风险路径补充目标测试、`go vet` 或 race 检查。
5. 执行用户用例闭环：选取最能代表价值和风险的 1–3 条链路，记录输入、接口/CLI 行为、数据最终状态和日志。
6. 按八项评分并写报告：维度分、加权总分、阻断项、得分点、失分点和证据。问题仅描述现象、影响和位置，写入 backlog 等待规划。

## 4. 评估报告补充模板

后端专项报告在通用评估报告格式之外，增加以下内容：

```markdown
## 后端范围与闭环

- 范围：<手写 Service/API/配置>
- 关键用户用例：<动作 → 可观察结果>
- 自动验证：<命令及结果>
- 数据状态证据：<查询/API 响应/日志>
- 阻断项：无 / <现象与证据>

## 加权评分

- 功能正确性与数据完整性：<x>/18
- 分层与职责边界：<x>/14
- 风格一致性与可读性：<x>/10
- 抽象、复用与复杂度控制：<x>/10
- 健壮性、并发与可观测性：<x>/12
- API、安全与兼容性：<x>/10
- 测试策略与用户用例闭环：<x>/16
- 废弃代码与文档同步：<x>/10
- 总分：<x>/100（<x.x>/10）
```

## 5. 使用边界

- 本标准适用于新功能前的基线评估、完成后的质量复评和日常后端治理。
- 发现的清理、测试或文档问题必须独立建 backlog 条目，避免混入任一功能任务的验收范围。
- 仅当阻断项关闭、关键用户用例闭环可运行且不存在会误导后续开发的废弃边界时，才建议继续在对应边界上扩展功能。
