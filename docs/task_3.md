# Photo Agent - 第三轮开发计划

## 目标

在前两轮已完成 MVP 和 Python AI 服务层的基础上，本轮聚焦**检索质量提升**、**产品能力扩展**和**工程稳定性加固**三个方向。

- 两轮已完成：Go 后端核心 + Dify Agent 联调、LangChain/Chroma/Text-to-SQL/LangGraph 全链路、AI 工程保障（重试/降级/Token 追踪）、RAG 评估体系
- 本轮目标：让检索更准确、让 Agent 更聪明、让系统更稳定

---

## 一、Phase 1 — 检索质量提升（核心体验，P0）

### 1.1 混合检索：向量 + 结构化过滤器

**现状**：查询路由将请求分为 SQL 或 RAG 两个独立分支，但"找云南的雪山"这类问题需要同时用到语义（雪山）和结构化（时间线=云南）。当前要么走 SQL（查不到语义），要么走 RAG（查不到时间线过滤）。

**方案**：

- 新增**混合检索分支** `hybrid`
  - 先用 Text-to-SQL 生成带 `WHERE timeline='xxx'` 等条件的过滤子句
  - 但**不执行 SQL**，而是提取过滤条件 → 传给 RAG 作为元数据过滤（Chroma `where` 参数）
  - 在已过滤的子集中做向量检索
- 路由分类器扩展为三分类：`sql` / `rag` / `hybrid`
  - "用 Nikon 拍的雪山照片" → `hybrid`
  - "我有多少张照片" → `sql`
  - "找日落风景照" → `rag`

**验收标准**：

- 新增分类器能正确识别 10 个混合查询场景中的 8 个以上
- 混合查询的 Top-5 准确率高于纯 RAG（在评估集中验证）
- 不引入额外 API 调用（复用已有 Embedding 和 LLM）

### 1.2 多轮对话上下文感知

**现状**：`photo_agent.py` 的 `_chat_loop` 每次调用 `agent.route()` 都是独立的，用户说"上一张""再找找""只要有人物的"这类追问完全无法理解。

**方案**：

- `RouterState` 扩展对话历史字段：`history: list[tuple[str, str]]`
- 分类节点和回答节点均注入历史上下文
- `_classify_node` 中，用户输入如果是单句代词/省略（"上一张""再细化"），用 LLM 结合历史做**指代消解**，恢复完整查询
- `hybrid` 分支中，如果上一轮已做了时间线过滤，本轮追问可直接复用过滤条件

**验收标准**：

- 支持 4 类典型追问：
  - 指代追问："上一张" → 能引用上一轮结果
  - 条件追加："只要有人物的" → 在上一轮基础上叠加过滤
  - 否定修正："不要夜景的" → 排除上一轮中的某些结果
  - 范围扩展："再找找类似的" → 放宽检索条件

### 1.3 RAG 评估集扩充与基线建立

**现状**：`evaluation.py` 只有 6 条评估查询，覆盖度不足。

**方案**：

- 扩充到 20~30 条黄金查询，覆盖：
  - 物体检索（猫、花、车等）
  - 场景检索（海边、雪山、城市夜景）
  - 颜色/光线（红墙、蓝调时刻、逆光）
  - 情感/氛围（温馨、孤独、热闹）
  - 组合查询（湖边的日落、雪山上的人物）
- 运行评估建立当前基线，记录 P@10 / R@10 / MRR
- 尝试两种分块策略（`none` vs `fixed_size`）对比，选择最优策略固定

**验收标准**：

- 评估集 ≥ 20 条，人工标注完成
- 当前最优分块策略的基线指标记录到 `docs/eval_baseline.md`
- Phase 1 完成后再次评估，验证混合检索带来的提升

## 二、Phase 2 — 产品能力扩展（超越 PRD）

### 2.1 相似照片推荐

**功能**：用户问"这张雪山照片还有其他角度吗？"或"帮我找和这张照片风格相似的"

**方案**：

- 基于 Chroma 向量库的**以文搜图**已具备，扩展**以图搜图**：
  - 用户传入 photo_id → 获取该照片的描述向量 → 在 Chroma 中做近邻搜索（排除自身）
- CLI 新增 `--similar {photo_id}` 模式
- Agent 聊天中新增 `similar` 意图，路由到相似推荐分支

**验收标准**：

- `python chain/photo_agent.py -c config.yaml --similar DSC_001` 返回 Top-5 相似照片
- Agent 聊天中输入"和 DSC_001 风格相似的照片"能正确返回

### 2.2 智能相册自动生成

**功能**：Agent 自动发现照片库中的主题聚类，生成"虚拟相册"。

**方案**：

- 基于 Chroma 向量做**层次聚类**（HDBSCAN 或 K-Means + 肘部法则）
- 每个聚类用 LLM 生成主题标签（如"云南雪山系列""城市蓝调时刻"）
- Go 后端新增 `/api/albums` 接口，返回自动生成的相册列表
- 不修改数据库schema，相册为**动态生成**（运行时聚类），避免持久化带来的同步问题

**验收标准**：

- 对 300 张照片聚类，生成 5~15 个有意义主题
- 每个主题有 1 句 LLM 生成的描述
- `/api/albums` 返回 JSON 列表，包含相册名、照片数、代表照片

### 2.3 摄影报告生成（P1 创作建议的深化）

**功能**：用户输入"分析我的 2024 年摄影风格"，Agent 生成一份结构化的摄影报告。

**方案**：

- 复用 Go 后端 `/api/photos/stats` 的七维统计 + Chroma 向量聚类结果
- 设计报告模板（Markdown）：
  - 概览：拍摄总量、最常去的地方、最常拍的题材
  - 器材偏好：常用品牌/镜头/焦段分布
  - 时间规律：季节性分布、一天中拍摄高峰
  - 风格趋势：基于 VLM 描述聚合的主题分布
  - 创作建议：基于上述数据的 LLM 生成建议
- CLI 新增 `--report [year]` 模式

**验收标准**：

- `python chain/photo_agent.py -c config.yaml --report 2024` 输出完整 Markdown 报告
- 报告中引用具体数据和照片示例（非空泛描述）
- 报告生成耗时 < 10 秒

### 2.4 时间线关联分析（P2 落地）

**功能**：用户问"我每年春天都拍什么""我去海边的次数有什么变化"

**方案**：

- Go 后端新增时间线聚合 API：`GET /api/timelines/stats?by=season|year|location`
- Python 侧新增 `timeline_analyzer.py`：
  - 跨时间线主题提取（用 LLM 总结同一季节不同年份的共同主题）
  - 地点重复出现分析（基于时间线标签中的地点关键词）
- Agent 路由新增 `timeline` 分支

**验收标准**：

- "我每年春天都拍什么" → 返回跨年份的春季主题汇总
- "我去海边的照片有什么变化" → 分析不同时期的风格/器材差异

## 三、Phase 3 — 工程稳定性加固

### 3.1 SQLite WAL 模式

**现状**：`AutoSync` 多 goroutine 并发写库存在锁竞争。

**方案**：

- `service.InitDB()` 中执行 `PRAGMA journal_mode=WAL;`
- WAL 模式下读写不互锁，AutoSync 并发导入效率提升

**验收标准**：

- server 启动后确认 `PRAGMA journal_mode` 返回 `wal`
- AutoSync 处理 300 张照片的总耗时对比（WAL 启用前后）

### 3.2 异步后台同步（替代启动阻塞式 AutoSync）

**现状**：server 启动时执行 AutoSync，照片多时启动慢。

**方案**：

- 引入轻量级异步队列：`github.com/hibiken/asynq`（Redis）或 SQLite 轻量队列
- server 启动时：检查是否有未同步的描述文件 → 将同步任务入队 → 立即启动 HTTP 服务
- 后台 worker 异步执行同步，支持进度查询和断点续传
- Go 后端新增 `GET /api/sync/status` 查询后台同步状态

**验收标准**：

- server 启动时间 < 2 秒（无论多少张照片待同步）
- `/api/sync/status` 返回 pending/processing/completed + 进度百分比
- 同步失败后可重试，不丢失中间状态

### 3.3 内存缓存层

**方案**：

- 引入 `github.com/patrickmn/go-cache`：
  - 缓存 timelines / tags 列表（TTL 5 分钟）
  - 缓存照片元数据（TTL 10 分钟，更新时失效）
- 图片服务端点增加 HTTP 缓存头（ETag / Last-Modified）

**验收标准**：

- 重复查询 timelines/tags 的响应时间 < 10ms（缓存命中）
- 图片二次请求返回 304 Not Modified

### 3.4 可观测性接入

**现状**：无监控，出问题只能靠日志排查。

**方案**：

- Go 后端暴露 `/metrics` 端点（Prometheus Client）
  - HTTP QPS / 延迟 P99 / 错误码分布
  - 业务指标：照片总量、导入任务状态、VLM API 调用次数与延迟
- 复用 pgo 的 Prometheus + Grafana + Loki 监控栈
- Grafana dashboard 增加 Photo Agent 专属面板

**验收标准**：

- `curl localhost:10000/metrics` 返回有效 Prometheus 格式数据
- Grafana 中能看到 HTTP 请求延迟、照片总量、VLM 调用成功率
- 不引入 Jaeger（单服务，无链路追踪必要）

### 3.5 优雅关闭与限流

**方案**：

- Go server 监听 `SIGINT/SIGTERM`，关闭前：
  - 停止接受新请求（HTTP server Shutdown with timeout）
  - 等待后台同步任务完成或优雅中断
  - 关闭数据库连接和 Chroma 客户端
- VLM API 调用增加客户端限流（Token Bucket），保护 API 配额

**验收标准**：

- `Ctrl+C` 后 server 在 5 秒内优雅退出，无 panic
- VLM 并发调用被限制在配置值内，超限时排队而非报错

## 四、Phase 4 — 架构演进（可选，视进度）

### 4.1 本地 Embedding 模型部署

**动机**：当前 Embedding 调用火山引擎 API，300 张照片虽然费用低，但后续扩容到数千张时费用累积。

**方案**：

- 评估本地部署 `BAAI/bge-small-zh` 或 `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`
- 通过 `sentence-transformers` 库在 Python 侧直接生成 Embedding，绕过 Go 代理
- Go 代理保留作为备选（通过配置切换）

**决策点**：

- 先做性能对比（本地模型速度 vs API 延迟）
- 再做质量对比（本地模型 vs API 模型的检索准确率）
- 两项均达标才切换默认策略

### 4.2 图片格式自适应

**方案**：

- 图片服务端点 `GET /api/photos/:id/image` 根据 `Accept` 头自动返回 WebP/AVIF/JPEG
- 首次访问时异步转码并缓存，后续直接返回缓存

## 五、实施顺序与依赖关系

```
Phase 1（检索质量）
  ├─ 1.1 混合检索 ←────┐
  ├─ 1.2 多轮对话 ←────┤ 可并行
  └─ 1.3 评估扩充 ←────┘
        ↓
Phase 2（产品扩展）
  ├─ 2.1 相似推荐 ←──── 依赖 Chroma 向量库（已有）
  ├─ 2.2 智能相册 ←──── 依赖 2.1 的向量近邻能力
  ├─ 2.3 摄影报告 ←──── 依赖 stats API（已有）
  └─ 2.4 时间线分析 ←── 依赖 Go 后端新 API
        ↓
Phase 3（工程稳定）
  ├─ 3.1 SQLite WAL ←── 独立，高优先级
  ├─ 3.2 异步同步 ←──── 依赖 3.1
  ├─ 3.3 缓存层 ←────── 独立
  ├─ 3.4 可观测性 ←──── 独立
  └─ 3.5 优雅关闭 ←──── 独立
        ↓
Phase 4（架构演进）←──── 视前三阶段进度选择性实施
```

**建议优先级**：

1. 3.1 SQLite WAL（影响启动性能，改动小）
2. 1.1 混合检索（核心体验提升）
3. 1.3 评估集扩充（为 1.1 提供验证依据）
4. 1.2 多轮对话（Agent 智能感的关键）
5. 2.1 相似推荐（产品差异化亮点）
6. 3.2 异步同步（影响日常使用体验）
7. 其余按需并行推进

## 六、验收总标准

- 混合检索 Top-5 准确率较纯 RAG 提升 ≥ 10%（基于扩充后的评估集）
- Agent 支持 3 轮以上连贯对话，追问理解准确率 ≥ 80%
- server 启动时间 < 2 秒（异步同步模式）
- Grafana 能看核心指标（HTTP 延迟、照片量、VLM 调用）
- 新增 2 个产品级功能（相似推荐 + 摄影报告 / 智能相册 / 时间线分析 三选二）
