# 3.4 评估报告

- **报告 ID**：eval-3d3e1b7a8f2c
- **日期**：2026-07-27T18:30:00
- **对象**：3.4 主题发现选题相似度过高 — 三阶段编辑视角提案

## 摘要

**总分 4.2/10 ❌ 不通过**（阈值 6.0）。

三阶段编辑视角提案的代码设计质量整体可接受（Stage 1 的随机采样+编辑直觉思路正确，三阶段边界清晰），但存在一个阻塞性基础设施问题：Stage 2 的 RAG 检索依赖 Go 后端的 /v1/embeddings 代理接口，该接口因 Go 端缺少 Embedding 配置段的 APIKey/BaseURL 而恒定返回 500。导致主路径永远无法走通，运行时 100% 回退到旧版三维度属性分析，实际选题建议与改进前完全一致——仍是按单一属性值归类的高相似度照片组合。Stage 1 消耗 LLM token 产出了有趣的主题直觉（'触摸与拥有的瞬间'、'行走的姿态'、'自然的调色板'），但因 Stage 2 失败而全部丢弃。另有代码重复（JSON 解析逻辑两份）、_fetch_all_photos 仅返回 300 张照片（数据库 1,177 张）等次要问题。整体评分 4.2/10，评估不通过。

## 分维度评分

### 代码质量

#### 正确性 4

得分点：

- Stage 1 随机采样逻辑正确：9 张照片覆盖 9 个不同日期（296 个日期中选取），实现了日期多样性
- Stage 1 LLM prompt 设计合理：不暴露日期信息，引导 LLM 做视觉内容层面的跨上下文编辑思考
- Stage 3 的 prompt 要求按叙事逻辑排序照片而非按时间，契合设计意图
- 回退机制正确连接：Stage 1 无产出或 Stage 3 无提案时自动回退到备选三维度路径

失分点：

- Stage 2 RAG 检索依赖 Go 后端 `/v1/embeddings` 代理接口，该接口因 Go 端缺少 Embedding 配置（Embedding 段空白→回退到 VLM 段也空白→BaseURL 为空串）而恒定返回 500，导致主路径永远无法走通
- 实际运行 100% 命中回退路径，三阶段编辑视角提案是死代码
- _fetch_all_photos 仅返回 300 张照片（数据库实际 1,177 张），Go 后端 SearchPhotos API 或 SDK 分页逻辑可能导致 Stage 1 采样池缩小

#### 健壮性 6

得分点：

- Stage 1/2/3 逐层有判空和 fallback，不会因单阶段失败导致整个 suggest API 崩溃
- RAG 检索失败时 catch 异常后置空结果，不会阻断后续流程
- Stage 3 扩展照片数不足 _STAGE2_MIN_PHOTOS 时跳过单个选题而非整体失败

失分点：

- 没有在调用 Stage 1 前检查 embedding 服务可用性，浪费了一次 LLM 调用（token 成本）才进入回退
- Stage 2 对 RAG 失败的处理是'跳过该选题'，但当前基础设施下所有选题都会失败，结果每条直觉都触发一次 RAG 请求（均失败）后才回退
- Go 后端 `getEmbeddingConfig()` 的 VLM 回退在 VLM 段 BaseURL 也为空时不做任何校验，静默构造出空 BaseURL 导致不可用的 HTTP 请求

#### 可维护性 7

得分点：

- 三阶段边界清晰：Stage 1/2/3 函数独立，各自有明确的输入输出 dataclass
- 新增的 TopicIntuition、TopicProposal dataclass 与旧的 TopicSuggestion/CandidateGroup 共存，命名区分度好
- 常量统一在文件顶部（_STAGE1_SAMPLE_MIN 等），方便调参
- log 信息完整，每个阶段都有明确的日志锚点

失分点：

- _parse_intuitions_response 和 _parse_legacy_response（约 120 行）使用几乎相同的 JSON 解析策略（直接解析→strip markdown→正则提取→逐对象提取），重复代码
- run_suggest 函数约 180 行（1012-1191），同时容纳主路径 + 回退路径 + 数据采集，职责偏重
- suggest.py 全文 1249 行，三种不同的 section 划分方式混合（Stage 常量区/Stage 函数区/旧代码别名区），后续维护者定位成本较高

#### 简洁性 6

得分点：

- 新增代码无未使用的 import 或死函数
- 随机采样算法简洁（两轮：每日期取 1 → 补充不足），无过度抽象

失分点：

- _parse_intuitions_response 和 _parse_legacy_response 逻辑重复（~80% 相同），可提取公共 `_parse_json_response(raw)` 减少约 50 行
- 旧函数别名 `_parse_suggest_response = _parse_legacy_response` 和 `_build_suggest_prompt = _build_legacy_prompt` 增加了间接层，且没有任何调用方
- Stage 2 的 date_groups 构建和 Stage 1 的 date_groups 构建存在相同的 `shot_at[:10]` 日期提取逻辑，重复了约 10 行


### 功能效果

#### 准确性 3

得分点：

- Stage 1 产出的主题直觉符合设计预期：'触摸与拥有的瞬间'（跨场景人物关系）、'行走的姿态'（姿态线索）、'自然的调色板'（色彩线索），均为跨上下文的编辑视角发现
- 回退路径兼容性好：旧有三维度分析逻辑完整保留，错误场景下至少返回可用的选题建议

失分点：

- 运行时 100% 走回退路径，实际输出仍是旧版三维度的'高频未成组'类选题（5 条建议 4 条是高频情绪词：静谧/轻松/平静），选题相似度问题未得到改善
- 5 条建议的 photo_ids 均为同一属性值的同组照片，照片时间跨度不可知（回退路径不检查时间跨度），不符合验收标准中的'时间跨度 > 7 天'
- '稀缺优质'维度仅返回 2 张照片的选题，不符合验收标准'至少包含 5 张照片'

#### 完整性 4

得分点：

- 三阶段工作流在代码层面完整实现：随机采样→RAG 扩展→LLM 提案，每个阶段函数可独立测试
- 设计方案中的关键参数均落地为常量（_STAGE1_SAMPLE_MIN=6、_STAGE2_MIN_PHOTOS=5、_STAGE2_MAX_PER_DATE=2）

失分点：

- 设计方案步骤 3.6 验收标准中'照片时间跨度 > 7 天'仅在 Stage 2 日志中输出天数，未在最终 TopicSuggestion 结构体中携带，API 消费者无法获取
- 设计方案中提到的'照片顺序按叙事逻辑排列'因 Stage 3 从未成功执行而无法验证
- 设计文档 listing 的'回退路径'仅在 Stage 1/3 失败时触发，不包括 Stage 2 基础设施故障的场景——当前情况是 Stage 1 成功但 Stage 2 全部失败，设计未覆盖此路径的降级策略


### 用户价值

#### 惊喜度 2

得分点：

- Stage 1 LLM 生成的 3 个主题直觉（'触摸与拥有的瞬间'、'行走的姿态'、'自然的调色板'）体现了真正的编辑视角——不是按属性归类，而是按叙事线索跨上下文连接，若能在最终输出中呈现将带来惊喜

失分点：

- 实际呈现给用户的输出 100% 来自回退路径的'高频未成组'类选题（'静谧时光合集'、'雪山之巅专辑'、'轻松一刻合集'），这些选题本质上仍是按单一情绪/场景属性值归类的同质化照片组合
- 用户看到的选题建议与功能改进前完全一致，没有感受到任何编辑视角或跨上下文连接的惊喜

#### 可用性 5

得分点：

- 输出格式与之前一致（title/angle/rationale/photo_ids/category），API 消费者无需改动
- meta 中新增 pipeline 字段告知调用了哪个路径，便于运维排查

失分点：

- 选题建议中的 photo_ids 是后端 SDK 的内部 ID，前端展示需要额外拼接图片 URL，用户无法直接从 JSON 判断照片内容
- angle 描述泛化（'记录慢生活的闲适状态，如午后街边、居家小憩。发一组生活片段，倡导松弛感。'），可以套用在任何一组生活照片上，缺乏针对性的可执行建议

#### AI 增量 5

得分点：

- Stage 1 的'随机采样 → LLM 编辑直觉'流程是真正的 AI 增量：随机性引入偶然发现，LLM 做人类编辑般的模式识别，这是简单统计无法替代的
- Stage 3 的'按叙事逻辑排列照片序列 + 为每张照片赋予叙事角色'也是 LLM 独有能力

失分点：

- 运行时实际走的回退路径中，AI 增量仅停留在 LLM 润色——将统计出的属性值分组（'静谧 45 次'）包装成选题标题（'静谧时光合集'），核心发现工作由简单频率统计完成
- 该功能的 AI 增量设计优秀但未生效，属于'有图纸没盖房'的状态

## 下一步建议

- Stage 2 RAG 检索失败：Go 后端 /v1/embeddings 代理接口因缺少 Embedding 配置段（Embedding.APIKey/BaseURL 为空且 VLM 回退也为空）恒定 500，导致三阶段主路径永远回退到旧版三维度
- Stage 1 LLM 调用浪费：在 embedding 不可用时，3 个主题直觉的生成消耗了 LLM token 但全部因 Stage 2 失败而丢弃，应前置 embedding 可用性检查
- _fetch_all_photos 仅返回 300 张照片（数据库实际 1,177 张），Go 后端 SearchPhotos 或 SDK 分页需排查
- _parse_intuitions_response 与 _parse_legacy_response 约 80% 逻辑重复，可提取公共 JSON 解析函数
- 设计方案未覆盖 Stage 2 基础设施故障的降级策略：当前只有 Stage 1 无输出或 Stage 3 无提案时才回退，Stage 2 全部失败不在回退条件中
